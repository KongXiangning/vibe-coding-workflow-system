# Current requirements, design and changes

Read selected requirement/goal/design bodies, declared constraints, related summaries
and recalled discussion summaries before updating. Expand only relevant raw fragments.
Verify current explicit intent against historical sources; do not let task plans
freeze business goals or use modified time to pick a truth. Read code only when
needed to describe actual implementation; an adopted design is still a target.

For a formal added requirement, analyze the complete requested increment first:
read its raw request and affected current definitions, trace normal and important
exception paths, quality/interface combinations and actual impact on parent or
shared capability. Present concrete added/changed acceptance and exclusions,
separating new current obligations, clarification of existing meaning and optional
future enhancements. Do not copy a coarse new heading and leave its essential
behavior undefined, or expand into unrelated project analysis. Proposals remain
proposals; use the actual adoption to save the increment and local arrangements.
An already explicit adopted decision is sufficient and is not asked again.
Ordinary narrow fixes, explicit maintenance deferral and bounded exploration do
not trigger this full-increment method or a mandatory overall plan.

Apply real requested changes to current body. New/add/modify/defer/cancel/restore
are ordinary scope updates: planned/candidate/retired do not mean done. Split or
merge by retaining retired/withdrawn prior IDs and declaring replaces/derived_from
with actual destinations, not reusing an ID for another meaning. Restore old words
only as requested; do not infer rollback or reuse old PASS. Preserve unaffected
acceptance, exceptions, exclusions and still-valid explicit user decisions.

For a material change retain old and new intent in change.deltas with actual basis.
Capture recoverable old scope only as needed and within authorized capture_paths;
unknown previous content stays null with an explanation. A wording/formatting fix
does not require a change record. Plan arrangement changes can target the plan
and name stable work IDs in note. Do not create a duplicate authoritative body in
the change or discussion. New substantive workflow departures follow the existing
one-time informed-choice rule; this is not requirement approval.

Update related design when authorized: actual implementation/differences and
unsynchronized portions remain explicit. Adopted != implemented. Delivery summaries
require actual sources and checked implementation subjects. A retired obligation may
be withdrawn with its failure retained; if that failure affects remaining capabilities,
describe that actual scope. Never require repairing retired scope before honoring
new intent, stopping or continuing other authorized work.

For v3/v4/v5 keep root_goal_id an explicit project choice and current part_of/supports
relations distinct from dependencies and historical replaces/derived_from. Adding
a child retains the parent's identity/scope by default; real replacement needs
explicit withdrawn coverage and the corresponding old scope/relations changed,
not just a replaces edge. Preserve any other goal the old item still supports.
Maintain one project requirement_order: initial adopted decomposition order, then
the helper appends successfully saved new v2/v3/v4/v5 requirement IDs in batch/file-item
order when a unique usable v3/v4/v5 project exists. An explicit order supplied or
removed in the request takes precedence, including an intentionally empty order.
Do not migrate the requirement files merely to register order. If project order
maintenance is pending/failed, retain saved requirements and retry only that update;
v2-only additions without a usable v3/v4/v5 project keep their legacy save behavior,
while v3/v4/v5 additions report pending order maintenance. Read back the final project
and requirement files after the batch; the order follow-up is a separate per-file save.
Only an explicitly adopted reorder changes existing positions; record its basis
and old/new order. Dependency, task, work-item and report changes never reorder it.
Keep all readable unordered requirements visible rather than inventing order.

## Local contribution checks after changed obligations

Use binding-contribution.md after an actual requirement, acceptance, adopted Task
scope or coverage change affects a related binding. Read both the old obligation
and the changed one; preserve valid historical attribution instead of assigning
new obligations retroactively. Reclassify only supported affected relationships,
under their existing IDs with coverage/reason/sources and necessary prior material.
Unreviewed relations and unknown old classifications remain readable, not globally
invalidated. A classification-only correction does not rewrite requirement bodies,
create a new business requirement, change order or prepare a successor Task.

Maintain delivery separately through reconcile.md; a changed binding is not evidence
of satisfaction. A failed source check or whole-file byte change is not automatically
a changed business definition. Only a real authorized obligation/arrangement change
uses the existing Roadmap maintenance below. Do not require roadmap current before
saving contribution, and do not replan all work for a metadata correction.

## Adopted structure in the same maintenance pass

Read the actual request, affected definitions and adoption/source basis before
choosing structure. Complete-current planning includes adopted capability that
will be implemented later or has no Task; original obligations do not require a
historical Task to exist. Formal increments analyze only the increment and its
actual impact, not the whole project on every update.

Use a parent requirement for an adopted capability with business scope whose
delivery matters, and child requirements for independent functional or quality
obligations. Pure navigation may use module; it is optional and not a delivery
assessment target. Keep examples, simple detail and acceptance conditions in the
body. Original feature numbers are not automatically independent objects.
Reuse identities for classification, rename and moves. A shared capability has
one identity/body with multiple source-backed paths, not copied definitions or
automatically inherited TaskBindings. Moving detail to a child leaves the parent
with overall scope/common constraints and references, not a second current copy.
Organization may create needed structure IDs within existing adopted scope; it
must not add KPIs, device matrices, architecture promises or other obligations.

declared means explicitly recorded with traceable adopted/source-grounded basis,
not that the user recited an internal ID. Within maintenance authority, save
declared + active for an already adopted hierarchy, a relationship explicit in
formal source material, or clearly delegated classification of existing scope
with sufficient basis and no business expansion. Assign/reuse actual IDs without
another per-edge confirmation. Label Agent paraphrases accurately and retain the
real source. A broad inventory request does not adopt every new inferred relation;
title/code similarity, a convenient unused parent or Agent authorship alone do
not decide origin. Keep new uncertain relations inferred or unresolved, preserve
prior rejections and never bulk-convert inferred links. Adoption proves neither
implementation nor execution authority.

For each affected operation, save and verify together within this authorized pass:

- Addition: complete definition, sources, scope, established parent/goal links and
  append the new identity in project.requirement_order.
- Refinement: retain the parent, append independent children with child→parent
  part_of, and reference detail moved out of the parent body.
- Adopted hierarchy/classification: persist stable entries and core links;
  extensions, body indexes and classification counters cannot replace structure.
- Scope change or real replacement: adjust only affected current relations/scope,
  preserve history/destinations and reconcile applicable reports locally.
- Unknown ownership: save the known definition and actual candidate/unresolved
  basis without inventing a parent or blocking a Task.

Use supports for goal support, part_of for current composition and depends_on for
engineering prerequisites; replaces/derived_from remain historical. Do not copy a
direct supports edge for every ancestor. Migrate only affected v2 definition files
explicitly to v3 when child→parent requirement links are needed, or use a legal
mixed-version layout; a v3 parent does not grant v3 link directions to a v2 child.
Manifest stays v2 and old reports/Task identities/results remain intact. Tree
layout does not move old requirement_order positions next to their parents.

After helper writes, read/check the affected complete items and actual
product_view.current_relations. Compare this pass's adopted paths with saved core
relations; report formed paths, real candidates, unassigned/unsaved parts and
detail retained only in prose. Schema valid, file saved or all classified is not
structure delivery. A legitimately independent requirement is not a defect.
This is a local result check, not a permanent expected-edge database or score;
the helper cannot infer missing business adoption from free text.

One pass may use several helper calls and independent file results. Read current
digests and successful receipts after a conflict; retry only missing definitions,
relations/order or reports. Keep saved work and real Task identity/focus; never
repeat prepare, tests or product effects for a document receipt. Deferral, paused
maintenance or missing PRODUCT retains ordinary task paths and explicit gaps.
These instructions run when the relevant Skill is invoked within authority;
they are not background listening or automatic synchronization of manual edits.

Apply an authorized requirement change first. Definition or goal/scope digest
changes flag the affected reports for local reconciliation; they do not invalidate
achievements, require whole-project evaluation or block the change/task. Put
progress and conclusions in independent reports, not the definition body. Reuse
actual acceptance without adding KPIs. Keep current goal assessment_scopes explicit;
reports do not define today's scope. See reconcile.md for scoped report handling.

Use localized apply updates and read back. Malformed neighbor entries remain intact;
repair only selected structure without restoring the former business meaning.
On partial saves report which current bodies, changes and designs actually saved;
record pending synchronization without blocking development or faking successful maintenance.

Distinguish goal tuning from replacement. A numerical/wording adjustment to the same
business outcome can keep its ID; a materially different outcome retains the former
goal and a replacement destination. Include observed time, population, measurement
scope and unknowns in result material. For v3 put the result in an independent
goal-targeted assessment with its declared scope/object; retain the goal's
requirements separately. Do not add a KPI system. A shipped feature does not prove
that outcome. See reconcile.md for report production.

Before splitting a requirement ask the business question internally: are there
independent obligations, or just several implementation batches? Batches belong in
work_items/tasks under the same REQ; genuine splits/merges preserve prior IDs and
where each scope went. Do not copy historical PASS to every destination.
For a withdrawal distinguish deferred/retired from fulfilled. Existing coupon code
may remain after coupons leave launch scope; shared amount bugs still warrant local
payment/refund impact checks. Do not auto-create cleanup work without current need
and authority. Clear user decisions are implemented without another field approval.

Put long constraints under ### or deeper sections in the selected body's complete
root heading. Read back the whole affected item, including exceptions and diagnostics.
If manual text puts an explicit constraint in an appendix, keep its authority and
locate/repair it within the request rather than ignoring it as outside the item.
Whole candidates may repair selected malformed fields; retain untouched bad neighbors.
Actual deletions use the API's precise removal declarations, not implicit renaming.

## Current decisions and arrangements

After adopted Requirement/Goal/Design changes, use plan.md to identify affected selected
Implementation Roadmaps by stable IDs and effective relationships. Save authoritative
definitions and necessary Change first, then reread and maintain affected arrangements
within authority. Compare definitions/membership even without Change; do not fabricate a
Change to find manual drift. Unknown ownership is a candidate, not an addition to every
Roadmap. Explicit deferral takes precedence. Advance planning_baseline only after actual
impact review; successful definitions remain intact when Roadmap writes partially fail,
with pending differences rediscoverable on next consumption. Retry only the failed part.

A clear adopted decision within existing maintenance authority updates the affected
current goal/requirement body, necessary change basis and related arrangement in
one scoped maintenance pass. Read affected relationships; preserve unrelated bodies
and delivered history. Alternatives and questions remain undecided. Do not require
archiving the full chat or invoking discussion first: an accurately labelled text
SourceRef can retain the current decision or its summary. Use discussion only when
selected original material is actually requested for preservation.

If the decision needs machine-readable display order, maintain an applicable plan's
work_items or a small local plan when none exists, following plan.md. The Agent
chooses the document/fields, without asking the user for an internal strategy.
New scope after a closed task retains that task's original coverage and evidence;
a new authorized task serves the added scope, without inheriting old PASS.

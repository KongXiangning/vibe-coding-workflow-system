# Observations, local impact and E6 repair

Implementation Roadmap reconciliation is separate from delivery assessment. Use plan.md
and read/check roadmap_query for the selected scope's baseline differences; current means
reviewed versions match, never delivered/PASS. Task closure or binding never satisfies a
whole Requirement or a real engineering prerequisite. Preserve cross-stage work such as
REQ-20's W20-A and W20-B independently of actual Task creation. Report missing baseline,
unread/unassigned scope and failed saves without suppressing historical delivery. First
baseline initialization can reconcile existing achievements without redoing old Tasks.
An explicit no-adjustment/deferred decision binds exact reviewed versions and sources;
new versions retain old history but need reassessment. Do not move a baseline simply
because a new definition was read. Read-only reconciliation writes nothing. Closure
keeps local delivery scope and parent continuation priority, with no full-project scan.

An actual external/user observation can exist without any task. Save obtained
material via capture or registered source; label user report, external log and
Agent reproduction separately. Discussion suggestion and actual observation may
cite one raw fragment but are different facts. Never create a verification task
just to receive a failure or assert Agent reproduction of a user report.

Read selected requirement/goal, applicable scoped reports (or legacy assessment_id), original reports and actual
implementation subjects/input coverage. Use impact_ids to get direct candidates,
then read their bodies and judge actual dependencies. Ordinary references and
inferred links do not invalidate an entire graph or mandate project-wide rechecks.
Expand only actual impact; unknown/no-impact remain explicit. Reuse existing
debugging/execution capabilities for product root cause, not a maintenance debugger.

An unchanged requirement/file digest cannot hide new counterevidence. Add obtained
related sources to selected assessment.pending_sources when not yet reconciled,
or save a new scope-specific assessment and explicitly select it. Preserve the
original reports and prior assessment where a conclusion materially changes.
Compare historical byte availability, requirement definition alignment and current
implementation applicability separately. Working-copy label is not a precise
code snapshot. Different subjects/inputs explain distinct results, not automatic
mixed. Unknown is valid; other reported labels need actual source and exact coverage.
Repeated unchanged read/check does not append assessments or timestamps.

## New counterevidence: finish the local impact pass

Treat this as part of normal reassessment, including a request naming only one
requirement. After saving the new observation once, read the selected requirement
and inspect helper `impact` hints. Scoped item/assessment reads include them by
default; explicit `impact_ids` selects the seed. Candidates include direct links,
shared active Task identities and scoped/code file sources, even without a declared
requirement dependency. A shared overall goal or unscoped business Markdown alone
is not a reason to evaluate every requirement. Hints never certify actual impact.

Read candidate definitions and existing reports, then map the observed behavior to
their concrete obligations. Also use the known implementation entry and actual
input/output when metadata cannot locate a relevant requirement; no candidate is
not proof of no impact. Preserve no-impact/unknown judgments with their reasons in
the original report's impact section, without a second observation database.

For each directly affected scope, save a local reconciliation or add the exact
new SourceRef to the applicable report's `pending_sources`. Reuse the original
probe/log bytes and report unknown version/input applicability; do not rerun work,
create TaskBindings, change acceptance or erase older results. If no applicable
report exists, retain the requirement/scope/evidence locator and missing declaration
in the originating report. If maintenance is read-only, paused, deferred, outside
authority, conflicted or unread, return those precise pending locators and save only
within existing authority. A related save failure does not undo the main report.

Example: an empty MD aborts judicial directory import before per-item results.
Record it against judicial handling and check batch import's per-item terminal and
failure-isolation obligations. An older batch PASS cannot hide this counterexample;
persist pending evidence there if full reconciliation is deferred. A name containing
a type keyword does not automatically invalidate an unrelated Evidence coordinate
contract. Explain the actual affected behavior, not transitive graph reachability.

Read back each saved affected report/pending source separately. Return evaluated,
no-impact, pending and unsaved direct scopes; a main report saved/selectable alone
does not mean its known impact has been handled. Do not recursively reevaluate the
project or turn unfinished maintenance into a development gate.

## One detailed assessment and linked summaries

Before saving, choose the existing applicable detailed report or create one independent
scope/object report using the current contract. Preserve distinct objects, runs,
failures and scopes; reuse a report for unchanged reads, and use explicit same-location
supersession when its conclusion is replaced. Do not choose by filename or recency.

Keep the complete functional-point table, acceptance checks, evidence/limits and
remaining work in that report only. PROJECT and existing progress/implementation
reports may retain a short coverage/result/pending summary and a Markdown/SourceRef
link to the detailed item. Do not paste the full new report into those old surfaces
or refresh their checked_at/verification as if an additional evaluation occurred.
Use existing links/SourceRefs, not a new required summary schema or report registry.

Helper `ASSESSMENT_BODY_COPY` is a read/check/apply warning for matching full bodies
on the same target. Inspect the actual objects before treating them as mirrors;
independent factual reports remain separate. For an authorized mirrored current
surface, preserve its old bytes via existing history/preimage and maintain only
the brief summary/link. Do not delete historical duplicates, edit frozen files,
auto-merge reports or shorten independent evidence merely to clear the warning.
Read the saved detailed report and each navigation/summary back. Only those selected
reports and actual new impact are maintained; unrelated summaries stay untouched.

E6: one requirement, original E6A/B/C plan work items, actual task/step refs where
they exist. After A/B disposition, an external import failure can insert E6R with
origin=added, problem source, original requirement coverage, repair binding to A
history and specific affected scope. The script being A's delivery does not prove
A introduced its defect. Keep original A/B decisions and stable C ID. A repair
before C must explain order/real prerequisites; closing repair is not reliable data.
No automatic reopen/resume of A/B, replacement of C or replan of every Runtime task.

After actual repair acquire real checks for the actual implementation version and
inputs; reconcile that scope into the summary and retain residual/pending sources.
Task close is not PASS and does not clear pending_sources. Early/current/evolved/
retired requirements retain their historical attribution; current repair binds
the scope actually served without restoring retired goals or recertifying old PASS.

For contradiction/omission reconcile body, design, plan, bindings, assessment and
sources locally. Do not choose by newest file. Maintenance may be deferred by
user instruction; list saved material and unsaved documents separately. Failures
of summary/binding do not block implementation, commit, closure or stopping.

Withdrawn scope can legitimately keep an unresolved historical failure. Determine
whether shared implementation still affects retained payment/refund or other current
capabilities; keep that risk scoped instead of requiring all old defects fixed.
Historical CSV attribution and current Excel repair are separate bindings. If current
compatibility support is explicit it still needs coverage; retired alone does not
erase that obligation. Pure history without current effect/authority can be recorded.

For goal result material use its actual requirements/sources and observed measurement
scope. In v3 an independent goal-targeted assessment is valid; it is not a task or
child-count aggregate. For split requirements and
multi-owner tasks compare each delivered/input scope individually. Different versions
or new formats do not automatically contradict every historical report. New failure
with unchanged definition must remain pending or be reconciled; repair close never
changes this. Unaffected parts of C may continue under the existing instruction while
the real data prerequisite of affected parts remains unsatisfied.

For sufficiency, contradictions and prerequisite candidates use the shared analysis in
inventory.md. Delivery evidence and material sufficiency answer different questions;
assessment is not a documentation score. Reuse earlier dispositions and preserve the
unread/contradictory/current-necessary/future-optional distinctions in their actual scope.

For next-work selection compare the current complete requirements against actual delivered
and verified coverage, including newly added/modified scope after partial delivery. Keep
historical facts and unknown implementation applicability; do not subtract requirements
because tasks closed or count tasks to compute the remainder. Split/merged requirements
and tightened or restored acceptance need their own current-scope check; old bindings and
PASS stay historical evidence, not automatic certification of each destination or restored
text. Use plan.md to arrange or directly prepare authorized nearby work, with or without
a plan. A partial read establishes only its stated scope, not a complete remaining backlog.

Use useful existing results and explicit user reports to state concrete delivered
coverage, while naming their source, version/applicability limits and remaining scope.
Missing a new full test run does not erase prior reported delivery or make everything
unknown. Conversely a new range is not verified by a closed task's old PASS. Update
only affected assessments/pending sources and arrangements when actual results arise;
no full product retest is required merely to write a progress summary. At task end,
use plan.md for the business next item separately from workflow routing/continuation.

## Rejudge existing requirements and historical bindings

Use this entry for natural-language requests to reassess an ongoing project's
requirements, old Tasks, relations and achievements; no new Skill, required mode
or configuration is needed. Read binding-contribution.md for the sole contribution
method and disposition matrix. This is broader than filling missing enums, but
its writes stay within the actual request:

1. Locate the working copy, stable requirements and current Task/parent continuation.
   Protect existing edits/frozen targets and state the requested local or full scope.
2. Read current definitions and acceptance, important historical changes, Task adopted
   scopes/steps, existing binding reasons and actual results/reports. Use stable
   references to find candidates; titles only help discovery.
3. Compare concrete obligations, Tasks/code/source material, existing relations and
   reports in one scoped account. Keep current versus historical intent and unread
   material explicit. Full-range requests proceed in recoverable batches, not one
   sample declared complete.
4. Apply the shared method to confirm direct/supporting, correct the original ID,
   dismiss a disproven relation, add a proven omission or preserve old unknowns.
   Keep history and rejection protection; no speculative new formal bindings.
5. Independently evaluate delivery only when that phase is requested/already authorized,
   using current goal scope, subject and applicable evidence. Existing implementation
   without a historical Task can be assessed without creating one or a binding.
6. Save authorized local changes with read digests and reread each result. Binding,
   Assessment and definition writes are separate; retain successes, retry only failures.
   Do not call Task prepare/adopt/close/resume/focus/supersede for rejudgment alone.
7. Use plan.md only when the discovered actual remaining scope changes an authorized
   arrangement. Binding-only correction does not require Roadmap review or advancement.
8. Return requested/read scope, relation dispositions, independently confirmed delivery,
   gaps, unknowns and unsaved/deferred parts. Keep the real Task focus/continuation.

Analysis-only writes nothing. Binding correction does not authorize changing acceptance
or Assessment; a request to update delivery does not erase old failed results. Do not
reshape a requirement to match current code, copy old PASS to expanded scope, reconstruct
Task identities from display numbers or use today's review time as old completion time.
Do not force new full tests merely to retain applicable existing achievements.

After actual closure or new debug/validation material, use the same method only for
relations whose coverage/classification is materially affected, preserving original
results. A new failure with unchanged requirement definition still needs scoped
pending_sources/Assessment handling; a supporting Task's closure never promotes its
owner to started/delivered. Read-only review returns exact pending owner/binding/source
locators. Neither local rejudgment nor deferred maintenance can replace parent return,
reopen old work or gate authorized development, Git, closure or stopping.

## Local assessment after task closure

When a child requirement changes or produces evidence, read its actual current
part_of parents and compare only the affected obligation against each parent's
declared coverage. A parent may be evaluated from direct integration evidence;
it does not require reports for every child and never equals all(children).
Adding a child does not by itself invalidate an older explicitly scoped report.
If the new obligation actually changes current parent coverage, reconcile that
coverage locally. If maintenance is deferred or fails, retain the earlier report
and explain the newly unchecked/unsaved scope rather than certifying it from the
old conclusion. Do not recursively invalidate ancestors or other goal scopes.

The host Agent performs semantic evaluation; Runtime saves/queries facts and the
product helper validates, hashes and saves reports. A direct Runtime close does
not call a model. In close-task, save the actual closure first and read task-status
to confirm closed and removed from active focus; separately report publication
gaps. Only then, when maintenance is enabled and the current authority covers it,
evaluate this task's actually related requirements/goals, their current scope and
the evaluated object. Do not evaluate each step, scan all project history or treat
closure as evidence of satisfaction. Pure read-only requests do not save reports.
Read and retain the actual parent continuation/focus first. Product evaluation
and next-business advice do not focus a new task, replace that continuation or
block its already authorized remaining step when maintenance fails.

Read those definitions, relevant declared relationships, existing applicable
reports and available delivery/verification evidence. Take scope_id/coverage from
the selected goal.assessment_scopes, never from an old report or a guessed range;
retain ambiguous/missing declarations as pending scope. Use the reported subject
(working-copy, commit or release and actual revision/limitations) rather than
assuming today's working copy matches a historical result. Requirements, reports,
definitions' alignment and evidence applicability answer different questions.

Judge against the actual agreed acceptance and scope, preserving qualitative
criteria; do not invent KPI thresholds or demand fresh tests just to close or
write a summary. Use the existing four conclusions: satisfied, partially-satisfied,
not-satisfied, undetermined. Partial means known fulfilled and known unfulfilled
portions; known achievements plus unknown remainder is undetermined with those
achievements retained. No report is unknown, not a failure or zero progress. Goal
results require their own scope/evidence, never counts or percentages of tasks,
steps or children. One requirement may have different conclusions for different
goals, scopes and objects; never overwrite them with one global status.

Use API.md and contract.md section 10 to produce independent v3 assessment report
files, not result updates to requirement/goal definition bodies. Save one target
and explicit applicability/subject, actual target/goal source locators and their
definition algorithms/digests, actual checked_at, evidence and the required body
sections (coverage, delivery/verification basis, remaining/pending). Let the
helper compute/check bytes; these checks do not certify the judgment. Preserve
old reports; explicitly supersede only the same exact target/goal/scope/subject
when correcting that conclusion. Read the saved report and scoped selection back
with the helper; report persistence separately from selectable current conclusion.
Legacy reports remain navigable and do not gain missing scope or satisfied from
old PASS. New v3 reports may cite v1/v2 requirements without wholesale migration.

Respect paused maintenance and explicit deferral without reasking. Missing PRODUCT,
unreadable scope/evidence or report write failure leaves closure intact: state the
known achievements, unknown or deferred scope, and any saved/unsaved report. When
enough scope metadata is available, an undetermined report may retain the lack of
evidence; otherwise keep a pending locator without inventing fields. Do not reopen
the task, force tests, create a remedial task or undo an already saved part because
another maintenance write failed. Retry only an authorized failed report/binding
write, preserving concurrent-edit protection and successful task/report identities.

On a direct user requirement change, first save the authorized definition and
only then reconcile the affected old conclusions locally. Changed digests are
check hints, not automatic business invalidation or Runtime admission. Preserve
unaffected goals/scopes and earlier outcomes; do not rerun all evaluation merely
because the same goal's conservative digest also changed for another scope.

# vNext：完整任务管理，不恢复开发准入

实施基线：`da0c3c211749b7349983ec0b41b360b65e0d1573`（0.23.2）。
本设计修正辅助方案把“记录保存成功”等同于“任务操作完成”的缺口，取代旧文档中
“当前状态投影可以长期不维护”的表述。保留辅助型 Runtime 和所有流程偏离的一次确认。

## 职责

Skill 理解用户意图、实施业务、在实质偏离约定时确认一次。管理服务分配任务身份、关联
计划/执行/审查/处置/真实提交，并维护可重建的统一视图。视图不是许可证；未通过审查、
过期证据、未提交改动均不禁止用户选择继续或关闭，也不被自动转换成 PASS/clean。

原始 `record` 继续宽容保存报告；任务动作使用同一个 assistance 服务的 `task` 命令。
`task-status` 和 `context.management` 从全部已保存事件计算当前状态，不采用一页 find
结果、文件名顺序、墙钟时间或旧 CURRENT_TASK 作为最新真相。

## 完整链路

| 动作 | 管理交付 | 不代表什么 |
| --- | --- | --- |
| prepare | 分配稳定 task_id 和显示编号，保存候选计划与步骤、验证及环境 | 不代表用户采纳或当前任务切换 |
| review（draft） | 明确关联被审查的 plan_ref，保留意见及条件 | 不替代计划采纳 |
| adopt | 关联用户实际决定与计划，建立采用计划和当前工作位置 | 不代表已经执行；不自动关闭其他任务 |
| execution / test | 保存任务、计划、步骤、实际版本、结果与命令来源 | 不把失败、未运行或旧结果变成通过 |
| review（change） | 关联实际 execution_ref，保存覆盖范围、发现与审查来源 | 自审不是独立审查 |
| review-decision | 保存修复、接受、暂缓、继续等用户处置 | 不改写审查 verdict，也不清除 findings |
| step | 记录 finished/skipped 等工作处置，计算下一未结束步骤 | 不执行下一步，不认证当前代码 |
| git（按需） | 显式要求持久关联任务与提交时，写入实际 SHA 及管理视图；Git 对象校验只读 | 不作为每次提交的后置步骤，不推导 push/deploy |
| close / pause / resume / focus | 维护处置和工作焦点；关闭后不再作为活跃任务 | 不要求 active/clean，不回滚文件 |

这是默认工作顺序，不是必须逐项经过的状态机。用户可以明确跳过、合并或调整阶段；
Skill 记录一次知情决定并实施选择，服务只描述结果。继续、关闭与验证资格是独立维度。
每次显式调用工作流 Skill，重新读取所选入口并查询当前任务状态。复审后需要结束步骤时，
状态建议 `execute-step` 的 `finish` 模式；用户明确调用该模式后核对证据、记录步骤处置并
回读。默认执行模式不从“没有代码可改”推断结束步骤。

## 派生前置任务与原步骤续接

步骤中发现需要独立交付的前置问题时，可准备派生任务；普通步骤内修复和同任务计划
修订仍使用原身份。派生任务保留独立 task_id 和数字显示编号，`origin` 显式关联原任务、
原计划与原步骤，并保留派生原因、移交范围、原任务剩余范围、返回策略和续接上下文。
不从事件因果 parents、计划修订或任务命名猜父子关系。

准备或采纳候选不会自动切换。明确从原任务切入派生任务时，焦点事件保存当时的工作
检查点，包括计划采纳、生命周期、当前步骤及该步骤的执行/审查/处置事实。原任务保持
未完成状态；等待依赖是视图描述，不要求 pause，不引入开发门禁，也不复制/回滚代码。

派生任务的生命周期与依赖结果分开。`dependency` 或 close 中的同名字段记录实际结果：
satisfied、unresolved 或 cancelled。关闭不推导 fulfilled；satisfied 要有实际结果说明，
Skill 核对交付和适用范围，Runtime 不认证 PASS。原失败、未运行检查和未完成工作保留。

选择 auto 返回策略后，关闭/补登依赖结果的同一事实事件可保存返回效果。只有依赖明确
满足、派生任务已关闭、焦点仍属于该次切入，且原任务仍 active、原计划/步骤/检查点未变，
才恢复原任务焦点。用户切换到别处、改计划、继续原任务、暂停/关闭原任务或并发修改时，
报告未返回原因，允许人工选择。返回只是管理位置恢复，不自动实施、审查、finish 或提交。
派生任务的生命周期和依赖结果也按返回边界的因果关系核对：相互矛盾的并发选择会抑制
返回；明确选择有效关闭/结果后可恢复；返回之后正常发生的后续操作不倒退已有焦点。
return_result 是按这些选择及有效返回事件推导的视图，不作为另一项需重复确认的冲突。
内容一致的并发尝试展示实际有效返回；明确选择未解决结果则保持未返回，不残留待选择项。

恢复后的 continuation 保存续接上下文并建议 execute-step / continue-step；保持原执行、
finding、审查和处置。后续原任务工作改变检查点时，再按真实阶段建议下一入口，不重复
恢复旧位置。事件重放、跨会话读取和 rebuild 均不重跑业务，不追加第二次返回；投影发布
失败与事实保存分别报告。next_task_id/next_step_id 与 next_route 一起说明实际当前焦点。
人工返回可用 focus 的 return_from 关联原派生任务，保留续接上下文和未满足依赖。补登的
historical 执行只增加历史，不视作当前工作变化；真实并发修改需明确选择焦点。
人工返回时，原步骤仍有其他待满足依赖则 continuation 保留 dependency-unresolved；
派生任务生命周期有歧义则保留 child-state-unresolved，均不显示 ready，不构成开发门禁。
派生来源步骤沿用计划投影的统一归一化方式，空/不完整步骤不使整个实时视图不可读。

第一版支持单层、每个原任务/原计划/原步骤一个未收束派生前置任务。旧计划的派生关系
继续保留，但不因步骤 ID 相同而阻止新采纳计划的派生或返回。嵌套或多前置提案保留并说明关联
限制，不静默构造调度关系。已存在的真实派生关系可通过 link/correct 补充原 prepare 解释；
不猜历史返回检查点。具体字段和操作见 runtime support 的 TASK_MANAGEMENT_API.md。

## Git 提交与管理记录

提交事实以 Git 自身的历史为准。普通提交完成后只读核对 Git 并向用户报告 SHA、提交范围
和剩余改动，不自动调用 `task git`、`record`、`rebuild` 或刷新 CURRENT_TASK。
任务视图中的 commits 是显式保存的关联，列表为空不代表没有提交，也不构成补录或再次
提交的理由。非末步成功结束时，`execute-step` 可在当次结果中建议保存该步骤的实际改动，
并说明精确提交范围；这是一次性建议，不授权提交，也不阻止直接实施下一步骤。末步可先
`close-task`，再按用户指令提交。`task-status` 则持续报告当前未完成阶段；实际提交后，
`git-commit` 根据这份状态建议下一入口，不靠 Git 关联判断提交是否发生。

只有用户明确要求持久保存任务/执行与提交之间的关联时，才调用 `task git`。该动作会写
日志与展示；“只读”仅指读取 Git 对象，不能据此把整个动作描述成只读。产生的管理改动
按用户要求处理，不递归提交这些文件来记录它们自身的 SHA。现有管理记录和生命周期
操作继续保留；无需靠删除记录、忽略已跟踪文件或重写提交来掩盖循环。

## 身份与版本

稳定 task_id 不依赖显示编号。新 prepare 分配身份；指定 task_id 的 prepare 是同任务
计划修订。显示编号由不覆盖的编号保留文件分配，并检查当前/已有任务及可识别历史编号；
并发创建不复用同一编号。显示名冲突、分配失败不抹掉原始计划，重建可补充缺失显示名。

计划引用是保存事件的稳定 ref。adopt 必须明确指向采用的计划；候选计划晚写入不会自动
替代已采纳计划。执行、审查、步骤处置保留各自计划和目标引用；旧计划的执行继续出现在
历史中，不伪装成新计划已验证。计划重排后可据已有事实明确补登相应工作处置，无需重跑。

任务事件自动保留当时已观察到的因果 heads。相互矛盾的并发决定保留为冲突，不用最后
写入者覆盖。相同幂等请求使用第一份实际记录，即使后来焦点、步骤或 heads 已变化。
补充和更正只改变当前解释；原始字节、用户原话和失败历史保持不变。

## 统一视图与 CURRENT_TASK

事实仍保存在 `.workflow-system/records/events`；任务管理事件使用同一个日志，不另建
独立审批库。缓存为 `records/task-view.json`，它可以删除并重建，不是第二个权威事实源。

首次正常任务操作保存旧 CURRENT_TASK 的完整历史快照与来源指针；新 CURRENT_TASK 是
明确标记为 `vnext-task-view` 的当前展示。旧 Task Store、task-history、证据 blob 不删除。
不能继续向旧内核写入这份新展示。CLI 的普通 task-context 转到统一视图；`--legacy` 才读
旧格式接口，仅供历史诊断。task-read/export 等旧专用接口不用于回答“现在任务是什么”。

缓存/展示更新在事实落盘之后进行。写入失败返回独立 projection 结果。状态读取总是重新
汇总已保存事实并说明缓存/展示的新鲜度，因此缓存损坏或更新延迟不会静默返回旧任务。
写展示使用短的管理 I/O 锁和原子替换；它不是开发锁。实际活动写入者导致的视图繁忙只
影响本次发布，不影响只读重建或其他原始记录保存。

对旧标准格式只读提取明确的身份、工作处置和活跃步骤字段，不把它重新作为准入条件。
复杂旧计划、编码载荷和自由文本决定仍可能需要链接补充；系统报告未关联记录与来源，
不猜测完整历史、不要求重新 prepare/review/confirm。旧来源不清或新展示被用户修改时，
不静默覆盖；可在保存快照后按明确选择重建展示。

## 恢复与用户选择

| 能力 | 操作 | 约束 |
| --- | --- | --- |
| 重建 | task rebuild | 根据现有记录重算视图；不重跑测试、执行或 Git 操作 |
| 补登 | task link | 用 record_ref 和明确事件含义补齐任务/计划/步骤归属 |
| 更正 | task correct | 追加更正，关联原记录；不覆盖原文 |
| 冲突选择 | task resolve | 明确选择具体冲突的一项来源；其他记录保留 |
| 暂缓 | task defer | 记录待处理事项及用户选择；不把 deferred 显示成 resolved |
| 暂停/结束/切换 | task pause/close/focus | 落实实际选择，保留未完成工作 |

正常确定性维护是操作本身的一部分，不每次询问。无法自动确定的归属/冲突才展示具体
差异让用户选择；已确认的内容不重复审批。无法执行的实际文件 I/O、缺失原文或不存在的
Git 对象不能靠确认变为成功。API 分开报告 recorded、association、projection；不得用
一个 recorded=true 声称关闭/采纳/状态更新全部完成。

## 保持边界与实施限制

不修改产品代码、执行业务命令、清理失败、生成假审查，亦不替代宿主权限控制。
事实无完整结构时仍可保存；解释失败只影响相关管理记录。查找/快照服务继续可用。

本版每次状态查询完整扫描日志，并依据显式关系重建；这消除了第一页/旧缓存误判，尚未
进行大型历史库性能基准。深度关系、任意旧 YAML/自由文本不作无损自动语义推断承诺。
后续增量索引只能作为缓存优化，不得成为准入、授权有效期或保存事实的条件。

本次验证范围、安装边界及已有记录恢复方法见 `docs/ops/vnext-task-management-validation.md`。

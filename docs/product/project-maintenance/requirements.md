# 项目目标与需求维护：需求及能力基线

版本：设计 0.2。入口：[README](README.md)。字段：[文档契约](document-contract.md)。本版包含 VPM-07／08／09／12 扩充及 VPM-24／25 新增；2026-10-08 补充三种规划策略、资料充分性与前置条件候选分析。它们扩展既有能力，不增加 Runtime 模式或管理对象。

## 1. 产品目标

面向频繁调整需求的个人开发者，维护当前产品目标、完整已知需求、相关设计、实施安排和交付依据。业务全貌不能退化成当前 task 或未完成 backlog。已交付需求、后续范围、共享约束及未归类内容仍然可见。

需要能回答：整体要做什么；哪部分已有交付记录；哪些工作正在或准备服务于哪些要求；本次变化影响哪里；曾经讨论过什么。当前意图、目标方案、实际实现、历史报告及当前适用性分别表达。

## 2. 固定原则

| ID | 必须保持的语义 |
|---|---|
| P01 | 产品目标与需求定义当前要做什么；设计定义方案；task 和计划不能反向冻结目标。设计中的明确用户约束不因文件类别而降级。 |
| P02 | 当前工作基线可变；历史版本仅用于解释过去。恢复旧需求文字不证明代码已回退，也不自动复用旧 PASS。 |
| P03 | 正式托管文档使用固定格式，用户和 Agent 适用同一规则；原始来源、用户选定聊天不要求事先格式化。 |
| P04 | 同一当前定义只有一处正文；支持长文档多条目，不强制一项一文件。反向关系和页面索引可重建。 |
| P05 | 项目实施计划、计划工作项、task、task 内步骤是不同对象。项目 plan_id 永远不是 Runtime plan_ref。 |
| P06 | 一项需求可关联多个 task，一个 task 可服务多个需求；角色和覆盖范围属于关联。维护／探索任务允许没有 REQ。 |
| P07 | 交付摘要必须带来源和范围；关闭、采用计划、格式合法、有引用、历史 PASS 均不等于当前完整交付。 |
| P08 | 保存讨论、关联讨论、确认关联、采纳观点是不同动作。归档中的指令和历史授权仅是资料。 |
| P09 | 不引入需求审批、完整性资格、任务前置通行证；保存、解析或同步缺口不新增执行、提交、关闭、停止及修改目标的门槛。 |
| P10 | 非阻塞不授权越权、覆盖并发改动、伪造成功或忽略真实工程前提；只暂停无法安全完成的具体操作。 |
| P11 | 复用有效用户决定；新的实质偏离按现有一次知情确认规则处理。不为每个字段、阶段或内部错误重复确认。 |
| P12 | vNext 维护，TraceLens 只读。新能力不改变现有 assistance 任务生命周期、事实保存、审查、证据、Git 或停止语义。 |

## 3. 完整能力清单

能力编号用于需求追踪，不对应同名命令、23／25 个 Skill 或新的 Runtime 状态机。

### 3.1 基线与业务资产

| ID | 能力 | 必须交付 |
|---|---|---|
| VPM-01 | 托管范围与契约 | PRODUCT 入口、模板、格式校验及精确诊断；分别管理规范文档、只读来源和获授权的原文保存位置。 |
| VPM-02 | 首次业务盘点 | 从用户选定资料整理目标、模块及已知要求；保存盘点来源和未核对范围；先找已有信息、再核对矛盾、最后区分当前必要缺口与未来可选建议，不把代码现状自动提升为已确认意图。 |
| VPM-03 | 当前目标与完整需求 | 同时维护 current／planned／candidate／retired 范围及已交付能力；无 task、无设计、未归类要求仍可见。 |
| VPM-04 | 日常需求变更 | 支持新增、修改、延期、取消、拆分、合并、恢复；局部更新正文，保留未改变的要求、例外和排除项。 |
| VPM-05 | 设计同步 | 维护相关方案及当前实现差异；采用设计不自动表示已经实现，未同步范围明确可见。 |
| VPM-06 | 决定与变化依据 | 保存实质变化的旧意／新意和实际来源；未知旧内容保持未知，小改字不强制建 change。 |
| VPM-07 | 范围化任务关联 | TaskBinding 支持目标／需求与 task 多对多，实施／修复／验证／探索角色，计划工作项及历史交付关联。新建、已关闭及远期历史 task 均可关联。 |
| VPM-08 | 交付与验证对账 | 接纳无 task 的外部观察，按需求范围和实际检查对象核对新旧资料；新失败即使需求未变，也必须被纳入相关对账或显示待核对。 |

### 3.2 变化、历史和可靠维护

| ID | 能力 | 必须交付 |
|---|---|---|
| VPM-09 | 变化及缺陷影响分析 | 从需求、设计、新观察或交付不一致出发找候选，再判断直接影响；普通链接不自动成为强依赖，不要求全项目复验。 |
| VPM-10 | 不一致与遗漏对账 | 找到正文、设计、索引、任务关联和摘要中的缺口或矛盾；按范围说明依据、影响、未知与处置，读取旧处置，不按修改时间选出“正确答案”，不无依据复活已否定建议。 |
| VPM-11 | 手工编辑接纳 | 合法手工编辑直接可读；结构错误局部降级，修格式不把业务改回旧版本。 |
| VPM-12 | 身份和历史连续性 | 稳定需求、计划工作项及真实 task 身份；保留拆分替代去向和历史范围。插入修复不重编号，不自动重开旧 task／恢复 retired 需求。 |
| VPM-13 | 维护触发与延期 | 启用后在相关范围变化、任务建立及新交付资料出现时维护；可明确延期，不每步全项目扫描，不把维护完成挂到任务门槛。 |
| VPM-14 | 安全写入与部分失败 | 保留用户改动，检查读写版本，逐文件报告结果；task 已创建但关联失败时重试只补关联，不重复 prepare。 |
| VPM-15 | 稳定离线读取 | 版本化契约与样例；消费者无 Runtime 仍可读，旧项目不被强制全量迁移或升级。 |

## 4. 使用入口

一个逻辑入口 `maintain-project`，支持整理、更新、规划、收存讨论、对账五种可组合意图。是否最终注册为 mode 及其英文拼写由实现按仓库机制确定，不能改变上述语义或增加审批阶段。

| 用户场景 | 正常路径 |
|---|---|
| 小而明确的需求／修复 | 直接 prepare-task，按需补 TaskBinding；不强制持久 plan。 |
| 预先安排全部已知实施范围 | maintain-project 形成 plan／稳定工作项，说明本次全部已知范围的去向、顺序与前提；未来 task 不必提前建立。 |
| 无总体 plan，持续决定下一步 | 按相关范围核对需求、交付、新反馈与前提 → 选下一项或近期几项 → 在授权内直接 prepare-task；需要时才建局部 plan。 |
| 保留总体方向，细化近期工作 | 混合策略保留架构／阶段／里程碑，区分具体近期工作与粗略远期方向，逐步展开。 |
| 已有合适计划 | 读取、核对并复用，不重复规划；未来 task 不提前虚构身份。 |
| 关键可行性未知 | 可先准备受限探索／验证 task，再细化计划。 |
| 外部验证发现缺陷 | 保存实际材料 → 局部影响核对 → 在既有授权内安排修复／调整计划 → 对账交付。 |
| 用户要求先实现后整理 | 尊重决定，明确待同步范围，不伪报资料已更新。 |

新计划候选不是被采用的安排；采用项目 plan 不等于采用每个 Runtime task 计划。纯产品维护不自动建立 task、不切换焦点、不结束步骤、不执行代码或测试。

### 规划策略与持续选取

三种方式是使用策略，不是三个 Runtime mode 或必填配置。不必每轮询问策略；尊重既有选择，允许按项目阶段或业务范围切换。规划必须说明业务价值、真实前提、风险或用户优先级，阶段名称不替代选择理由。

共同流程为：读取相关目标、完整需求、设计、既有安排和交付依据 → 范围化核对剩余工作、变化与未知 → 提出有理由的选择或总体安排 → 落实已有授权 → 保存并回读。完整需求持续保留；交付过的范围不会从需求正文删除。task 关闭、有无关联或旧 PASS 都不能直接确定完整交付；新增／修改需求之后需核对实际覆盖，保留未知及待验证部分。

持续选取可在 task 结束后或执行中出现新信息时发生，不每轮无条件全项目扫描。用户直接指定下一项时核对该选择的相关范围，不强制比较所有候选。建议本身不授权关闭当前 task 或启动新工作；已有连续实施授权仍按原规则适用。

纯讨论可以只输出建议。需要持久保存且无 plan 时，将必要选取结论、来源、读取范围和未决项写入 project 正文；有适用选定 plan 时写回该 plan。同一当前结论只维护一处，不建立第二份权威 backlog、不复制完整需求。创建 task 必须在实际请求或既有授权范围内，使用现有 TaskBinding；关联保存失败只补关联，不重复 prepare。

### 资料充分性与前置条件候选

分析先读已有信息，再核对矛盾，最后提出缺口。区分已知资料不可读、已读信息矛盾、当前必要信息未说明、未来可选建议。每个重要问题说明关联范围、依据、影响、未知部分及当前处置。信息已存在时不要求另建独立文档；不可读的已知资料沿用 inventory，不虚构文件或把信息缺口当作文件缺失。

前置条件候选须说明为什么需要、是否已满足及依据、属于业务规则／方案条件／实施工作／外部条件、在开发／集成／交付哪个时点需要，以及是否可复用更小的现有能力。例如识别原支付交易可以复用交易标识与查询能力，不自动要求自建钱包。未成立候选保留在 project 或适用 plan 的未决正文；采纳后更新对应 requirement、design 或工作安排。assessment 只用于交付与验证，不作为文档完整性评分。

重新分析先读取已有处置；没有新依据不恢复被否定建议，用户明确改变决定时可以维护。沿用原授权与一次知情选择规则，不新增候选审批流程。执行中确需独立前置任务时复用既有派生路径；单层、单未收束前置任务等执行限制既不扩张，也不转为项目规划限制。

## 5. E6 场景的固定行为

E6A／E6B／E6C 首先是项目计划工作项，可分别关联真实 task；若实际是一个 task 内步骤，则引用原 task＋step_id，不强制转换成三个 task。

用户在 E6C 前自行验证 E6A 交付的导入脚本：不要求补建验证 task；材料可以是日志、选定文本或明确的用户报告。不能把用户报告说成 Agent 已复现。实际观察与讨论建议可以引用同一原文，但地位不同。

新增 E6R 修复时关联原需求、相关历史交付、问题来源及计划工作项。导入脚本在 E6A 实施，不足以证明缺陷由 E6A 引入。保留 E6A／E6B 的历史处置，不自动重开、撤销或替换它们。

E6C 先后安排应表达真实理由；“依赖可靠导入数据”不等于“修复 task 关闭即前提满足”。用户可在原授权与真实风险边界内调整安排，文档依赖不生成 Runtime gate。

需求未变而出现新反证，也需更新选定 assessment 或明确 pending_sources。原报告不删除；修复 task 关闭不自动代表需求复验通过。更早或已经 retired 的需求，分别说明历史归属及当前修复实际服务的范围，不自动恢复旧目标。

## 6. 非阻塞与完整性

维护必须分别报告：实际取得的决定／观察、原文保存、规范文档保存、关联／对账、待处理范围。它们不是其他能力消耗的资格凭证。

结构错误可以使一项资料无法可靠结构化读取；不能据此宣称用户决定无效或整个项目不能工作。真实文件权限、并发改动及工程前提仍要处理，不用“非阻塞”伪造写入／通过。

撤销当前要求可以撤销其当前交付义务，不要求先修复已经退出范围的失败；历史事实保留。若问题仍影响保留能力，再说明相应范围。

### 业务维护闭环补充

- 目标口径／数值调整可保留同一身份；实质不同目标的替代保留旧身份及去向。经营结果材料写在 goal 正文及 sources，保留时间、范围和口径未知，不新增 KPI 或给 goal 套 requirement-only assessment。功能交付／task 关闭不证明目标达成。
- 拆实施工作和拆独立业务要求分别判断：一个 REQ 可有多个工作项／task，必要的需求拆合保留旧范围和来源；不复制旧 PASS 到所有新要求。退出、延期、取消和完成分别表达；业务退出不说明共享代码已清除，也不遮住仍影响 current 能力的风险。
- 受限探索可以在方案不可行时完成探索目标，结果回到设计／计划而非产品交付。近期插入工作区分排序理由和真实工程前提，任务计划仅在其自身范围实际改变时按现有授权修订；不从文档依赖或 task 数量推导状态、排期及完成率。
- 讨论按选定片段整理多议题。未采纳、待确认、明确 dismissed 分别保留；确认关联不采纳观点。当前明确改变原否定是合法新依据，不要求额外材料／关联审批，原否定及改变决定的事实仍保留。
- 历史归属和当前修复范围分别绑定；retired 不自动恢复，也不掩盖现有兼容维护义务。新失败按对象／输入／版本核对，需求摘要未变也须纳入或列 pending，修复关闭后复验仍单独报告。
- worktree 根与 project_id 共同定位本次工作副本，冲突后重读并仅补剩余写入。task 已创建不重复 prepare，原文已存不重复 capture。读取完整性、结构可用性、所列业务盘点和特定交付结论分别报告；延期维护及停止遵守原有效用户选择，不产生维护 gate。

## 7. 首版完成与排除项

首版须覆盖全部 25 项能力的正常路径和关键边界，并提供可安装的 helper、Skill、参考资料、格式资产、示例及使用说明；至少一次真实宿主 Agent 的业务整理、需求更新、讨论关联和 E6 修复闭环。结构测试不能代替模型行为验证。

TraceLens 在本项目中的交付是独立读取契约、样例及对接说明；真实前端改造在获得其仓库授权后实施，未验证不得称 UI 已完成。

不包含：全聊天自动采集、持续监控、需求审批状态机、第二套任务 reducer、图／向量数据库、额外常驻模型服务、全量旧史迁移、自动执行测试／提交／推送／发布／部署、跨项目自动合并。安装和升级不得覆盖项目拥有的 PRODUCT、需求、讨论原文或历史数据。

## 当前决定、可解析安排与旧资料整理

明确采纳且已获维护授权的决定，在同次局部维护中落实到受影响目标／需求完整正文、必要 change 及安排；备选讨论不自动采纳，维护决定不以全聊天归档为前提。需要机器展示顺序时使用现有 plan.work_items 有序数组；无总体计划可建立局部 plan，不需要用户选择内部字段。无顺序展示需求的持续选取仍可写 project 正文。

B 移到已交付 A 前只改变展示安排，保留 A 的身份、日期、交付依据及 task 状态。无 plan 直接 prepare 后，对可确定归属补真实 TaskBinding，plan_items 可缺省；未知归属如实保留。追加范围不重开旧 task、不继承旧 PASS。

旧项目全貌整理按实际来源组合 inventory/update/plan/reconcile：完整正文、已有交付覆盖、适用旧安排、可靠历史绑定及重要变化分别处理。不强制全史／全 CR 迁移。已有结果和用户报告可以支撑范围化进展，缺一次全量新测试不抹去既有报告；总体目标达成仍与功能交付分开。task 结束的下一业务事项与公共 next_route 分开，保留原任务续接及授权边界。

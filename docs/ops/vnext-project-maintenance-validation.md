# 项目目标与需求维护：验收与交付检查

状态：待执行的验收计划，不是测试通过记录。依据：[需求](../product/project-maintenance/requirements.md)、[契约](../product/project-maintenance/document-contract.md)、[实现方案](vnext-project-maintenance-implementation.md)。

## 1. 检查原则

验证声明、复用／运行已有检查、是否新增持久测试是三件事。按实际风险采用最小充分证据，不为每个标题、字段文案或 VPM 编号新增测试。正反样例能检查结构，不能证明模型理解、权限遵守、真实安装或浏览器交互。

所有 E6 task 身份、决定和报告示例均为虚构，不得导入真实项目冒充历史记录。自动化测试使用隔离目录及合成数据；真实项目与聊天材料只在授权范围内读取／写入。

## 3. 结构与算法检查

重点覆盖：YAML 重复键／别名／自定义标签；代码块与引用中的假标题；条目身份重复；必要章节；关系方向；task_id 与显示标签区分；plan_id 与 Runtime plan_ref 区分；工作项重复／环／撤销前置项；历史来源摘要冲突；未知和超范围引用。

定义 hash 要检查：CRLF／LF 归一；正文变化；关系排序去重；assessment_id、TaskBinding、讨论和普通来源变化不引发需求定义自循环；不同文件条目变动不能自动使所有需求失效。文件 bytes hash 与 Git OID 不混用。

写入检查包括已读版本变化、新建路径已存在、程序自身并发、单文件失败及原文 capture 成功但元数据失败。程序只承诺实际实现的 I/O 保证，不用模拟测试声称消除了所有外部编辑器竞态。

## 4. 按实际改动选择命令

下列命令已在勘察基线 package.json 中存在；这份文档没有执行它们。

```sh
node --test test/vnext-assistance.test.mjs test/vnext-task-management.test.mjs
bun run validate:vnext-source
bun run test:workflow-vnext-source
bun run build:vnext-runtime
bun run build:vibe-governance-distribution
bun run test:workflow-distribution
```

前两项原生测试用于相关回归而非每次文档修改必跑；Skill 注册和分发改变时必须有相应证据。若改迁移／bootstrap 路径，再选择当前相应聚焦测试。新产品 helper 测试命令在实施时建立，不能引用尚不存在的命令声称通过。

不要默认运行 test:workflow-all，也不要为文案改动新增 contains／标题快照测试。广泛核心改动确实需要更大回归时说明依据。构建会改变生成产物，应审查实际 diff，不手工修生成文件。

## 5. 四层交付证据必须分开

| 层次 | 需要的证据 | 不代表什么 |
|---|---|---|
| 源码／契约 | Schema、解析、引用、计划／绑定及写入的实际检查结果 | 不代表宿主模型会正确维护业务 |
| 分发 | 构建 bundle 中 helper、Skill、references、模板、Schema 的实际清单和可执行性 | 不代表目标项目已升级 |
| 目标安装 | 干净目录的新装、已有资产升级保留、Node 运行，不依赖源码／Bun | 不代表用户真实项目已经部署 |
| 真实 Agent／消费者 | 一次授权业务整理、更新、讨论关联、E6 场景；离线消费者读取；有条件再验 TraceLens 页面 | 自动化结构测试不能替代语义和界面验证 |

## 6. 完成交付模板

实现者记录实际 commit／工作区基线、改动范围、已完成 VPM、helper 与 Skill 使用方法、实际运行命令及结果、分发／安装证据、真实 Agent 观察，以及未执行检查和限制。未执行就是未执行；不得把权限不足、环境缺失、Schema 通过或虚构样例视为真实场景通过。

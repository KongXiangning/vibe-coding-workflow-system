# TraceLens 与 vNext：目标、需求管理及可视化完整方案

> 方案性质：2026-10-11 讨论定稿。本文整合已确认的产品方向、职责、数据消费、实施范围与验收场景；较早的效果图和中间方案不作为相冲突设计的依据。本次交付仅更新本方案文档，不开始实现、升级或项目资料迁移。
>
> 实现依据：vNext 源码仓库 HEAD 为 `334580494634cbd88c60b62bcdf50345e1b0abe5`（0.24.5），TraceLens HEAD 为 `ba0bc59`。前期评审核对了两个仓库的本地工作区，均含未提交改动；工作区观察不等于这些提交已包含全部改动，也不代表远端最新版本。本文明确区分已有基础与待实施设计，文末列出来源及有限验证范围。

## 1. 产品目标与总体结论

本次建设的目标，是让用户能够直观了解项目当前想达成什么、已经拆分出哪些需求、需求之间有什么组成和支撑关系、现有成果满足了哪些约定，以及各需求通过哪些 Task 推进。

整体设计保留两条相互关联但不互相设置门槛的主线：

- **执行主线**：Task → Step → 执行、验证、审查与生命周期记录。vNext 的首要职责仍是帮助实际工作顺利推进。
- **业务认知与维护主线**：项目总目标 → 必要的子目标或已约定阶段／直接关联的需求 → 当前范围下的达成说明、来源与演变。vNext 协同用户维护，TraceLens 只读展示。

两条主线通过可选的 TaskBinding 软关联。一个需求可以关联多个 Task，一个 Task 可以关联多个需求，Task 也可以完全不关联需求。

最终页面分工：

| 页面 | 主要内容 | 回答的问题 |
| --- | --- | --- |
| 项目概览 | 明确的项目总目标、按项目级登记顺序排列的需求、关联 Task 概况 | 项目要达成什么，已明确哪些需求，目前哪些 Task 正在推进？ |
| 需求视图 | 项目总目标、必要子目标与拆分需求的关联图、当前范围下的达成情况 | 为达成目标需要具备什么，已具备什么，还缺什么，哪些尚不能判断？ |
| Task 详情 | Task 的原有计划、Step、执行及生命周期记录 | 具体工作怎样实施、推进到哪里、留下了什么结果？ |
| 演变详情 | 目标、需求及必要安排的实际变化及来源 | 当前结构和要求是怎样演变而来的？ |

本次不建设自动排程系统、需求审批系统、第二套 Task Runtime，也不将需求全景变成项目准入或任务准入工具。

## 2. 职责边界

### 2.1 用户与 vNext

用户决定业务目标、需求范围、采纳哪些建议，以及实际工作如何推进。vNext 通过现有 Skill 引导宿主大模型读取相关资料、分析与拆分要求、提出关联和后续工作建议，并在有效授权内把已采用的结果保存到项目文档。

`maintain-project` 是用户主动盘点、修改要求和查看成果的入口；范围化成果评估复用现有 `references/reconcile.md`，不新建评估 Skill。`close-task` 默认触发与本次交付有关的局部评估；`prepare-task` 消费相关要求并准备可执行任务，附带局部的可选关联建议。主 Skill 仅保留路由、必要行为和范围边界，按需读取参考文档，不把每次 prepare、close 或 Step 操作扩成全项目分析。

工具负责结构校验、定位、摘要、保存、冲突提示和已有 Task 状态处理，不代替用户或大模型作业务判断。

### 2.2 TraceLens

TraceLens 读取规范项目文档，并以 vNext Runtime 只读查询作为 Task／Step 的主要数据来源；Runtime 不可用时可使用已知快照降级。允许搜索、筛选、展开、布局、按显式关系导航、查看来源及演变。

TraceLens 不创建或修改需求，不采用方案，不决定或重排实施顺序，不改变 Task 状态，不调用大模型重新评估业务，不把图中的依赖变为执行门槛。只读查询不意味着开放 Runtime 的写操作；TraceLens 不执行 `close`、`adopt`、`rebuild` 等任务或修复操作。

页面不提供“新增需求”“确认需求”“关闭 Task”“拖动写回排序”等编辑动作。图形布局的视觉调整不写回业务关系或顺序。

### 2.3 软关联的实际含义

没有 PRODUCT、维护暂停、资料尚未整理、未关联需求、关联无法确定、达成情况未知、维护保存失败或展示投影失败，均不能单独成为 Task 的准备、确认、执行、关闭或停止门槛。

发生局部失败时，保留已经成功的工作，准确说明尚未保存的关联或资料；只补失败部分，不重复创建 Task，不撤销已经生效的 Task 确认。

软关联不降低文档写入的真实性、权限和并发保护要求，也不代表真实业务前提已经满足。实际需要的接口、数据或用户选择缺失，按其真实影响处理；图中的连线本身不产生阻塞效力。

## 3. 信息结构及语义

### 3.1 业务结构和执行结构

```text
项目总目标
    ├─ 直接关联的需求，可按实际业务继续分解
    └─ 必要的子目标或已明确的阶段范围
          └─ 关联需求，可按实际业务继续分解

每项需求
    ├─ 当前约定范围与验收要求
    ├─ 按目标范围保存的成果、剩余缺口与尚未判定部分
    └─ 可选关联多个 Task
          └─ Step、执行记录、验证、审查、关闭说明
```

这是主要阅读层级，不是只能有一个父节点的强制数据树。需求可以支撑多个目标，Task 可以关联多个需求；均保持原来的稳定身份，不为图形显示复制业务对象。

目标说明“想得到什么结果”；需求说明“应具备什么能力、行为或约束”；Task 是有限范围的执行单元；Step 是 Task 内部步骤。模块仅在项目已有或确有组织需要时使用，不要求每个项目额外造一层模块。

### 3.2 分解不等于实施分批

存在独立业务要求时，可以分成不同需求；只是同一个要求需要分批实施时，保持同一需求，用多个工作项或 Task 承接。没有必要把每个 Task 反向变成一个需求。

真实分解、替代或合并需要保留原身份及去向，不把旧身份静默改成另一件事。细化当前要求、补充子需求时，父项默认继续存在；只有实际决定替代、合并或退出时才调整旧项范围，不能凡是补出子需求就将父项退休。当前组成关系与历史演进关系必须区分，不能把 `derived_from` 或 `replaces` 当作当前父子分解关系使用。维护指引、关系校验和展示同时采用这一语义；关系异常或循环应如实提示，不靠布局伪装成有效分解，也不形成 Task 门槛。

### 3.3 项目总目标、子目标与分期

默认围绕一个明确的项目总目标组织阅读，先回答“这个项目要达成什么”。需求可以直接支撑总目标，不要求经过子目标；只有存在真实、有用的业务层次时才保留子目标。模块、专项、Task 和未来方向不自动升格为同级目标。

总目标、阶段范围、基础设施交付和专项支撑不能仅因 `scope: current` 就被平铺成多个同级总目标。项目确有多个结果方向时，说明它们与项目整体定位的关系；不为满足显示结构强行合并不同业务要求，也不由 TraceLens 猜选第一个目标作为总目标。资料尚未明确时保留项目定位及待整理提示，由 vNext 在授权维护中整理。

不自行增加“第一期”“第二期”。项目明确记录了阶段时可以使用，但阶段、目标身份和目标版本是不同概念。已有项目整理时优先保留身份并澄清层次，不为了图形显示重新制造目标。

新增需求后，更新受影响的目标展示、关联和必要正文；没有业务变化的部分不重复改写，不为每条新增需求强制生成新的目标版本。

总体目标或需求的历史演变按需进入二级页面。一级页面展示当前结构，不铺开新增、修改、拆分、撤回的历史事件。

## 4. 项目概览

### 4.1 页面结构

保留简约的应用导航和项目选择。主体只包含紧凑的项目总目标区域，以及唯一的需求全景区域。

- 项目总目标：名称、简短范围、来源和“查看演变”入口；必要时提供已明确的子目标或阶段范围选择。
- 需求全景：同一组需求卡片同时表达已拆分内容、稳定展示顺序以及关联 Task 的概况。

原来的“需求顺序线”和“需求拆分概览”合并，不再把同一批需求重复展示两遍。也不保留常驻的大型“界面原则／状态说明”区域。

### 4.2 需求卡片

每张卡片默认只显示需求 ID、名称、简短范围说明、关联 Task 数量及可确认的生命周期分布。状态以本次 Runtime 查询或明确标注的降级快照为依据；任务查询失败、身份未确认与未关联 Task 分别表达，不以零值替代未知。具体 Task 编号、完整依赖、完整正文与来源详情按需下钻。

卡片不显示永久性的“需求已完成”，不计算需求完成率。卡片主体使用中性样式，颜色用于少量 Task 状态标记；选中状态与业务达成状态不混用。

以下是合成展示例，不是 LawAgent 的真实进度：

| 需求 | 范围摘要 | Task 概况 |
| --- | --- | --- |
| R1 法律内容采集 | 约定法律内容的采集与整理 | 关联 3 个 Task；已关闭 3 |
| R2 底层库设计 | 数据库与向量库结构设计 | 关联 4 个 Task；已关闭 4 |
| R3 自动导入流程 | 内容清洗、切分与自动入库 | 关联 5 个 Task；已关闭 2、进行中 2、已暂停 1 |
| R4 检索优化 | 召回、排序与查询效果优化 | 未关联 Task |

“未关联 Task”不等于没有实现；“关联 Task 均已关闭”不等于需求已满足。

### 4.3 下钻

点击需求卡片，进入需求视图并定位该需求，展示它在当前目标结构中的位置，同时打开其详情。点击详情中的 Task，再进入现有 Task 详情。

返回时保留选中的需求、目标范围及必要的筛选和滚动位置。不另建内容相同的需求详情副本。

## 5. 需求展示顺序

### 5.1 唯一基础规则

需求全景使用项目级的一份有序需求身份列表，不为每个目标维护一套顺序。初始顺序按需求首次纳入分解结果的先后形成；后续新增需求按本批次确定的顺序追加，保留已有需求的相对位置。

```text
初次拆分：       A — B — C
后续新增一批：   D — E — F
最终展示：       A — B — C — D — E — F
```

D 即使被发现是 C 的前置条件，也不自动变成 A—B—D—C—E—F。

`maintain-project` 可以协同用户确定本批次 D、E、F 的内容和排列，但不能借此自动重新优化已有 A、B、C 的位置。用户另有明确重排指令时，由 vNext 修改文档；TraceLens 仍只是读取。显式重排后称为当前登记顺序，不继续宣称它完整代表历史创建先后。

### 5.2 不代表什么

该序列不是执行队列、依赖拓扑排序、时间工期计划或历史事件时间线。需求位于左侧不意味着它已经完成，也不意味着它必须先实施。

任务关闭、暂停、新增修复任务、需求改名、正文更新、依赖变化，不自动改变需求的已有位置。同一需求不因多个实施工作项而在同一需求轴上重复出现。

筛选或切换目标只改变展示范围，保留项目级列表的相对位置，不修改原始顺序。退出当前范围的需求保留身份与历史；即便在当前筛选中隐藏，也不重编号其他需求。分层展开控制可见范围，不借此重排登记列表或为共享需求复制身份。

### 5.3 持久化要求

由 vNext 在规范文档中保存稳定的有序需求身份引用，TraceLens 原样消费。不按文件修改时间、ID 字典序或前端推断重新生成业务顺序。

需求全景不直接由任意 `plan.work_items` 投影排序。已有 plan 仍可表达实施安排，但实施安排的调整不自动改动本节的需求展示序列。

优先在已有项目规范文档中增加最小、可选的顺序表达，只引用需求身份，不复制需求正文或状态，不建立第二套需求库，也不要求为展示顺序先创建完整项目 plan。具体字段及兼容方式在实施中依据现有闭合契约确定。

旧项目缺少可靠顺序时，由用户与 vNext 在维护中明确当前采用的排列；列表尚未覆盖的需求保留“未指定顺序”的可见入口，不消失，也不伪造历史创建先后。该缺口不影响 Task。

## 6. 需求视图：目标、需求与达成情况的关联图

### 6.1 主体不是目录，也不是另一条路线图

主体采用自上而下的关联图：项目总目标位于上层，按实际文档展示直接关联需求、必要子目标和当前需求分解。先展示上层及直接关联需求，再按需展开更细层级；不把所有 current goal 自动平铺为同级根节点。

主图的连线表示当前组成或支撑关系。依赖是另一类关系，仅在选择某需求或明确开启局部查看时展示，并使用可区分的线型及标签；不默认铺满全项目依赖线。

左侧需求目录如有需要，可作为搜索定位的辅助面板，而不再是页面主体。主图不同时铺开全部 Task、Step、设计和证据。

### 6.2 需求节点

节点重点呈现：需求身份、当前所选目标与适用范围下的达成说明、已具备的内容、明确剩余缺口或待核对项。Task 数量是次要信息。必要的范围标签随节点或详情可见，避免相同需求的不同结论被误读为冲突。

合成示例：

```text
R3 自动导入流程                      部分满足

已确认：全量内容入库
尚有缺口：失败后的恢复与重试

关联 5 个 Task                                  查看详情
```

该结论的前提是源文档已经明确记录相应范围与结果。没有这些资料时展示已知正文及“尚未判定”，不由 TraceLens 根据 Task 数量补写结论。

### 6.3 范围化达成语义

达成结论归属于“需求身份＋明确适用范围＋被评估对象”，记录关联目标、依据和必要时间。被评估对象可以是说明了适用边界的工作副本、提交或发布版本；无法固定精确版本时说明限制，不为登记结论强制创建提交。

支持同一需求在不同目标下有不同结论，页面按明确适用范围选择，不能给需求挂一个全局满足状态。例如，全量导入可以满足固定知识集演示目标，而持续更新目标仍有增量更新和恢复能力缺口；两者共用需求身份，各自保留要求与证据范围。多个结论适用范围不明或相互矛盾时保留待核对，不按时间自动挑选“最新正确结论”。首版不建设复杂范围计算或自动证据合并系统。

“已满足”仅针对当前查看的已约定要求，不表示该长期需求以后不能改进。

| 表达 | 语义 |
| --- | --- |
| 已满足 | 有适用于当前约定范围的明确满足结论 |
| 部分满足 | 有已满足的明确范围，同时有尚未满足的明确范围 |
| 未满足 | 有明确依据表明当前要求尚未达到 |
| 尚未判定 | 缺少足够或适用的结论，或相关材料尚待核对 |

这些是可选的、来源可追溯的展示结论，不是新增需求审批状态机，也不是 Task 的前置状态。

已确认一部分满足、其余部分尚未核对时，整体可显示“尚未判定”，同时明确展示已确认成果；不能把缺少证据直接解释成未满足，也不能因为整体未知就隐藏局部成果。四值标签是阅读摘要，不替代覆盖范围、缺口和待核对项。

不得把 `current`、`planned`、`retired` 等范围属性，当成上述达成结论；也不能把 `delivered-reported` 与 `pass-reported` 两个字段简单合并成“当前要求已满足”。

“已满足当前全量入库要求，同时有增量更新改进 Task 进行中”是合法状态。新增后续改进不自动否定此前交付；当前要求确实发生变化时，再由 vNext 按受影响范围更新结论。

### 6.4 总体目标的判断

总体目标是否达成，不能由所有子需求、Task 或测试数量相加得出。目标层结果使用其自身的明确结论、适用对象和来源，由同一套 Skill 引导的评估方法整理；不把现有 requirement-only assessment 自动解释成总体目标认证器。

没有总体使用结果的核对材料时，可以显示“整体结果尚未判定”，同时保留各部分已经确认的成果。不得因为整体尚未判定而把所有局部结果清零，也不得因此阻止独立 Task。

需求分解是否充分、目标是否还有漏拆要求，也不是图形算法能够自动证明的。只展示已记录的分解及已知缺口；存在尚未分析范围时按文档说明，不声称已经找全遗漏。

只按已经约定的目标要求判断。定性目标可使用演示、实际使用结果和用户反馈；明确约定了定量要求才按相应指标核对。模型不得临时新增 KPI，再以缺少该 KPI 为由拒绝承认已有成果。

### 6.5 查看缺口与局部展开

可以提供“全部”“未满足与部分满足”“尚未判定”等少量筛选。筛选保留总体目标及必要父节点，让用户理解缺口的位置。

后续、候选或已经明确退出当前目标范围的要求，不混入当前目标的必需缺口。某个需求仅有一般支持关系，不代表它单独或共同构成全部必要条件；图必须保留文档实际声明的范围。

文档有明确子需求、验收项或功能点时，可进一步展开；没有时不强制新建“能力对象”或机器验收项，也不把自由正文自动转成正式子需求。

### 6.6 需求详情内容

点击需求后展示完整说明与边界、所属目标、所选结论的适用范围与被评估对象、显式前置关系、阶段性交付与依据、剩余和待核对内容、关联 Task，以及来源／演变入口。不同目标下的结论可切换查看，不复制需求正文。

关联 Task 使用适合多任务查阅的紧凑列表，可按其真实状态筛选。具体 Step 在进入 Task 详情后展示，避免需求图同时承载全部执行信息。

## 7. 目标与需求分析、维护流程

### 7.1 两部分能力分别验收

文档规范化负责可保存、可读取、可定位和可追溯；Skill 引导的大模型分析负责理解业务、适当分解、建立关系和总结真实成果。

Schema 通过不等于分解正确或没有遗漏；资料已经登记也不等于已经读懂或完成业务盘点。

### 7.1.1 后续契约与 AI 指导审查原则（2026-10-11 补充）

vNext 依靠 Skill 引导宿主 AI 理解、维护与评估业务；Runtime 和 TraceLens 负责确定性保存、查询、解析与展示。审查必须先说明规则由谁执行、影响什么，再判断是否需要修订。

| 审查类型 | 判断与处理标准 | 验证方式 |
| --- | --- | --- |
| 格式与机器消费契约 | 身份、字段类型、定位、选择、版本、隔离与降级应让生产和消费得到一致结果。可复现的误读、错误套用、漏报相关缺口或相互矛盾，按实际影响修复。 | 有限共用样例、结构或确定性行为核对；样例演算与实际实现测试分开报告。 |
| AI 行为指导 | 关注是否说明用户意图、授权范围、适用证据、已知／未知和局部维护边界。只有明确误导核心行为或真实交互暴露的问题才作为缺陷；一般业务判断不展开成穷尽分支或机械清单。 | 在相应实施阶段用有限、代表性的 Agent 交互观察；文字精确、Schema 或程序测试通过均不保证 AI 必然遵循，也不证明业务判断正确。 |
| 产品取舍与假设边界 | 已明确且不违背产品目标的保守提示、简化策略和低概率边界，记录代价或待观察事项；不能仅因存在更精细方案而升级为必修缺陷。 | 说明触发条件、用户影响及收益与成本；出现实际问题或与定稿要求冲突时再调整。 |

审查意见应附执行主体、可定位依据、触发条件和实际影响，区分已复现问题、规则歧义与假设风险；严重度依据实际影响，不能以“AI 可能出错”直接推成必然失败或高优先级。优先用一条必要规则或一个共用样例消除误读，不默认新增字段、状态机、审批、测试矩阵或全项目流程。不能为了追求表述精确而扩展本轮范围或给普通 Task 加门槛。

目标整体摘要的首版保守核对属于已选取舍：同目标新增其他范围声明可能使旧报告显示待核对，原成果仍保留。这是机器无法判断语义影响时的提示，不能要求 AI 重新评估全部范围，也不等于业务成果失效；是否需要更细粒度摘要留待实际使用观察。

### 7.2 maintain-project 的主要行为

按用户请求范围读取现有目标、完整需求、设计、决定及必要实施材料，识别当前已知范围和未知。独立要求可以提出拆分，实施批次不必拆成新需求。

采用的结果在已有授权内保存为当前目标、需求及明确关系；需要新增展示节点时按批次追加到需求序列。备选、问题和未采纳建议不自动变为当前要求。

有实际交付或新反馈时，局部维护相应成果、缺口与待核对材料，引用已有证据，不复制整份历史，不仅保留“还没做完的清单”而删除已交付需求正文。

用户要求先实施或暂缓维护时，继续已授权实施并保留待维护范围。每次 Task 或 Step 操作不要求全项目重盘点。

### 7.3 验证与证据

维护范围化结论可复用适用的已有测试、静态分析、检查、演示、人工确认、外部实际结果等最小充分证据。

不为更新进度摘要强制创建验收 Task、强制新写测试或重跑整个产品验证。新材料只影响其实际覆盖的范围，旧材料保留其真实历史意义；未受影响范围不被自动全图失效。

评估由现有 vNext Skill 引导当前宿主大模型完成：读取本次目标下的实际要求，核对被评估实现及已有材料，说明已确认成果、明确缺口和未知。代码存在、测试通过、用户反馈与实际运行结果分别标明，不以缺少材料断言未实现，也不因存在代码直接认定业务满足。Runtime 只负责确定性处理与保存，TraceLens 只消费结论；两者都不启动模型代做评估。

### 7.4 Skill 组织与评估时机

不新增评估 Skill，不给 `maintain-project` 继续堆叠无关能力。复用并收敛现有 `references/reconcile.md` 作为统一评估方法，主 Skill 只保留适用场景、路由和必要边界。将长说明移入 references 不代表每次都必须读取全部分支。

| 时机 | 行为 |
| --- | --- |
| 用户通过 maintain-project 盘点项目或查看成果 | 评估本次请求覆盖的范围 |
| Agent 执行 close-task | 默认触发本次 Task 相关的局部评估，按 7.5 处理 |
| 新交付、验证或反馈材料出现 | 在已有维护授权内更新实际受影响的结论，不要求每个 Step 都评估 |
| 用户改变需求或目标范围 | 先落实新要求，再判断原结论哪些仍适用；可按用户要求暂缓评估 |
| 打开或刷新 TraceLens | 读取已保存结论，不重新调用模型评估 |

### 7.5 close-task 默认触发局部评估

现有 close-task 已有维护相关产品摘要的入口，沿用该入口和 reconcile 方法，不把完整评估流程复制进主 Skill。维护开启且授权覆盖时，关闭后的局部维护在本次调用中完成，用户通常不必再手动调用另一个 Skill。

1. 汇总本次 Task 的实际成果、验证结果和保留事项。
2. 保存关闭决定并回读确认 Task 已关闭；成果评估不是关闭的前置条件。
3. 根据已有需求关联和明确受影响范围，调用同一 reconcile 方法更新适用结论。
4. 一次报告关闭结果与评估保存结果，分别说明未保存或待核对部分。

不因关闭一个 Task 扫描全项目，不为评估补造需求或关联。没有业务成果变化时可以说明无需更新；停止未完成任务也保留已产生的成果和剩余范围。PRODUCT 缺失、暂停、用户要求暂缓维护或保存失败，均不撤销关闭、不重开任务，也不要求再跑验证来取得关闭资格。

这是 Agent 执行 close-task Skill 时的编排行为。直接调用 Runtime `task close` 只记录生命周期处置，不自动启动模型、不隐含完成产品评估。关闭后的新反馈仍可通过同一 reconcile 方法补充，不重演关闭动作。

### 7.6 需求定义与结论的持续维护

需求正文主要维护要求、边界和验收约定；阶段成果、缺口和依据放在独立评估报告中，页面组合展示，避免每次登记进展都改写需求定义。目标结果同样保持要求与结果的语义区分，复用其正文、来源和最小必要结构，不引入独立 KPI 系统。

体系引入前的资料由大模型在授权范围内整理成当前结论，保留实际依据与未知；不建设全面历史迁移、旧摘要修复或逐条旧版本认证工程，也不要求历史整理完成后才能使用。

体系使用后，用户明确改变要求时先保存新要求，保留原结论的历史适用范围，再局部更新当前说明。暂时不能判断的部分留待核对；“先改要求、以后再评估”应直接落实。并存的新旧结论按范围和被评估对象解释，不机械覆盖或按时间淘汰。

定义摘要或哈希变化只提供核对线索，不等于成果失效，也不授权 Runtime 拒绝需求变更、任务继续或关闭。改名、补充说明和登记进展不触发全项目重新评估。结论适用性由模型依据内容判断，不能变成版本审批关卡。

并发写入保护与上述业务判断分开：读取版本过期时重新读取并应用用户明确指令，避免覆盖他人修改；只有无法自动协调的实际冲突才需要用户选择。真实文件保存失败如实报告，但不伪装成业务拒绝或阻塞独立工作。

## 8. prepare-task 与可选需求关联

### 8.1 正常行为

用户已指定需求时，使用该归属并核对相关正文，也可顺带提出少量明显相关的其他关联建议；用户没有指定时，结合实际 Task 范围推荐关联。建议不覆盖用户已有选择，不要求全项目搜寻匹配。Task 可以保持无关联，不为填字段临时创建需求。

维护开启且已有有效授权时执行主动维护；维护暂停并不禁止按本次请求正常读取相关需求文档。PRODUCT 缺失、暂停或材料不可读，不要求先初始化、补完或修复项目管理后才能准备 Task。

主 Skill 保持简短，较细的维护说明放到现有参考文档，不新增独立关联审查阶段。正常语义判断不展开成额外校验清单。

### 8.2 prepare 与 confirm

默认在 prepare 结果中呈现任务范围、已有明确归属和可选关联建议；在 confirm 按实际采纳范围确认 Task，并在有效维护授权内补充关联。

```text
prepare：准备 Task，附带相关需求或“暂不关联”
    ↓
confirm：确认实际任务计划
    ↓
保存已经明确采用的关联，或者保持为空
```

用户已经明确给出的归属或已包含在采用内容中的关联，不重复逐条询问。确认 Task 不自动采纳未被明确包含的额外建议；确有必要保留推断时，用现有推断来源语义表示，不冒充用户决定。

只读请求不写入；任务确认和产品文档保存不做成必须一起成功的跨系统事务。

### 8.3 保存失败与后续补充

Task 确认成功但关联失败，Task 确认仍然成立。保存其真实身份，仅重试关联或按用户安排延后，不再次 prepare，不回滚 adopt，不自动 focus、resume、close 或改 Task 范围。

以后可以补充、修正或否定关联，保留准确来源。修改纯管理关联不要求重开历史 Task；业务 Task 范围确实变化时才按原任务机制处理。

已有版本在 prepare 后保存的草案关联可保留，不要求集中迁移或清空；存在关联不证明 Task 已确认或已经执行。

### 8.4 关联数据与展示

优先复用 TaskBinding 的真实 TaskRef、角色、覆盖范围、来源、显式／推断属性及可选计划引用。无项目 plan 时不为关联补造 plan。

以真实 Task 身份连接，不只凭显示编号或标题。历史身份不明时保留来源及未知，不新建假 Task。

分别表达“在该工作副本的任务数据中定位到真实 Task”“关联来源能否读取和核对”“是否存在明确身份冲突”。真实 Task 可定位但历史来源不可读时，可以查看任务详情并标明关联依据尚未核对，不能宣称来源已验证；来源中明确存在不同身份或冲突时不能静默忽略。纯来源缺失不等同于身份冲突。

不为每条路径维护重复正反向关系。Task 经需求间接支撑目标时可以沿显式关系导航；这不等于新增一条直接确认的 Task→目标业务绑定。

## 9. Runtime 只读接入、快照降级与多项目隔离

### 9.1 当前选定路径

目标、需求和评估结论继续来自规范 Markdown/YAML；Task／Step 以 vNext Runtime 只读查询为主要来源。TraceLens 复用现有任务状态计算和记录读取能力，不自己实现第二套 journal reducer。Runtime 查询只返回截至本次读取可确认的事实，不调用模型做业务评估。

这里的 Runtime API 是本地命令和程序查询接口，不是已有的项目 HTTP 常驻服务。TraceLens 的本地服务调用固定、可信且兼容的查询入口，每次显式传入项目根目录；不执行任意项目脚本，不要求启动被观察项目的业务应用。

复用 `assistance.mjs task-status` 的 summary、task、step 等查询形式，以及已有只读来源读取能力；需要时由 Runtime 理解逻辑记录和归档。TraceLens 不暴露 `close`、`adopt`、`focus`、`rebuild` 或记录写入等操作，不把查询失败转为自动升级、修复或任务动作。[S11]

### 9.2 本机项目与克隆场景

主要场景是查看本机正在开发或已保存的项目。Agent 会话无需保持运行；TraceLens 可以在刷新时发起只读查询，之后从自己的内存结果展示。这里不建设独立的“断网离线模式”。

克隆到另一台机器后，需要兼容的运行环境、Runtime 程序，以及已经提交推送或另行迁移的任务事实和必要归档。`task-view.json` 是默认不纳入 checkpoint 的本地派生缓存，不能假定随克隆存在。事实完整而缓存缺失时，Runtime 可以只读计算状态，不必先发布新文件；事实本身未迁移时，安装 Runtime 也不能还原缺失资料。

不要求为本方案迁移所有历史，也不默认建设专用导出包。对实际可用范围如实展示，未知不补造。

### 9.3 查询、内存缓存与刷新

项目显式刷新时发起只读查询，TraceLens 按项目缓存结果。已有 summary 分页应按接口要求消费，未读页不能作为零任务或完整覆盖；不必对每次页面切换重复重算。Task／Step 详情按需查询并缓存，避免把全量历史反复送到每个页面。

一次展示中的任务数据采用明确来源及其版本：Runtime 查询结果，或已知降级快照。不要静默拼接新列表、旧生命周期和另一版本的步骤详情。列表与详情的视图版本不一致时重新加载相关数据；读取过程中的变化保留诊断，不能宣称多次读取是一个跨文件原子事务，也不因此锁住项目或暂停 Agent。

查询时间、文件实际生成／更新时间和业务发生时间分别表达。无法取得文件发布时间时说明未提供，不用读取时间冒充执行或发布时间。内存缓存是本次查询结果，不是绝对实时状态。

当前 Runtime 查询会读取完整日志并重算，再裁剪输出；summary 减少输出量，不等于已经减少后台计算。采用 Runtime 的主要理由是统一状态语义、支持缺缓存查询和复用来源读取，不能承诺比读取现成文件快。首版采用按需刷新、内存缓存和小规模并发队列，不以本方案为由先建设增量日志索引或高频轮询系统。

### 9.4 局部失败与快照降级

缺什么就降级什么，不因单个详情或来源不可读而让整个项目页面失效。

| 情况 | 处理 |
| --- | --- |
| Task 列表可读，某个 Task／Step 详情失败 | 保留列表，该详情显示暂不可用，不拿其他版本详情冒充本次结果 |
| Task 状态可读，来源或归档材料不可读 | 保留状态，说明证据读取缺口；身份与来源核对依 8.4 分开 |
| 可选字段未提供 | 隐藏相应内容或显示未提供，保留其余有效信息 |
| Runtime 缺失、超时、失败或返回格式不支持 | 可使用可识别的现有任务视图或同项目最近成功结果，明确降级来源与时间 |
| 没有任何可用任务数据 | 显示任务数据暂不可用，保留独立可读的目标、需求及来源 |

快照降级优先复用 `.workflow-system/records/task-view.json` 或 TraceLens 已有内存结果，不默认新建第二套全量文件。文件表示最近一次成功发布的状态，不保证覆盖最新事件；`CURRENT_TASK.md` 是较简化的来源，不能单独证明全量 Task／Step 已读。[S4][S5]

降级文件仍需识别格式并满足读取预算；文件很大、损坏或超出预算时如实报告，不截断后声称完整，不回退成零任务、全部完成或“本次查询成功”。无需在首版建立独立离线导出和完整历史浏览系统。

### 9.5 多项目隔离

采用一个 TraceLens 服务，按项目异步启动短生命周期的 Runtime 只读查询进程。查询结束后进程退出；不为每个项目另起 HTTP 服务或分配端口，不在 TraceLens 主服务线程直接执行同步全量重算。

```text
TraceLens 本地服务
    ├─ 查询进程 A → 项目 A 根目录 → A 的事实记录 → A 的缓存
    └─ 查询进程 B → 项目 B 根目录 → B 的事实记录 → B 的缓存
```

| 隔离维度 | 规则 |
| --- | --- |
| 项目身份 | 使用 TraceLens 登记身份与明确工作副本根目录；不使用一个全局可变“当前项目”决定查询归属 |
| 任务身份 | 使用项目／工作副本身份与真实 task_id；TASK-001、标题或 PRODUCT 中同名 project_id 不能作为跨项目唯一键 |
| 多工作副本 | 即使来自同一仓库、包含相同 task_id，也分别展示，不自动合并未提交资料 |
| 查询参数 | 每次明确 root 和必要的 workflow_home、详情选择及分页上下文；后续请求保持同一项目上下文 |
| 并发与失败 | 同项目重复刷新合并；不同项目受小规模总并发限制，一个超时或失败只影响该项目 |
| 缓存与返回 | 结果绑定项目、配置版本、请求批次和视图版本；切换项目、删除登记或配置变化后，迟到结果不得覆盖其他项目或更新结果 |
| Runtime 差异 | 各项目分别检查当前查询契约；不兼容项目独立降级，不要求所有项目同时升级后才可使用 |

查询与 Agent 的正常写入可以并行。结果版本变化只需要重新读取相关数据，不是业务冲突，不创建开发锁，不争夺 Task 焦点。调用的入口须固定、可信且满足当前契约；不因为目录中存在脚本就自动执行。

### 9.6 开发期接口兼容：一套当前契约

开发期维护一套当前查询契约，允许小幅增量变化，不建设历史版本适配层、版本矩阵或专用握手服务。首版以双方核对的现有 `task-query/v1` 等读取返回格式为基础，列明各查询用途的必需字段和可选字段，不按软件版本号编写多套分支。

| 返回变化 | 消费规则 |
| --- | --- |
| 新增字段 | 忽略不认识的字段，不拒绝原有有效数据 |
| 可选字段缺失 | 隐藏对应信息或显示未提供 |
| 必需字段缺失或类型错误 | 相关查询结果不可用，按 9.4 降级，不猜字段意义 |
| 不认识的格式标识 | 明确提示不支持，按 9.4 降级 |

软件版本用于诊断，返回格式和本次用途必需的结构用于判断可用性。不存在“接口能执行就表示任务数据完整”的推断，仍需保留分页、覆盖范围、未知和冲突信息。

开发期破坏性变更通过 vNext 与 TraceLens 配套更新解决，同步生产端、消费端和少量契约测试；真正改变返回格式含义时调整格式标识。不兼容项目提示更新配套版本，同时保留其他可读资料；TraceLens 不自动升级 Runtime，不为未发布的历史实现长期保留适配代码。

### 9.7 发布与存储边界

保持“事实已保存”和“投影已发布”分开报告。文件投影失败不撤销 Task 事实，也不妨碍继续、关闭或停止；Runtime 只读查询可以根据已保存事实计算结果，但不能把查询成功描述为派生文件已修复。需要补投影时仍由 vNext 按原有维护路径处理，TraceLens 不自动执行 rebuild。

不为每次刷新新增持久化快照，不复制完整日志和证据到另一套记录。详情引用原有材料，不以本方案为由改造全量记录存储。Runtime 无法读取缺失或损坏的事实时保留真实限制，不能靠降级快照宣称原始记录完整。

## 10. Task 生命周期与界面表达

### 10.1 直接采用实际状态

固定基线中，`pause` 对应 `paused`，`resume` 对应 `active`，`close` 对应 `closed`；暂停与关闭是不同状态。[S4]

建议 UI 基础标签如下：

| 状态 | 展示 |
| --- | --- |
| draft | 草案／待确认 |
| active | 进行中 |
| paused | 已暂停 |
| closed | 已关闭 |
| ambiguous 或不可可靠识别 | 状态待核对／未知 |

具体词语可以随现有界面统一，但不得把暂停计入关闭，不得仅凭 Step 未开始就擅自改变 Task 生命周期，也不把 draft 强行解释为已确认的待执行任务。

### 10.2 关闭的含义

用户决定关闭，就直接展示“已关闭”，不再次审查剩余工作来决定能否算关闭。

关闭意味着该 Task 已按用户决定结束；不意味着所有 Step 被改成 finished，也不意味着所有结果改为 PASS。原有关闭说明、遗留事项和证据在 Task 详情中保留。[S4][S5]

不新增“完成型关闭／放弃型关闭”等生命周期类型，不把已经关闭的 Task 因为遗留事项重新算作进行中，也不自动创建补做任务。

Runtime 的关闭事实本身不推导需求满足或改变需求范围。Agent 的 close-task 按 7.5 默认触发局部评估，由已有成果和要求得出结论；不能把这一维护行为误写为“closed 即满足”。用户明确取消的要求由 vNext 更新范围，不继续计入当前目标的必需缺口；仍然保留的要求按其自身资料判断，不自动重开原 Task。

## 11. 来源、演变与异常展示

来源与历史通过小型入口按需查看。目标演变、需求演变与需求拆分顺序分别表达，不用日期事件把一级页面铺满。

保留实际决定、变化前后范围和必要来源；缺少旧内容或确切时间时说明未知，不补造历史。修改当前关系不意味着采纳某段历史讨论全部观点。

读取部分文件、Runtime 查询、详情或来源失败时，保留独立可用条目和原文入口；格式校验、字节覆盖、任务状态计算、业务盘点和交付结论分别说明，不把其中一项成功冒称其他项成功。只读查询返回的事实与关联证据是否已核对分开展示。

多数时候保持界面安静。异常提示只在有实际缺口时出现，详细诊断按需展开，不把“界面原则”大段常驻在首页。

### 12.2 必要增量

**增量一：目标层次与项目级需求序列。** 在现有规范文档中明确总目标入口、必要子目标或阶段范围，以及项目级的有序需求引用。序列只负责展示，默认按批追加；不计算依赖，不要求项目 plan，不成为 Task 条件。

**增量二：当前组成和支撑关系。** 现有正式关系方向不能完整表达需求间当前分解及所需目标层次；按真实语义补最小表达、校验和消费者处理。同步修改维护指引，明确细化时父项继续存在，替代／合并才按决定调整旧项范围；不滥用历史 derived_from，不要求所有需求都有父节点。[S3]

**增量三：按目标范围消费评估结论。** 复用已有报告与来源机制，补足“需求身份＋适用范围＋被评估对象”的最小表达与选择方式，使同一需求可按不同目标展示不同结论。现有单一 assessment_id 不足以直接承担全部语义，需要同步调整生产与消费；不进行复杂范围计算，不把结论反复写回需求定义。总体目标使用独立的明确结果依据，不自动从子项认证。[S1][S2][S7]

**增量四：prepare／confirm 的轻量关联约定。** 在主 Skill 保留简短行为说明，细节写入现有 references；准备阶段推荐、确认时按实际决定保存、可为空、失败不阻塞。不新增关联准入操作。[S6]

**增量五：关闭后的局部评估与非阻塞维护。** 复用 close-task 的现有入口和 reconcile 方法，收敛主 Skill；关闭事实先保存，授权内完成局部评估，两种保存结果分开报告。需求变更先落实、结论按影响维护，定义摘要不成为 Runtime 的业务门槛；不建设全面历史迁移或新评估 Skill。[S7][S8][S10]

**增量六：Runtime 查询接入、多项目隔离及轻量契约。** TraceLens 异步启动独立查询进程，显式传入项目上下文；使用现有只读任务与来源接口，补充接口消费、详情、缓存、超时、版本一致性和局部降级处理。开发期只维护一套当前查询契约，破坏性变更配套更新；不新建常驻项目服务、第二套 reducer 或历史版本适配层。[S11][T1][T2]

**增量七：TraceLens 页面实现。** 合并概览重复区域，突出项目总目标和项目级需求序列；将需求视图主体改为目标、当前分解与范围化达成图；复用并适配需求详情、结构化 Task／Step、历史与来源导航。保留返回时的选择、筛选和滚动位置，不把已有局部关系图当作完整实现。[T3][T4]

新增表达对 Task 路径始终可选，但对某项可视化信息的准确展示可以是必要输入。其缺失应产生展示降级，而不是执行门槛。

### 12.3 实施安排

实施时先固定最小文档表达和当前只读查询契约，以已有源码核对结果选取复用位置；随后完成 vNext 的必要生产侧增量与 TraceLens 的读取、隔离和展示改动；最后用同一组合成材料验证跨层行为。此次定稿不执行这些步骤。

优先原有文件、模板、Schema、解析器和参考指引。现有产品文档核心 Schema 是闭合的，新增可选字段也不天然被旧读取器接受；实施时选择最小表达并同步生产与消费资产，必要时调整文档格式标识，不把未确定字段填入现有元数据后宣称受支持。此处不建设旧产品格式自动迁移工程；Runtime 查询输出的增量字段规则与文档核心 Schema 校验应分开处理。

本方案不预创建所有后续 Task，不指定虚构 Task ID，不要求先完成全项目资料整理。真实项目资料可以在已授权范围内分批维护。

## 13. 验收场景

以下是行为验收清单，不意味着每行都必须新增一个自动化测试。优先复用现有测试和夹具，结合真实页面与交互核对；不为标题、文案和静态排版制造大量持久测试。

| 场景 | 应有结果 |
| --- | --- |
| 无 PRODUCT 或维护暂停，直接 prepare/confirm Task | 正常处理 Task，不要求先建立需求管理 |
| 用户指定 R3，或明确暂不关联 | 使用既有决定；空关联合法，不额外逐项审批 |
| Task confirm 成功，关联写入冲突 | 保留实际 Task 及确认，仅补关联，不重复 prepare |
| 已有 A-B-C，后续拆分 D-E-F | 项目级序列展示 A-B-C-D-E-F |
| 发现 D 是 C 的前置依赖 | 关系按文档可见，但顺序仍不自动改变 |
| 同一需求有多个工作项或新增修复 Task | 需求轴不重复、不自动移动，Task 关联更新 |
| 切换目标或筛选、存在未登记顺序的需求 | 保留项目级相对顺序，未指定顺序的需求仍有可见入口 |
| 同时存在总目标、阶段范围和专项支撑 | 突出项目总目标，按明确层次展示，不把所有 current goal 平铺为同级根节点 |
| 为父需求补充子需求 | 父项默认继续存在，不自动退休，也不继承无关历史通过结论 |
| 概览展示一批需求 | 不再有第二个重复的“需求拆分概览”区域 |
| 进入需求视图 | 主体是当前目标／需求分解关联图，不是目录或实施流程 |
| 多个 Task 已关闭，需求没有适用达成结论 | Task 显示已关闭；需求不自动变为已满足 |
| 需求已满足当前范围，同时有后续改进 Task | 两者可同时展示，不自动撤销已确认成果 |
| 同一需求支撑两个要求范围不同的目标 | 依据明确范围和被评估对象展示不同结论，共用需求身份 |
| 一部分成果已确认，其余范围尚未核对 | 保留已确认成果，整体可显示尚未判定，不把未知当成未满足 |
| 用户改变要求，但原结论尚未核对 | 先保存明确的新要求，局部结论可待核对，不因哈希或旧报告阻塞 Task |
| 文档存在真实并发修改 | 重新读取并应用明确指令，不覆盖他人修改；仅实际无法协调的选择需要澄清 |
| 维护开启且授权覆盖，Agent 执行 close-task | 保存关闭后完成相关局部评估，无需用户再手动调用评估 Skill |
| 关闭成功但评估保存失败、维护暂停或用户暂缓 | 保留关闭，分别报告待维护范围，不重开任务或要求先补测试 |
| 直接调用 Runtime task close | 只记录任务处置，不自动启动模型或声称已完成产品评估 |
| pause 与 close 分别发生 | 分别显示已暂停与已关闭，关闭不强制补完 Step |
| 所有直接子需求有局部成果，但总体结果无核对 | 保留局部成果；总体尚未判定，不自动算百分比 |
| 定性目标已有适用材料，但没有额外 KPI | 按已约定要求评估，不临时新增指标作为认定成果的门槛 |
| 有未关联 Task 的需求或无需求归属的 Task | 都保留可见，不编造关系或交付判断 |
| Task 真实身份可定位，关联历史来源不可读 | 允许查看任务详情，单独标明来源未核对；明确身份冲突不能忽略 |
| 文件投影缺失／损坏／未及时更新，Runtime 可用 | 查询已保存事实，不依赖先修复文件，也不把查询成功说成投影已发布 |
| Runtime 查询失败但存在可识别快照 | 明确使用降级来源及时间，不伪装成本次实时查询成功 |
| Task 列表可读，单个详情或来源失败 | 保留独立可用内容，仅相应详情或来源降级 |
| Runtime 与快照都不可用或超出预算 | 显示任务数据暂不可用，保留产品文档，不显示零任务或全部完成 |
| 克隆后任务事实完整、没有 task-view.json | 兼容 Runtime 可只读计算，不要求先生成展示文件 |
| 克隆时未迁移必要事实 | 明确资料缺失，不能声称安装 Runtime 即可恢复全部任务 |
| 两项目同名任务、同仓库两个工作副本 | 按项目／工作副本与真实 task_id 隔离，不串用任务或来源 |
| 同项目重复刷新、多项目并发、某项目超时 | 合并同项目在途刷新、限制总并发，失败只影响相应项目 |
| 配置变化、删除登记或切换项目后旧查询返回 | 不覆盖其他项目、更新配置或更新批次的结果 |
| 列表与详情查询之间发生正常任务写入 | 按视图版本重新加载相关数据，不静默混合状态，不暂停 Agent |
| 查询增加字段或缺少可选字段 | 忽略新增字段，按需隐藏未提供信息，其他数据正常展示 |
| 必需字段错误或返回格式不支持 | 相关查询降级并提示配套更新，不启动历史适配或自动升级 |
| 用户打开目标或需求的历史 | 二级展示真实演变；一级顺序与图结构不混入事件时间线 |
| 一个需求支撑多个目标或发生真实分解 | 保持稳定身份、实际覆盖及演进来源，不复制需求或继承无关旧通过结论 |

接口验证以同一组合成任务资料覆盖正常读取、增量字段、可选字段缺失、不可识别结果、失败降级和多项目隔离即可；不建设历史版本矩阵测试平台。页面与 Skill 行为仍需分别验证，接口测试通过不能证明模型会正确评估业务或页面已符合设计。

## 14. 不纳入本轮的内容

不纳入自动工期估算、资源优化、全项目自动排程、按依赖自动重排需求、需求完成率、需求审批或新增关闭状态机、必须绑定需求的 Task、TraceLens 写回编辑或调用 Runtime 写操作、TraceLens 自建 journal reducer、为展示新增大量证据副本。

不新增评估 Skill、Runtime 内的模型评估服务、每项目 HTTP 常驻服务、中央任务服务、复杂范围计算系统、历史 Runtime 版本矩阵或适配层。不默认建设离线导出产品、高频全项目轮询、增量日志索引和全面历史结论迁移。现有 Runtime 查询内部读取完整日志是复用行为，不属于另建 reducer。

不强制项目分期，不要求每项要求测试化，不因本方案建立强制 E2E 验收 Task，也不要求已有项目先补齐全部历史才能继续开发。

现有工程能力和真实约束保留，但不得借可视化扩充它们对 Task 的控制范围。

## 1. 结论与目标

在已有测试准入政策和 assistance-first 工作流上，补充“实现是否必要、复杂度是否相称”的共用工程原则，并将同一判断方法贯穿规划、实施、调试、代码审查和验证。

不另建反过度工程子系统，不新增 Skill、Runtime 准入、审批表或风险评分。不按 Astra、Sol、Luna 分别维护政策。

目标不是最少代码、最少测试或最少运行时间，而是：在满足当前已确认的行为、支持边界、安全及数据完整性要求的前提下，减少没有足够现实价值的防御、兼容、恢复、抽象、测试和流程负担。

成本考虑覆盖设计、实现、模型上下文与生成消耗、审查、运行、故障诊断、后续修改和长期维护。不能以当前一次执行快几秒替代长期可维护性判断，也不要求计算虚构的风险概率或成本分数。

## 2. 基线事实与问题定位

### 2.1 已有能力，应保留而非重建

1. `templates/vnext/bootstrap/test-admission-policy.md` 已经要求保护对象、具体检出能力和增量价值；明确不按函数或分支机械加测试，不以覆盖率为独立目标，不为每个测试填写理由，不新增 Runtime 状态或准入表。它同时保留聚焦单元测试，区分本次取证与长期回归，并要求同时审查过量测试和验证不足。[S2]
2. `WORKFLOW_PROTOCOL.md` 已采用 assistance-first：管理服务失败不是开发否决；事实、资格、用户决定分开；一次确认处理实质工作流偏离；不得伪造 PASS 或独立审查。证据章节已经要求最小充分验证，不因管理元数据扩大测试。[S1]
3. `execute-step`、`debug-task`、`validate-change` 已限制为了记录而加永久测试、扩大验证或重复执行。代码审查也明确 review-only 不授权修复。[S5–S8]
4. `host-guidance.ts` 已要求显式 Skill 调用时重新读取项目本地 Skill 和共享协议，不需要再把整套政策复制进 AGENTS.md。[S9]
5. 发布构建已将协议、测试政策和 Skill 模板映射到目标项目；安装测试已有政策/协议一致性和部分 Skill 引用检查。[S10–S12]

### 2.2 本轮补足的缺口

- 范围控制解决“是否获准做”，但尚未同等具体地解决“同一授权范围内是否值得增加这些行为和复杂度”。
- 测试政策的明确适用范围集中在 prepare-task 和 review-draft；实施中补测试、修复回归、审查提出新增测试等决策点需要显式承接。
- 代码审查对正确性、安全、数据、兼容和证据问题已有明确提醒，但“实现过度”缺少与“实现不足”相称的具体检查要求。
- 上一轮建议中的“默认明确失败”“不支持未声明环境”等表达需要限定，防止被理解为一律禁止必要恢复，或把资料缺失当作缩小支持范围的授权。

以上是对已读取指引结构的判断，不是对模型行为的量化评测，也不构成对整个仓库过度防御程度的全面结论。

修改现有共享协议、测试政策及六个直接参与工程决策的 Skill：prepare-task、review-draft、execute-step、debug-task、review-change、validate-change。必要时小幅扩展现有分发测试，沿现有构建、安装和升级路径验证交付。

### 3.2 明确不做

不改目标/需求/assessment/绑定/Roadmap 等需求管理机制，不改 PRODUCT 资料和 maintain-project 需求管理指引。

不增加模型专属政策，不建立模型全量评测平台，不把本方案全文设置为每次 Skill 调用的必读材料。

本地候选构建验证或发布所必需的现有版本元数据、清单、摘要及生成产物更新，可随对应的已授权实施验证或发布工作处理；本地候选构建不等于对外发布授权，也不允许改变 Runtime 行为或扩展业务范围。

## 4. 统一工程决策原则

### 4.1 共用原则拟稿

建议将以下语义放入 WORKFLOW_PROTOCOL 的一个短节，实施时沿用源文件语言和风格，不复制本方案全文：

> 在当前已确认的支持边界和契约内，选择足以满足需求且总体成本相称的实现。额外防御、兼容、恢复、抽象和长期测试应有具体保护价值，而不是仅因可以想象某种异常。
>
> 在作出、调整或获授权审查实现/验证决策时，先判断行为是否需要实现，再选择本次必要证据，并分别判断是否需要新增或保留长期自动化回归保护、哪些检查需要在当前版本执行。优先复用有价值的现有实现、测试和证据，但复用必须与实际对象及范围相符。
>
> 仅记录、查询、按已有决定处置、汇总、提交或执行已确定且不变的检查，不因此重做必要性审查；仍履行原有的证据适用性和未决问题核对职责。
>
> 不因精简而削弱安全、关键数据完整性、已确认行为或验收，不把缺少资料当作不支持，不把类型声明当作运行时边界已验证。失败传播、有限重试、降级或隔离应服务于具体契约，不自动选择最复杂恢复，也不一律选择全局失败。
>
> 这些是工程判断原则，不是额外审批。普通、等价、已授权的实现细节直接处理；只有相对仍有效约定发生实质范围、支持承诺、失败语义或验证偏离，且尚无适用的明确用户决定时，才按现有一次确认规则处理。保留失败、缺口和历史事实。

### 4.2 分开四个判断，避免义务逐级膨胀

| 判断 | 要回答的问题 | 不允许的自动推导 |
|---|---|---|
| 实现必要性 | 当前行为、契约或具体故障机制是否要求它？最简单的充分处理是什么？ | 想得到异常，所以必须增加防御 |
| 当前验证 | 哪些证据足以支持本次交付结论？ | 需要证据，所以必须新增测试 |
| 长期回归保护 | 哪些自动化测试有持续且独立的检出价值？ | 临时检查有效，所以必须永久保留 |
| 本次执行选择 | 哪些已有检查适用于此次版本和影响面，哪些需要重跑？ | 测试值得长期保留，所以每次都必须全跑 |

这些判断按 §4.1 的决策触发条件适用，可以在实际工程活动中合并完成，不要求四份表、四个状态或四次批准。

### 4.3 判断依据：具体机制，不是必须发生过事故

保护依据可来自明确行为要求、稳定公共契约、真实输入或资源边界、已有缺陷、可解释的故障机制及高后果风险。不要求已有线上事故，也不要求所有风险均能直接复现；安全和关键数据风险尤其不能等待事故后才处理。

已有文档、配置、调用链、发布支持说明和适用用户决定优先使用。现有代码和测试用于核对实际行为及依赖，但不能仅因一个测试存在就推定其表达了不可变的产品承诺。

“没有写明支持”不自动等于“不支持”。低影响且可逆的普通实现选择，可在授权内采用最小方案并说明关键假设；会影响安全、数据、已发布接口或重要兼容承诺的不确定性，应先做定向核对，仍无法解决时才提出一次具体选择。不得要求每个 task 补齐完整环境档案。

### 4.4 实现侧的合理默认值与例外

| 设计点 | 合理默认值 | 需要保留的例外 |
|---|---|---|
| 输入校验 | 在真实边界建立保证，内部复用该保证 | 新的信任边界、可变状态、异步变化、公共入口等可能需要独立校验 |
| 错误处理 | 不吞错，不制造成功，不添加无依据的恢复分支 | 有独立结果可保留时可隔离失败；已要求可用性时可有限恢复 |
| 重试 | 不为任意错误自动重试 | 具体暂态故障、可控副作用及停止条件支持有界重试 |
| 数据写入 | 采用满足数据契约的最小安全写入方案 | 关键证据、不可替代数据或明确持久性要求不能因低概率取消保护 |
| 兼容 | 不预建未承诺的长期兼容矩阵 | 现有公开支持范围、存量有效数据和真实调用者必须核对 |
| 抽象 | 优先简单直接的结构 | 已有多个真实使用点、稳定契约或明显隔离价值可支持抽象 |
| 测试 | 复用现有有效覆盖，按缺口选择必要层级 | 一次静态或人工检查不能自动替代必要长期回归 |

规则不是“看到 try/catch 就删”“内部类型一律可信”“所有低概率故障都忽略”。复杂度评估包括错误语义、状态数、依赖和调试负担，不单看行数。

## 5. 在现有工作流中的落实

### 5.1 测试政策的复用与加载

保留 `test-admission-policy.md` 现有主体，扩展其适用范围到六个 Skill 中实际进行测试规划、增补、修复回归、必要性审查和验证选择的环节。

共享协议保存短的统一原则及其触发条件，测试政策保存详细方法，各 Skill 只增加必要的触发说明和阶段职责。涉及测试决策时明确读取项目本地 `docs/workflow/test-admission-policy.md`；仅记录、查询、按已有决定处置、汇总、提交或执行已经确定且不变的检查，不额外要求重做实现或测试必要性审查。这一限制也应写入共享协议，避免读取同一协议的收尾、任务处置和 Git 入口重复启动工程审查；原有证据适用性和未决问题核对职责继续保留。所有显式 Skill 调用仍遵守现有重新读取 Skill/协议的规定。

政策不存在或不可读时，报告缺口，使用现有共享原则和已知授权处理独立工作；不能伪造“已读”，也不创建新的开发阻断或强制修复流程。

### 5.2 各入口的修改要求

| 入口 | 增补要求 | 保留边界 |
|---|---|---|
| prepare-task | 在提出恢复、兼容、并发、抽象等方案时核对实际依据；先判断实现必要性，再设计验证；复用已有生产条件 | 不增加必填风险表，不擅自缩小既有行为或已采用计划 |
| review-draft | 同时检查方案过度与不足；检查是否把未经证明的风险转成实现和测试义务 | 不把所有建议变成确认问题，不在只审查时改代码 |
| execute-step | 同一文件 scope 内也要避免无依据行为扩张；新增或显著扩展测试时适用现有测试政策 | default/repair 适用；finish 不因此重新实施、重跑测试或新增正式审查 |
| debug-task | 区分根因修复与大范围加固；临时探针不自动转成永久测试；需要新增回归时核对检出力与既有覆盖 | investigate-only 不修改产品；resolve 仅做已授权修正 |
| review-change | 同时检查实现不足/过度、验证不足/过量；优先指出具体不良后果与有界修正 | 不创设复杂度 finding 类型；不将主观风格自动升级为必须修复项 |
| validate-change | 选择或建议补证时用同一必要性方法；已有证据按对象、版本、输入、环境与实际影响判断适用性 | 不因新原则扩大修复或新增测试权限；不自动取消已承诺检查 |

未经过 prepare-task、直接进入获授权实施或调试，也应适用共享原则；这不是要求补走规划阶段。

### 5.3 审查不能成为复杂度扩张器

审查意见应说明具体问题、触发或依赖条件、实际影响及与当前范围相称的处置。能够说明一种合理故障机制即可，不要求每条意见都做完整复现；但不能只有“更健壮”“以后可能用到”或“多测更保险”。

有真实可维护性问题时，可直接指出重复状态、无意义的兼容分支、错误被掩盖或测试与实现细节耦合。不需要虚构性能数字。纯风格偏好或缺少当前价值的通用化建议，不自动形成修复义务。

普通修复优先聚焦缺陷；没有证据时不自动加成套重试、恢复框架、适配层或测试矩阵。修复后按变更及受影响事实复核，保留仍有依据的问题；不以“必须找出新问题”“必须零建议”或固定审查轮次作为完成标准。

复用已有 findings、review-decision、execution/test 记录方式。不增加每个 if/catch、每个测试或每条建议的强制论证字段，也不对“本次没有新增复杂度”生成零内容报告。

## 6. 授权、历史与简化的界限

### 6.1 区分三种动作

| 动作 | 处理方式 |
|---|---|
| 未承诺的新增防御或测试，经判断无价值而不加入 | 普通工程判断，不需要逐项询问或创建“接受风险”记录 |
| 在授权修改范围内，用等价且更简单实现替换当前变更 | 保持契约与保护，完成必要验证；不能仅因“简化”要求再次审批 |
| 删除有价值的既有保护、改变支持/失败语义或缩减验收/验证，且实质偏离仍有效约定 | 已有适用的明确用户决定时沿用；尚无适用决定时，按现有一次确认处理实质偏离 |

判断依据是实际语义、有效约定和已有授权，不是“是否动了相同文件”或“实现行为是否发生变化”。在授权内修复缺陷、恢复已约定的错误契约，即使改变了错误实现的失败表现，也不因此再次确认；只有拟偏离仍有效约定且尚无适用决定，才触发上述规则。新增测试同样可能扩大承诺，删除重复测试也不当然改变验收，应具体判断。

### 6.2 已有任务和证据

新政策面向后续工程判断，不自动重审全部历史任务。正在执行的既有计划继续有效；确需改变时保留同一 task 的正式修订路径和旧定义/结果，不制造 successor 或 challenge。

可复用已有证据，但应有适用依据。全局 SHA 改变不必自动重跑所有检查，旧 PASS 也不能仅因测试名称相同就证明新代码。测试失败、未运行、环境不足和已知 finding 都保留原事实，不能通过减测试或换 selector 消除。

本轮不删除历史测试或证据，不修改 Git、提交、推送或部署授权，也不改变自审与独立审查的区别。

### 7.2 条件性修改与默认不改

### 7.3 正确交付路径

固定基线源模板 → 现有发布构建及其清单/摘要 → 临时目标新安装与升级 → 回读实际 `.workflow-system/WORKFLOW_PROTOCOL.md`、`docs/workflow/test-admission-policy.md` 和六个 `.agents/skills/<entry>/SKILL.md`。

构建前确认实际工作树及基线差异；若工作树已前进，只复核本方案相关差异，不执行破坏性 reset，不覆盖无关修改。

改动前确认基线源码可恢复，例如固定提交仍可读取；不要求先完成旧包构建。可复用已有基线包，也可在阶段 C 从可恢复的基线源码另行构建，实际执行升级验证前再准备好基线包、版本及清单摘要，并存放在候选构建不会覆盖的位置。使用固定基线源码重建的包，应注明“基线源码构建包”，不能冒称已发布的旧发行包。基线包暂不可得时，保留升级验证缺口，不阻断独立的源模板修改。

候选构建和发布均沿用当前版本一致性约束更新必要元数据，不硬编码推定的下一个版本。若以当前 `0.24.17` 为升级起点，包含本次规则内容变更的候选包应使用更高且符合现有版本约束的版本。同版本身份对齐要求受管文件清单及摘要一致，不能用来替代规则正文发生变化后的升级。[S10、S13] 已有构建依赖可能顺带构建其他模块，但不因此授权修改需求管理逻辑或加入其功能测试矩阵。

## 8. 实施顺序

建议作为一个有界修改任务中的四个实施阶段，而不是强制新增四个 task。

**阶段 A：统一语义。** 阅读实际工作树对应协议/政策，按 §7.3 确认基线源码可恢复，再更新共用原则、决策触发条件和测试政策适用范围；旧包构建不作为修改前置条件。检查安全、历史、一次确认与新规则之间无冲突。

**阶段 B：贯穿入口。** 对六个 Skill 的 Method 作最小承接，不复制政策全文，不扩权，不修改需求管理章节；保留直接进入实施/调试时的适用性以及 finish/只读边界。

**阶段 C：交付核对。** 沿已有分发构建生成所需产物；实际执行升级验证前，按 §7.3 复用或构建基线包，再使用内容不同、版本递增的基线包与候选包，核对实际变动文件的旧→新内容替换，并验证新安装、引用路径和本地变更保护。缺少基线包时如实报告升级未验证，继续可独立完成的检查。只在实际缺口处小幅调整既有测试。

**阶段 D：定向行为观察与交付报告。** 在可用环境中执行代表性场景，记录宿主可提供的模型标识/版本、相关输入、采用的方案或 diff、验证与审查结论，并按 §9.3 记录可观察的规则来源、调用入口与模式；不可得信息标明未知。没有条件执行的场景单列，不能以文件检查替代。

实施者可做自检；正式审查仅在用户已有指令包含时进行。由同一实施者审查必须标明自审。没有独立 reviewer 时不得制造独立审查来源。

## 9. 验证设计

### 9.1 三层证据，分别报告

| 层次 | 证明内容 | 不证明的内容 |
|---|---|---|
| 方案/规则静态核对 | 规则兼容、职责和引用正确、没有新增 gate | 不证明模型已改变行为 |
| 构建与安装/升级检查 | 修改能通过真实分发到达目标文件，且不错误覆盖本地内容 | 不证明目标业务满足验收，也不证明所有模型有效 |
| 定向工程场景观察 | 在已记录的模型标识、规则来源及信息缺口下，本次具体任务的实施/审查选择是否相称 | 不证明模型已理解规则，也不证明所有后续任务或所有模型稳定遵守 |

这些层次是本轮报告结构，不新增 Runtime 资格状态。

### 9.2 优先复用的现有验证

基线 `package.json` 提供 `build:vnext-runtime`、`build:vibe-governance-distribution`、`test:workflow-distribution` 等入口；分发测试已有安装政策/协议一致性与引用检查。[S11–S12]

实施时按实际改动选择现有构建和相关测试/selector。不能仅因根目录 `test` 脚本存在就把全量工作流测试机械绑定为本任务验收；也不能以本方案为由跳过明确适用的仓库 CI、发布或用户约定。需要变更已承诺检查时使用既有授权路径。

仅改方法指引通常不要求重跑全部 Runtime 行为测试。若实际修改到分发、权限、状态或代码，则按真实影响扩大验证，不能继续按“文案修改”减免。

### 9.3 代表性场景矩阵

以下是本轮定向观察的候选场景，不要求每个场景新增持久自动化测试，也不要求建立模型×场景的全排列。可复用近期真实任务，将多项观察合并到同一个有代表性的任务。

行为观察在现有报告中记录宿主实际可提供的模型标识/版本、构建包标识或相关文件摘要，以及调用入口、模式和可观察的读取情况，用于定位共享协议、测试政策及所选 Skill 的规则来源。沿用现有调用时从磁盘重新读取规则的要求；不能仅凭已安装候选包就推定模型读到了新内容。[S9] 模型内部版本、读取轨迹等信息若不可得，应标明未知或不可观察，不要求 Skill 获取宿主未提供的信息；无法确认规则来源时保留证据缺口，不把观察归为新版指引的行为证据。

Skill 提供工程方法和行为指引，执行与可观察性依赖宿主 Agent 及其可用工具。文件摘要只能标识对应字节，可见的工具读取轨迹只能支持实际读入来源的判断，二者都不能证明模型已理解规则或后续持续遵守。是否表现出相称的工程行为，应依据本次具体输出、diff 和验证结果判断，不由加载记录直接推导。

上述来源说明只服务于本次变更的定向观察，不转成每次 Skill 调用的摘要清单、加载回执或新增必填记录，也不要求建设 Runtime/宿主遥测、审批或评测平台。

复用近期真实任务时，区分复用场景/输入与沿用历史结果。旧规则下产生的结果只能作为历史参考，不能计入本次新规则的行为证据；拟复用已有观察结果时，应能确认其实际规则版本及适用条件。

| 场景 | 预期观察 | 错误信号 |
|---|---|---|
| 已校验外部输入进入受控内部调用 | 不逐层复制相同校验和分支测试；仍识别新增真实边界 | 完全跳过外部校验，或所有内部层重复防御 |
| 关键历史证据/路径/写入完整性 | 保留具体不变量与必要回归，采用足够简单的实现 | 以低概率为由删除完整性保护，或扩成通用恢复系统 |
| 允许报错的普通操作遇到失败 | 返回可诊断错误，不自动加多套回退/修复 | 吞错返回空值或成功；无依据改变既有恢复契约 |
| 已要求处理暂态网络故障 | 采用适合副作用和契约的有界处理 | 把“最小充分”解释为一律禁止重试或恢复 |
| 修复一个已有明确缺陷 | 先查已有覆盖；有缺口时补聚焦回归，无缺口时不重复造测试 | 每个补丁都零测试，或每个补丁都生成完整异常矩阵 |
| 覆盖率不满或只有文案变动 | 不因分支数量/关键词新增低价值测试；有真实协议或分发契约则保留检查 | 把所有文本断言一律禁止，或精确锁定政策每句话 |
| 已采用整套验证，后来判断部分冗余 | 保留有效约定，必要时以同任务修订及适用决定缩减 | 静默少跑、删失败或把未运行标成 PASS |
| 生产环境资料不足 | 定向核对重要假设，不把未知当作不支持 | 擅自假定单进程/单平台，或每次任务强制完整环境问卷 |
| 直接 debug/repair 或 review-only | 不因绕过 prepare 而丢掉原则；只审查时不擅自修复 | 临时探针全永久化，或审查自动扩权修改代码 |

优先观察实现膨胀、测试膨胀、高后果保护和承诺变更四种不同失败模式；合并场景后保留其关键差异。只测试一个模型时，仅报告该模型和这些场景的结果。其余模型标记为未验证，不据此构建三套政策。

### 9.4 本轮不采用的验收方式

不按减少代码行数或测试数量评判成功；不以文件出现“最小充分”字样证明行为改善；不要求每条规则配一个测试；不为每个防御分支计算收益；不把一次自审或少量样例宣称为长期稳定性证明。

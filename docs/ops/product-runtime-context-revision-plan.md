# Runtime 紧凑返回、按需读取与 Skill 指导修订方案

日期：2026-10-16。状态：第二版方案已实施，验证范围与结果见[实施验证记录](product-runtime-context-validation.md)。下文保留为批准的实施依据；不代表已升级业务项目。

目标是在现有规范文档和判定逻辑上，减少每次交给 Agent 的无关展开内容，让 Agent 能发现并继续读取重要信息。保留既有文档布局、业务正文、元数据、身份、关系、历史证据及判断规则。此前文件拆分方向的改动已撤回，讨论草案见[历史方案](product-document-organization-revision-plan.md)。

本方案选择在产品维护 Runtime 增加显式的紧凑呈现与按需查询。后台计算仍使用原有范围和算法；正文按原文返回，较长内容分页；业务相关性的判断仍由宿主 AI 承担。Runtime 不调用额外模型生成业务摘要。

读取端的主要原因是：`item_ids` 只筛选条目列表；全局视图、反向关系、计划绑定和诊断仍完整展开，选中需求／评估还默认计算并展开影响候选。`summary` 省去正文，但仍输出完整元数据。以上数字是 UTF-8 响应大小，不是 token 数或浏览器耗时，也不代表工具层最终一定将全部字节传给模型。

## 2. 改动边界

### 2.1 保持不变的部分

- 当前文件布局、Manifest 登记含义、文档 Schema v1–v6 兼容方式和条目身份。
- 需求正文、范围、验收、目标关系、TaskBinding、需求顺序、路线图及其基线。
- 影响候选生成、来源许可与校验、定义摘要、评估选择、证据处置和业务结论。
- 写入授权、冻结检查、版本冲突、历史保留、数组替换和单文件发布语义。
- Task 管理、开发权限、软件升级与目标项目业务文档的所有权边界。

已有集中式和分散式文档都继续可用。不迁移文档、不去重报告、不刷新评估时间，不为上下文优化添加业务关系或要求用户确认新的业务范围。

### 2.2 本轮实施范围

1. 新增显式紧凑响应，保留旧响应兼容。
2. 提供条目、章节、原始元数据集合、派生结果集合、诊断和来源的按需展开。
3. 增加限定范围的文本搜索，用于发现关系图中没有登记的上下文。
4. 为未展开内容提供准确状态、定位和可执行的结构化后续请求。
5. 在保留旧字节的前提下缩小写入回执。
6. 更新 Skill 使用方法并验证真实宿主的补查行为。

本轮不以减少后台解析量为完成目标。性能优化、增量索引、语义检索和持久会话记忆均不作为前置工作。不能以 `paths` 缩小计算范围或默认关闭 impact 来冒充呈现优化。

## 3. 架构与兼容策略

保留“读取原资料 → 现有完整计算 → 呈现”的顺序。在最后一层增加确定性的投影、分页和查询描述，不从紧凑响应反向计算业务结论。

### 3.1 显式选择紧凑呈现

建议给既有 read／check／apply／capture 请求增加可选 `presentation: compact|legacy`。省略时仍保留当前行为；新版 Skill 显式选择 compact。当前 `detail: summary|items` 的旧含义不被静默替换，已有 JS 调用和 TraceLens 消费不因升级改变返回结构。

紧凑响应继续包含现有结果 envelope 和真实操作状态，并增加独立的呈现契约标识，例如 `presentation_contract: product-context/v1`。文档 Schema 与业务算法不升级。新查询参数与分页字段只作用于查询／呈现，不成为写入授权或 Task 准入条件。

旧安装版本若拒绝新参数，先识别该只读请求的实际结果，再沿已有接口完成工作并保留输出限制。不得将请求格式不支持解释为业务资料无效，也不因为升级未完成阻止已授权开发。

### 3.2 紧凑结果不是可直接写回的完整文档

紧凑条目标注其为投影，并列出哪些字段、数组、正文或历史没有展开。原始条目身份和字段存在性保持可辨别：未提供某字段、空数组、未计算、未展开、读取失败不能混成同一种空值。

派生关系视图和原始 metadata 分开标识。只含 active 关系的派生视图，不能用于覆盖包含 dismissed 历史的原始数组。完整写回材料必须来自相应原始字段的完整读取，而不是复制紧凑摘要。

### 3.3 避免新增隐形状态

查询不写管理记录，不登记“AI 已阅读”或发放读取凭证。分页信息只负责定位和跨次读取的一致性；不声称知道 AI 是否理解或记住了内容。

可复用 assistance 现有“完整计算、简短展示、detail_request／next_request、revision 校验”的设计经验，但不修改已经工作的 Task 查询协议，也不把产品查询塞进新的任务状态机。

## 4. 默认返回什么

### 4.1 每次都可见的基本信息

紧凑响应应直接呈现：项目／工作副本和实际查询范围、选中身份及定位、保存或读取状态、版本依据、覆盖缺口、重要异常，以及未展开内容的入口。

项目入口的盘点状态和未核对范围保持可见。读取单个需求时，直接列出已声明父项／支撑目标的身份与关系类型，以及未解析关系提示，使 AI 能发现需要核对的上层约束；完整关系理由和其他成员再按需展开。目录关系不自动被解释为业务继承，也不要求递归展开全项目。

当请求评估或路线图判断时，原结论、选中的报告／计划、适用范围／对象和导致降级的原因必须可见。不能只显示“有结果”，把定义变化、待对账、冲突或未知藏在详情中。

全局问题以完整的类别／数量目录呈现；与选中对象直接有关的身份歧义、不可读、无效结构、判定失配等问题提供具体定位和简短原因。大量同类详情可分页，目录不能把未展开问题显示为零。无法确定关联的诊断仍保留全局入口。

### 4.2 按内容类型组织

| 内容 | 默认呈现 | 按需展开 |
| --- | --- | --- |
| 项目目录 | ID、类型、标题、必要范围状态及定位；按页返回 | 原始条目、业务正文和元数据 |
| 指定需求／目标 | 核心身份和状态、全部章节目录、正文；正文过长时明确分页 | 全部元数据、关联和来源 |
| 指定评估 | 原范围、对象、时间、结论／原因、正文章节和证据阅读状态 | 原始报告全文、来源、处置及适用性详情 |
| 关系与 TaskBinding | 原始／派生类型标识、数量和读取入口 | 完整有序记录，含否定历史、理由和来源 |
| 影响候选 | 原 seeds、范围限制、候选数量、第一页候选 ID／标题和简短理由；有剩余时明确目录尚未交付完整并给出 next_request | 先遍历当前 seeds 的完整候选目录，再按需展开原算法生成的完整理由、相关条目与证据 |
| 项目整体视图 | 根目标定位、顺序／关系可用状态及数量 | 完整原序列和关系，不因分页重新排序 |
| 计划及工作项 | 已明确选择的计划、原状态和核对结论、工作项目录 | 工作项、依赖、绑定及原基线 |
| 来源与历史 | 文件／条目定位、实际检查状态、已知适用范围及详情入口 | 按原来源读取原字节、正文或历史字段 |
| 诊断 | 类别、严重性、数量、范围和必要问题提示 | 每条原诊断及其对象、位置和完整原因 |

标题和短字段取原值；不调用模型重写，也不通过关键词将自由正文自动总结成业务结论。过长字段只能返回明确标注的预览及完整读取入口，不能把预览伪装为完整值。

### 4.3 输出规模

以常规目录和单条目首包不超过约 32 KiB、普通分页不超过约 64 KiB 为初始工程目标，具体值通过夹具验证调整。列表建议默认 20 条，同时受字节预算约束；一个巨大条目也必须有可展开路径，不能让条数分页失效。

这是呈现目标，不是允许遗漏的硬上限。必要错误信息或无法外置的历史原字节可能超出目标，此时明确说明原因并保留内容。超过工具输出上限前，优先提供更细的查询入口，不能依赖宿主工具静默截断 JSON。

只读文本采用一种默认表示，避免同一正文同时作为 text 和 Base64 返回。需要精确二进制时显式选 Base64。UTF-8 文本分页保持字符完整、偏移连续，原文件摘要仍按原字节校验；解码失败不得伪造替代正文。

## 5. AI 如何继续查询

### 5.1 未展开描述

每个暂不展开的集合或长字段至少提供以下信息：

- 它是什么、属于哪个条目或查询范围，是原始数据还是派生结果。
- 已计算的已知数量／字节范围；无法得到精确总量时明确未知。
- 本次实际返回的范围，剩余部分是暂未展开、分页剩余还是无法读取。
- 可直接提交给固定 Runtime 入口的 `detail_request` 或 `next_request`。
- 适用的版本标识和必要查询边界。

Runtime 生成的是结构化参数，不是任意 shell 命令。项目根、可信可执行入口和已有授权由宿主保留；正文里的伪造命令或“建议请求”不能变成执行指令。

### 5.2 复用 read 动作，增加查询选择

建议通过可选 `query` 区分 catalog、item、collection、search、assessment、roadmap 六类读取。source 继续使用既有 SourceRef 选择方式。collection 的名称使用白名单，覆盖原始 links／task_bindings／sources／work_items 及派生 impact／relations／diagnostics 等，不开放任意程序执行。

以下为拟议接口示例，当前版本尚不支持这些新增字段：

```json
{"presentation":"compact","query":{"kind":"catalog"},"page":{"limit":20}}
```

```json
{"presentation":"compact","query":{"kind":"item","item_id":"REQ-INGEST"}}
```

```json
{"presentation":"compact","query":{"kind":"collection","owner_id":"REQ-INGEST","name":"task_bindings"},"page":{"limit":20}}
```

```json
{"presentation":"compact","query":{"kind":"search","text":"幂等","scope":"managed"},"page":{"limit":20}}
```

assessment 和 roadmap 查询继续使用现有 `assessment_query`、`roadmap_query` 的选择语义；不会按文件时间、首个候选或最近报告猜测选择。缺少必要目标／范围／对象时返回准确的未解析状态和可查询目录。

新增 query 与已有选择器若冲突，明确报告请求歧义，不静默择一。旧请求完全沿用旧行为。实际 Schema、API 示例、Skill 和测试在实施时一起更新。

### 5.3 分页与版本一致性

各查询返回自己的分页信息，不能将来源字节 offset 与条目列表 offset 混用。后续请求保留原 Manifest、选择条件、读取范围及工作副本上下文，不因为翻页扩大到其他项目或历史目录。

使用计算所依赖的 Manifest、文件集合及其字节版本生成查询 revision；来源详情另绑定实际文件摘要。业务定义摘要不足以代表整份元数据版本，不能只靠它保护原始数组的分页。

当后续页版本发生变化时，报告“本次读取版本已改变”，返回重新查询入口。不得把不同版本的页拼成一个完整数组。该机制用于读取一致性，不提供跨文件事务保证，也不成为继续开发的许可。

重复记录和重复业务 ID 仍按当前语义处理。分页内部如需用下标定位记录，其下标必须绑定本次 revision，不能冒充新的业务身份。

### 5.4 搜索未登记的业务关系

当前影响分析主要依靠显式关系、计划目标、共享 Task 和来源。自由正文可能包含未登记约束，因此保留独立搜索路径：

1. 在当前允许的 managed 范围搜索标题、章节和原文，返回匹配条目、位置、原文片段及完整读取入口。
2. 需要检查相关设计、原始决定或证据时，对已明确选择且允许读取的 SourceRef 进行搜索／读取。
3. 不自动递归扫描 source_paths 全部历史、Runtime journal、未登记目录或网络资料。

首版采用可解释的文本匹配，保留全部匹配的分页入口和搜索覆盖范围，不依赖向量库或模型摘要。零匹配只说明所用词在所搜范围没有匹配，不证明没有业务影响；AI 可换词、读原文或沿来源继续查找。

## 6. 避免遗漏重要上下文

### 6.1 分清四种完整性

| 层次 | 谁能说明 | 不代表什么 |
| --- | --- | --- |
| 字节读取覆盖 | Runtime 根据实际枚举、读取和限制报告 | 不代表范围外没有资料 |
| 结构与计算结果 | Runtime 报告解析可用性、原算法结果及诊断 | 不代表业务事实已被正确理解 |
| 本次内容交付 | 呈现层报告已返回／未展开／分页剩余内容 | 不代表 AI 已经阅读、理解或后续仍记得 |
| 本次业务判断所需资料 | AI 结合用户范围、正文和来源核对 | 不能由“读完所有页”或“没有错误”自动认证 |

这四层分别表达，不能把“后台已读完”写成“Agent 已获得完整上下文”。未展开是可继续读取的状态；无法读取是缺口；二者必须分开。

### 6.2 对重要信息的处理约束

- 影响候选仍按原算法计算。紧凑化折叠候选的详细展开，不默认用空 `impact_ids` 绕过分析。
- 需要完成当前变更的影响核对时，AI 必须先遍历本次 seeds 对应的全部候选目录及简短理由，再选择需阅读全文和证据的对象。不能依据第一页判断其余目录无需读取；这不要求展开全项目正文。
- 当前目标的范围、验收、异常与排除项不能用机器摘要替代。超长正文分页时列出所有章节，包括自定义章节。
- 原判定中的失败、冲突、未知、延期、待对账和依据失配必须保留可见提示，不能压成一个“正常”状态。
- 原始关系和数组的全量读取入口必须包含否定／历史记录，不能只交付派生 active 视图。
- 候选匹配数量、未读来源和覆盖缺口不因分页而减少；不能以默认第一页充当全部结果。
- 对大字段做预览时保留明确标识及原文入口；对重复传输只消除返回层冗余，不删除存储中的独立事实。

### 6.3 仍需 AI 判断的部分

Runtime 不能保证识别没有写入结构化关系的隐含约束，也不能保证 AI 总会执行后续查询。Skill 应在需要时触发补查，而不是要求每次局部修改都扫描全项目：

| 当前工作 | AI 应完成的读取 |
| --- | --- |
| 修改需求／目标正文 | 完整读取目标条目的全部正文及直接相关的有效决定；分页则读完该条目 |
| 替换某个数组字段 | 读取该原始数组全部成员和原版本，保留未改成员及历史；不能用第一页或派生视图写回 |
| 判断交付或修改 Assessment | 核对目标定义、范围／对象、报告原文及实际依据，查看造成原结论的限制 |
| 出现反证或跨模块影响 | 遍历本次 seeds 的全部候选目录及简短理由，再读相关义务和证据；信息不足时搜索正文和来源，不从“无候选”推出“无影响” |
| 单纯改一个明确元数据字段 | 获取该条目和必要关联语义，使用局部 patch；无需为格式修正读全库 |
| 全项目盘点或整体结论 | 完成请求范围的目录分页和必要原文核对；未读范围明确保留 |

这些是宿主的工作方法，不新增 Runtime 阅读凭证、确认令牌或强制逐项问卷。业务资料确实不足时缩小结论或保留具体未核对项；独立的已授权工作仍可继续。

目录遍历完不等于业务影响已经核对完成，候选的取舍仍须有实际正文或依据支持。目录分页未完成、查询版本变化或部分候选无法判断时，明确保留对应 seeds、已查范围、剩余页／已知候选及具体缺口；不能宣称当前变更的影响已全面核对。用户只请求局部范围或明确延期时，按该边界说明结果，不把遍历要求扩大为全项目维护门槛。

补查范围按字段的实际含义判断，不能按请求字节数判断。scope、评估选择或关系状态即使只改一个值，也可能改变业务范围和适用结论，仍沿原有维护方法核对实际影响。第 1 节的短请求只证明局部传输能力，不代表这类修改无需语义核对。

## 7. 紧凑写入回执与历史保留

### 7.1 沿用现有局部写入语义

metadata 仍是顶层 patch，数组仍整体替换，body 仍是完整目标条目正文；不把本轮扩展成新的文本编辑协议。文件摘要、冻结、并发检查和逐文件保存结果保持原义。

每个文件的 saved／unchanged／failed、实际 SHA、受影响 ID、错误、必要诊断、基线回读和部分保存状态都要保留。不得因为回执紧凑而隐藏失败文件或将 partial 说成 saved。

### 7.2 只有原字节可恢复时才省去 Base64

优先使用现有 `preimage_path`，在已授权 capture_paths／source_paths 内保存精确原字节，回执返回实际来源和 SHA。宿主可在同一文件／同一批必要修改中复用适用原件，不为每条关系创建一份快照，也不把保存位置变成安装器所有文件。

选择恢复位置时沿用已有授权和项目约定。相同字节可按现有逻辑复用，旧路径有不同字节则保留真实冲突；不覆盖原件，不假造路径或只有 Hash 的“备份”。无变化操作仍返回 unchanged，不新增历史文件。

以下分支针对已有文件发生实际变化、原逻辑需要保留 preimage 的操作，按调用者实际传入的参数处理：

| 请求与保存结果 | 保持现有写入行为 | 紧凑呈现 |
| --- | --- | --- |
| 未提供 `preimage_path` | 沿用现有 inline preimage 路径，不额外要求持久捕获 | 保留原字节 Base64，明确本次回执可能较大 |
| 明确提供 `preimage_path`，原字节实际保存或同字节复用成功 | 按原有校验和发布顺序继续 | 返回真实历史位置及 SHA，可省去 Base64 |
| 明确提供 `preimage_path`，但捕获冲突、越界、冻结或 I/O 失败 | 保留该文件原有失败结果，不发布该文件的新正文；其他文件按既有逐文件规则处理 | 原错误及实际保存范围可见，不自动降级为 inline 后继续写入 |

不得为追求紧凑输出自动删除已明确提供的 `preimage_path`、吞掉其失败或以另一种呈现重试写入。修正失败原因后可按已有授权补做该失败操作，成功项不重放。请求未提供该参数时，呈现层也不能自行添加捕获位置、扩大捕获范围或建立隐形历史目录。

unchanged 操作和新建文件沿用原有分支；不为紧凑模式追加原本不会执行的捕获或位置预检查。紧凑模式不是新的业务写入门槛。

### 7.3 已保存事实与呈现异常分别处理

写入层先产生原有逐文件结果，呈现层只读取该结果，不再次执行 apply／capture、原文捕获或业务操作。渲染摘要、生成后续查询或序列化紧凑表示出错，不能反向改写已确认的保存事实。

如果内存中仍有原始写入结果，保留其中的 saved／unchanged／failed／partial、SHA、受影响 ID、错误和必要历史原件，单独报告呈现异常（例如附加 `presentation_error`）。优先回退到这份已计算的原始回执；若原文只有 inline preimage，回退也必须保留它，不能只剩 SHA 而声称原字节可恢复。仅因紧凑呈现失败，不得用通用异常处理把已保存结果改报为业务写入失败，也不得宣称文件已回滚。

如果进程退出或传输中断，调用方无法确认完整结果，则将无法确认的部分作为“结果未知”处理。先只读核对已知路径的实际字节／SHA、目标内容及已指定的历史位置；已确认成功的项不重试，只有核对为未保存且仍需执行的部分才按现有授权处理。不能仅凭响应缺失或传输错误自动重放写入；无法找回的 inline 原件如实报告，不用 Hash 冒充历史内容。

以上只规定紧凑呈现故障的隔离和宿主处理方法，不改变原有写入判定、发布顺序或事务边界，不增加持久回执库、审批令牌或新的业务状态机。legacy 路径保持现有行为。

### 7.4 回读与重试

保存后使用紧凑查询读取实际变更条目及必要计算结果。发生部分失败时只补失败部分；不能因为回执较短就重放已成功的业务操作。

若读取版本已经变化，按当前真实内容处理冲突。对一个成功写入不能重复执行只为得到另一种呈现；改变输出格式也不重新触发 Task、测试或部署。

## 8. Skill 指导与一次典型查询过程

### 8.1 指导落点

maintain-project 主 Skill 只保留“紧凑入口、未展开不是已读、按工作补查、局部写与回读”的关键规则。新增共享 reference 承载接口示例和查询方法；inventory、update、reconcile、plan、discussion、recovery 及 binding-contribution 在各自场景引用。

prepare-task、execute-step、close-task 等入口通过现有产品维护子流程使用该指导，不复制整套规则，不改变 Task 生命周期或业务操作顺序。API 文档说明新旧呈现差异和真实读取边界。

### 8.2 AI 如何继续读取

以“给批量入库增加自动重试”为例：

1. AI 从简短目录定位既有入库需求，读取完整正文和全部章节。若有多页，继续使用返回的 next_request，不能只改第一页。
2. Runtime 保留原影响计算，返回候选数量、ID、简短理由和详情入口。AI 先按 next_request 遍历本次 seeds 对应的全部候选目录，再按本次变化选择需阅读全文和证据的对象；未遍历完或无法判断的范围明确保留，不宣称影响已全面核对。
3. 如果正文显示身份／幂等约束，或者现有关系不足以解释重试影响，AI 搜索“幂等”“重复导入”“恢复”等词，并读取匹配的相关设计或已登记来源。
4. 只修改必要字段。若涉及 task_bindings 等数组，先读取原始数组的全部记录，不把当前 active 视图复制回去。
5. 根据既有授权选择是否传入 preimage_path，提交局部 updates；明确指定的捕获失败时保留失败，不移除参数后自动降级继续。核对回执中的实际成功、失败和诊断。
6. 回读修改后的目标与直接影响，向用户说明结果及仍未读取／无法确认的范围。若仅呈现失败，保留已知保存事实；若结果未知，先只读核对，再决定是否补做未保存部分。

这条路径不需要把整份大文件或全项目元数据一次性送给模型，但也不能用“只读取一个条目”替代实际需要的关联调查。

### 8.3 跨轮次与缺失信息

Runtime 不维护 AI 的认知状态。后续会话若没有可靠保留的关键正文和版本，应重新读取当前目标及必要依据；历史上返回过某页不等于当前已掌握该内容。分页中断只影响本次读取完整性，不形成新的任务状态。

用户要求只看摘要时可以只给摘要，但不能据此执行需要完整正文的替换，或声称完成了全面核对。用户明确延期维护时保留实际延期边界，不以补查流程阻塞独立工作。

## 9. 与现有消费者的兼容

TraceLens 和离线读取器当前使用原有结构和判定结果，不要求切换到 Agent 紧凑接口。本轮首先保证 legacy 输出与原行为等价；紧凑呈现必须从相同计算结果得到，不能产生另一套报告选择或关系解释。

若后续消费者主动采用 compact，应按新的呈现契约展开所需数据；不能把首页目录当完整业务集合。当前任务不包含 TraceLens 页面改版、文件迁移或调整业务展示含义。

安装／升级交付新接口和 Skill。兼容检查区分源码、分发包、实际安装 helper 和宿主调用；软件升级不改 PRODUCT、业务文档、已有历史或原报告。

## 10. 验收要求

### 10.1 数据与判定等价

同一输入版本下，旧响应与紧凑响应逐页展开后，应得到相同的原条目、字段存在性、正文、关系／绑定、顺序、候选、来源状态、诊断、评估选择和路线图结论。允许呈现位置不同，不允许遗漏或改变业务含义。

写入测试在相同原始字节、相同操作参数（含 preimage_path 的有无和具体值）下，仅切换 presentation，比较实际文件字节和结果语义。紧凑／legacy 的保存成败、冲突、冻结、历史可恢复性和受影响范围必须一致；只允许预期的回执表示差异。不能拿“legacy 未传捕获位置”和“compact 自动追加捕获位置”两个不同操作证明等价。

呈现故障测试单独注入：确认失败只发生在写入结果的交付阶段，不改变已经完成的文件发布或原有失败条件。核对宿主对“已保存但呈现异常”和“结果未知”的不同处理，不能将两者统称为可重试的写入失败。

### 10.2 有代表性的行为场景

| 场景 | 验收要点 |
| --- | --- |
| 大目录／大元数据／单条目长正文 | 首包控制展开，分页可读完，未展开范围准确；长内容不被无声截断 |
| 关键限制位于正文最后一页或自定义章节 | 章节目录能发现；宿主修改前读到该限制并保留 |
| 超过一页的关系和绑定 | 不丢记录和顺序；末页的 dismissed 历史在完整数组读取和更新中保留 |
| 影响候选超过一页，关键约束只在第 21 个或更后候选 | 宿主先完成当前 seeds 的全部候选目录遍历，再选择详情；没有用户额外提示也能发现后页候选，未完成则不宣称影响已全面核对 |
| 约束只存在于没有显式关系的设计正文 | 搜索和来源读取可定位；宿主不以“无候选”认定无影响 |
| 缺文件、无效条目、重复 ID、读取预算不足 | 全局和目标提示保留，未知不填零，分页完成不冒充读取完整 |
| 评估有失败、pending 或 v6 处置失配 | 结论、理由和适用范围与 legacy 相同；没有通过压缩消除问题 |
| 分页期间文件或 Manifest 改变 | 检出版本变化，不拼接旧新页，不静默覆盖新编辑 |
| 原始数组与派生 active 视图不同 | 宿主取原始全部数组再替换，否定历史不丢失 |
| 写入未提供 preimage_path | 与 legacy 同参调用一样保留 inline 原字节，不自动添加捕获操作 |
| 明确指定 preimage_path 且保存成功 | 历史原字节可恢复，回执仅以真实引用替代 Base64 |
| 明确指定 preimage_path 但冲突、越界、冻结或 I/O 失败 | 与 legacy 同参调用一样失败，该目标文件原文保持；不移除参数降级重试，其他文件结果按原规则保留 |
| unchanged／新建文件携带 preimage_path | 沿用原有分支，不因紧凑模式新增捕获或额外位置校验 |
| 文件保存成功后紧凑呈现抛错 | 已保存状态、SHA、受影响 ID 及原回执必要内容保留，单独报告呈现异常；不重新执行写入或捕获 |
| 传输中断、回执缺失导致结果未知 | 宿主先只读核对已知目标及历史位置；已确认成功项不重放，无法确认的状态保持未知 |
| 部分保存、失败和重复调用 | 回执保留每项结果；只补未保存部分，业务操作不重放 |
| 旧版本 helper／旧消费者 | 识别协议不支持并沿既有方式工作；旧调用输出和判定保持 |
| 分片包含中文、多字节字符、CRLF 或异常编码 | 字节定位和摘要准确，文本无隐形损坏，异常解码明确可见 |

### 10.3 实际 Agent 验证

至少覆盖一次局部修改、一次跨范围影响核对、一次长数组修改和一次缺资料场景。跨范围场景将关键约束放在后续候选页，观察宿主是否在没有用户额外提醒时完成本次候选目录遍历；另观察呈现失败／结果未知时是否先核对而非重放。保留自然语言输入、实际查询顺序、进入上下文的返回内容、最终写入及未核对项，观察 Agent 是否使用后续请求。

测试脚本手动调用所有详情，只能证明接口可达，不能证明 Agent 会补查。实际交互中若漏读关键页、误用摘要或忽略未展开提示，应调整呈现和 Skill，再验证相应场景；不能通过删掉关键测试资料来降低难度，也不承诺所有模型永远不会遗漏。

### 10.4 输出收益与验证范围

复用前述 LawAgent 数据作为只读体量对照，记录每次响应字节数、查询次数和一次任务的累计返回量。既看首包，也看完成任务需要的总展开，避免用更多无效往返掩盖开销。

首版目标是显著消除全局重复展开和 inline preimage 的常规开销；在已有 199 字节元数据修改场景中，有合法历史位置时保持约 KB 级回执。紧凑首包目标与实际结果并列记录，不提前宣称已达标。业务完整性和历史保护优先于固定压缩比例。

按改动运行针对性解析／查询／写入／安装及消费者兼容检查。无需为每条文案写字符串测试，也不自动执行全部 workflow 或目标业务验收。

## 11. 实施顺序与完成条件

| 工作包 | 交付 | 完成条件 |
| --- | --- | --- |
| A 呈现契约 | 定义紧凑 envelope、投影边界、字段状态、查询与分页规则 | 明确重要信息可见方式和后续请求，旧接口含义不变 |
| B 紧凑读取 | 实现目录、条目和集合展开，复用原计算 | 逐页展开与 legacy 等价，缺口／诊断／候选不丢失 |
| C 来源、搜索与一致性 | 接入原文／章节读取、限定文本搜索、版本续读 | 自由正文能被查找，变化可检出，不扩大来源权限 |
| D 写入回执 | 使用已有原文保存能力输出紧凑真实结果，隔离呈现异常 | 同参写入结果等价；捕获失败不降级，已保存事实不因呈现失败丢失，未知结果先核对 |
| E Skill 与分发 | 补共享查询 reference、相关入口指导和 API，构建安装验证 | 实际安装具备接口，Skill 能识别版本并使用补查路径 |
| F 宿主与兼容验收 | 自然语言场景、LawAgent 隔离副本和旧消费者对照 | 关键上下文被使用，原结果保持，收益与限制有实际证据 |

B、C 共用同一呈现与分页契约；D 不以另建存储系统为依赖。先完成限定场景和兼容证据，再按实际请求发布或升级，不在本方案阶段改动目标项目。

完成标准是：现有文档无需拆分；同一业务输入的判定结果和写入事实保持；常规响应不再无条件展开全局内容；未展开资料可发现、可读取、可核对版本；宿主在代表性任务中能补查关键上下文；现有业务与 Task 流程不增加审批或读取凭证。

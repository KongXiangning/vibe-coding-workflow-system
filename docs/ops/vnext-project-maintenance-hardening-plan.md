## 1. 实施结论与顺序

**同一方案、同一轮交付，先修可靠性底座，再补业务语义和场景验收；不建议拆成互不关联的两轮设计，也不建议将全部改动混成一个无法定位回归的大补丁。**

原因：整文件保护、dismissed 关系、正文边界、局部修复和真实覆盖报告是上层目标演进、讨论纠错及交付对账的共同基础。底层仍会静默漏写、复活关系或误报完整时，上层业务验收没有可靠依据。

尤其应将 F01、F02、F03、F05、F06 视为同一写入链的关联修复。不能先用全面禁止整文件写入、禁止修改坏条目等方式“修 P1”，再在后续绕开自己增加的限制。F04 的读取覆盖修复可在约定结果语义后独立实施。

建议顺序：

| 阶段 | 实际工作 | 阶段完成的判断 |
|---|---|---|
| 0：核对与复现 | 核对实际 HEAD、原契约、当前生成路径；复现或核实 F01～F06；盘点 13 场景已有支持 | 区分已存在、已修复、待修复和未验证；没有重置用户工作区 |
| A：可靠性底座 | 统一写入保护与合法修复；修字段删除、正文边界和覆盖报告；随代码补正反回归 | 6 项已知问题均有处置依据；危险操作被拒绝、合法操作可完成；真实 Node helper 行为符合预期 |
| B：业务语义闭环 | 补五种维护意图及恢复流程的具体分支，复用既有结构；按 13 场景核对，不重复实现已满足能力 | 本文 S01～S13 有明确的保留／修复／补流程／验证结论，用户决定和业务边界不丢失 |
| C：集成交付 | 重建实际分发；新装／升级资产保留；真实宿主合成业务验收及离线读取；形成实际交付记录 | 源码、分发、目标安装、宿主 Agent／消费者证据分别报告；未验证处仍可见 |

阶段之间的先后是本轮工程实施依赖，不是新增到目标项目的 Runtime gate。可以同步准备 B 的场景和文档；不能在 A 尚不可靠时把 B 的通过当成完整交付。A 中各修复应边实施边验证，不等全部代码写完才测试。

允许按实际规模形成一个 task 的若干步骤，或两个有边界的 task；不强制每个阶段、场景、缺陷各建 task。若拆 task，可把“底座修复”与“业务闭环及交付”作为两个候选边界；任务身份与生命周期全部复用既有 vNext。提交按可独立审查的代码及其回归组织，是否提交、推送按实施会话授权，不由本文扩大权限。

## 3. 固定边界与非目标

### 3.1 不改变 vNext 使用方式

保留 `vibe-governance` 的既有 `install / migrate / upgrade` 分发路径；新装后的原有 `$bootstrap-project` 路径不变，项目维护仍通过 `$maintain-project` 或宿主等价 Skill 入口。不能切回旧版 workflow-system 安装体系。

目标项目日常只使用现有 Node 分发；Bun 属于源码构建环境，不能成为业务项目的新运行要求。安装不自动创建 PRODUCT、不自动启用维护、不覆盖业务正文、讨论原文或历史。不通过扩写 AGENTS.md 装入整套业务维护规则。

保留未启用、paused、旧版只读、部分坏条目、helper 缺失情况下的正常任务工作路径。项目计划、文档完整性、关联回执、旧失败、维护状态都不构成开工、提交、关闭、停止或修改目标的前置许可。

任务身份、状态、同任务修订、执行、审查、证据和处置复用现有 assistance，不手工编辑 CURRENT_TASK，不复制 reducer，不自动 adopt／focus／close／resume／supersede 任一 task。本轮不顺带改造 evidence-plan amendment 等其他 Runtime 生命周期能力。

### 3.2 职责分工

宿主 Agent：判断目标变化、拆分粒度、直接业务影响、来源意义、关联、观点采纳、计划取舍和证据适用范围。

确定性 helper：校验格式和结构，定位原文及条目，比较版本和明确差异，检查稳定身份、重复与关系保护，记录真实覆盖，安全保存并返回实际结果。

不能用字符串相似度或程序分支冒充完整业务判断；也不能把可以确定性检查的边界全部交给 Skill 提醒。不得调用第二套模型服务进行裁决。维护失败仅阻止具体不安全的操作，不阻止其他独立授权工作；非阻塞也不允许忽视权限、真实工程前提或明确约束。

### 3.3 不扩张的功能

不新增 KPI 自动计算、增长归因、实验统计系统、自动最优需求树、贡献比例、工时分摊、按 task 数自动计算完成率、独立探索子系统、强制探索阶段、自动排期或资源优化引擎。

不自动采集全聊天，不把推断或讨论自动升级为正式需求，不建设专门知识平台；在用户授权下整理已有权威需求、形成候选计划仍属正常能力，不在禁止范围内。

不建立关联审批、需求撤销审批或第二套模型裁决。不默认自动承担历史修复、恢复 retired 目标或生成清理 task；确有当前影响且已有授权时，仍可正常准备必要修复／清理任务。

不增加任意 Markdown 兼容层、全文件自动重排、全磁盘路径搜索、强制全项目迁移、实时协作、业务语义自动合并、跨文件强事务，或对任意外部编辑器的绝对 CAS 承诺。

## 4. 阶段 A：修复六项已知问题

### 4.1 原审核问题与对应关系

以下“已复现”是原审核的状态。本方案复核了关键源码路径，但没有重新运行这些用例；实施者必须在实际基线建立本轮证据。

| 编号 | 原优先级与事实 | 关联场景 | 主要接入位置 |
|---|---|---|---|
| F01 | P1：`content` 整文件路径绕过局部路径的稳定身份、dismissed 恢复和 v1 显式迁移保护 | S01、S03、S08、S10、S13 | `writer.ts` 的候选生成与写前差异检查 |
| F02 | P2：同样来源从 `[A,B]` 换成 `[B,A]` 被视为新依据，恢复 dismissed | S09、S10 | `writer.ts` 中 links／task_bindings 的依据比较 |
| F03 | P2：仅 `remove_fields:["assessment_id"]` 而无 metadata 时删除不生效 | S07、S13 | `writer.ts` 的 metadata 补丁处理 |
| F04 | P2：登记文件缺失没有准确诊断，目录联接跳过后仍可能 `coverage.complete=true` | S01、S07、S12、S13 | `paths.ts`、`catalog.ts`，按实际需要联动 `references.ts`／CLI／离线结果 |
| F05 | P2：授权的合法整文件候选修复未知字段，被误判为修改无关坏条目 | S13 | `writer.ts` 的受影响条目判定和降级保护 |
| F06 | P2：局部 body 内普通二级标题使后续约束落到需求外，保存成功却回读缺失 | S11 | `writer.ts` 的正文候选校验，复用 `parser.ts` AST 定位 |

### 4.2 统一写入校验，而不是叠加入口特例

目标处理顺序如下；函数名和内部对象按现有代码组织，不要求建立新的公共框架：

```text
明确输入与已读版本
  → 读取 original，核对路径和 expected_sha256
  → 识别已有文档版本；检查本次是否明确 migrate:"v2"
  → 根据 content / updates / append 形成候选
  → 解析 old 和 next，识别实际受影响条目与可定位范围
  → 统一检查身份、历史关系、正文边界和局部降级规则
  → 验证被修改条目及本次新增的文档级错误
  → 重新核对版本，沿用安全发布
  → 返回实际保存结果与诊断；宿主按范围回读
```

manifest 沿用它自己的 schema／路径校验；不要把产品条目字段规则误施加给 PRODUCT 入口。新建检查目标确实不存在；旧文件不因换成 content 就跳过版本与历史保护。

**受影响范围不能仅由输入形式推断。**局部 updates／append 有选定范围，但仍要核对解析后的实际效果；整文件候选需识别实际改变的条目，不能把 `affected=null` 解释为“没有条目被明确选择”或“所有保护可以跳过”。

已知同 ID 的 type 不得被普通更新挪用。合法修改同一目标／需求的正文应继续支持，不能因为稳定身份就冻结业务内容。拆分／合并保留旧身份和去向；整文件删旧添新不能默认为等价重命名或自动继承历史。

保留现有权限内的明确纠错、删除和迁移路径，不能为了防绕过而永久禁止删除、整文件写入或修复坏字段。已有明确选择可直接复用；不要再为每个条目要求确认一次。不能增加一个含义无限的 `force` 开关作为绕过所有保护的出口。

默认优先复用现有请求协议。若原始文件的身份或 AST 位置损坏到确实无法安全定位，只阻止本次无法安全完成的操作，保留原始字节和诊断，使用既有授权下的原文修复途径；不扩大为项目禁用。只有验证出当前协议无法表达必需行为时，才作最小契约调整，并同步 schema、API、分发及兼容说明。

### 4.3 F01 与 F02：历史及 dismissed 保护

`content`、局部 metadata 和 append 等相关写入路径应使用同一组 old→next 保护语义。校验覆盖 links 和 TaskBinding，不只修其中一类。

来源比较采用确定性规范化：对象属性顺序不影响意义；此处证据来源集合的换序和重复成员不构成新依据。不要全局排序所有数组，计划工作项数组等仍有展示顺序语义。规范化不能自动读取网络、修改原文、合并不同来源范围或重写用户字节。

新增来源、文件 hash 改变只能说明可能有新材料，不能直接证明原否定已被业务上推翻；来源排序、格式差异、同义改写理由尤其不能单独作为恢复依据。语义复核由当前宿主 Agent 完成，在既有授权内保留理由和可定位依据。

**用户明确改变原决定，本身可以构成新依据。**不应要求用户必须找来一份新的外部文件才能重新关联。按既有 SourceRef 表达当前明确决定，保留原否定及这次改变的依据；历史原文中的授权不能冒充本次授权。

默认重试应保留 dismissed。对于更换 link ID、先删后加、同目标同关系重新插入等明显等价的绕行，应核对现有确定性身份规则并补直接可判定的回归；语义近似但无法确定等价的关系由宿主判断，不为此建设全局语义墓碑系统。明确纠错或用户要求删除仍按实际授权处理，不把历史保护变成永久保留义务。

验收至少包含危险操作被拒绝和合法重新关联可完成两个方向。

### 4.4 F03：独立删除 optional 字段

metadata 的合并与 remove_fields 的执行分开处理；仅有 remove_fields 也应计算新 metadata、构造补丁并进行校验，不要求调用方额外提供空 metadata。

明确本次输入语义：沿用现有“先合并 metadata、再删除指定字段”的顺序；同字段两处出现时删除生效，避免不确定结果。必需字段删除按现有 schema 拒绝，id／type 不允许通过删除绕开身份保护。

删除不存在的可选字段可合法返回 unchanged；删除存在字段后返回 saved，并回读确认字段消失。删除 assessment_id 只撤销展示入口，不删除历史 assessment、不把当前交付状态写成已通过。

### 4.5 F05：允许明确修复，保留无关坏条目

用稳定 ID、可可靠定位的 AST 区域和实际 old→next 差异识别选中的坏条目。已授权整文件候选将该条目的未知字段删除、结果合法，应当允许保存。

同文件其他未选中且未修改的坏条目，保留原正文及 YAML 区域字节，继续报告局部不可用，不能顺手删除、修正文案或用新模板重建它们。整文件候选仍可保留未修改坏条目，不能把“所有条目必须合法”作为修一个条目的新门槛。

原始文档级错误造成无法可靠定位时不得猜测；候选不能新引入根级歧义或重复身份。修复路径仍必须通过 F01/F02 的历史保护以及路径、版本和迁移校验。

### 4.6 F06：正文边界与实际落点

局部 body 按现有 API 包含所选条目的 `## [ID]` 及必要三级章节。复用 Markdown AST 确认写入不会产生第二个真正的顶层二级标题，或借未闭合结构吞掉后续条目；真实修改结果必须仍属于所选条目。

普通二级标题导致正文越界时，拒绝本次局部写入并指出边界；由 Agent 按已有约定改成三级章节或明确调整结构。不静默降级标题、不丢弃尾部文字、不扩大到整份文档重排。

代码块、引用、列表中的伪标题不能被正则误判为边界。正常整份文档的附录规则仍保持，不得因为限制局部 body 而禁止文件中的所有普通二级附录。

保存后的回读用于核对真实效果，不可把“先写坏、再读出错误”当主要保护。保存前即检查解析后的 selected body、身份及未受影响相邻条目；换行比较只做既有契约允许的归一化。

### 4.7 F04：覆盖报告必须说明读到了什么

保持三种结论独立：

- 请求范围内的枚举／字节读取是否完整；
- 业务盘点是否在所列资料范围内完成、仍有哪些未核对资料；
- 特定需求、特定实现对象的交付／验证结论。

不要以一个 `complete` 值代替三者。已有 `coverage.complete` 继续只描述明确的读取范围，配合 omitted、diagnostics、usable／invalid 等结果；优先复用现有字段，不无故升级公开文档协议。

明确登记或本次明确请求的文件不存在、读取失败、相关目录无法进入、相关 symlink／junction 被跳过、枚举或字节预算耗尽，都必须记录实际未覆盖范围，不能仍报告该范围完整。遗漏可能只是目录或模式而不是已知文件名，应保留已知的路径／范围，不虚构里面有多少文件。

将“遗漏影响完整性”与“立即停止后续枚举”分开：一个路径读不到不应无故使其他可读独立路径全部停止；达到硬预算才按其边界停止并标出剩余未知范围。

明确排除和未选择的范围不等于读取失败，但不得包含在“已经完整检查”的声明中。glob 在已成功枚举的有效范围内零匹配可为合法空结果，不要与明确文件丢失混为一谈。解析到坏条目可以是字节读取完整、结构部分不可用，必须保留相应区别，不用“任何 warning 都 complete=false”替代语义设计。

source_paths 是引用读取许可，不是扫描任务；不得为了完整率递归扫描全部来源。只有本次选定或实际解析的来源，才分别报告其读取情况。选择性 paths 读取不证明全项目引用都完整；资料缺失也不意味着关联目标不存在。

保留原路径权限边界、排除优先、symlink／junction 跳过策略和有界读取。CLI、离线消费者和 Skill 对相同缺口的解释应一致；必要时补 schema 结果说明和消费方回归，不修改无授权的 TraceLens 仓库。

### 4.8 并发、部分失败和重试

保留当前工作副本根标识和 project_id，不拼接不同 worktree 的未提交内容。保留 expected_sha256、manifest 范围检查、短 I/O 协调和单文件安全发布；不声称它们消除了所有外部编辑器竞争。

冲突后不盲目原样重试，不覆盖用户字节；重新读取当前内容，重新计算仍需变更的部分。task 已创建但绑定失败，只重试绑定；capture 已成功但摘要失败，复用真实原文；不重跑业务命令来取得维护回执。

跨文件部分保存逐文件报告。失败不能被外层 saved 或 exit 0 隐藏，但也不能把已成功结果倒写为失败或擅自回滚用户修改。保留并回读必要 preimage；不建立全项目自动快照树或后台记录系统。

## 5. 阶段 B：13 类业务场景的实施与验收矩阵

每项都先核对当前实现和现有 references。已满足的能力保留并补最小充分证据；缺失时按最小位置补行为。以下矩阵不是要求新增 13 个命令、Skill、schema 类型或持久自动化测试。

### S01：目标演进和经营结果材料

业务例：在线文档产品从扩大注册量转为提高试用转付费。保留仍有价值的注册简化，延期邀请奖励，新增试用引导；已经存在的分享代码不因为目标变化而被声明已删除。

实施：Agent 区分同一目标的口径／数值调整与实质不同目标的替代；在 goal、requirement、change 和计划中保存当前意图、依据及直接影响，不机械地每次变化都分配新 ID，也不挪用旧身份。经营结果材料使用 goal 既有正文、sources 和必要 change 引用，记录材料中的时间、范围及口径，未知项保持未知；不新增 KPI 类型，不将 requirement-only 的 assessment 强行套给 goal。

验收：变更目标后仍能解释保留、退出和新增范围；目标结果材料可定位；task 关闭或功能已交付不能变成“转付费目标已达成”。不做自动统计、增长归因和实验平台。

主要 VPM：02、03、04、06、09、10、24、25。主要位置：`references/update.md`、`references/reconcile.md`、`references/plan.md`。

### S02：退出范围与仍然存在的共享风险

业务例：优惠券退出首发，支付与退货保留。优惠券叠加失败可以作为历史未解决事实保留；若暴露共享金额计算错误，仍要核对支付／退货是否受影响。

实施：区分延期、取消和完成；更新 scope、工作项安排及变化依据。历史失败不删除，退出范围不要求先修失败；识别仍影响 current 范围的共享问题，必要时纳入局部对账及后续工作。需求取消不等于代码已删除，计划变更不自动处置在执行 task。

验收：优惠券可以合法退出，不被历史失败阻断；当前支付风险仍可见；没有自动清理任务、全项目修复要求或撤销审批。确需清理且已授权时正常创建工作，不把“不自动”解释为永远禁止。

主要 VPM：03、04、06、08、09、12、25。位置：update／reconcile／plan references。

### S03：拆需求与拆实施工作的区别

业务例：“预约改期”先分时段校验、通知、费用处理三批实现；只有在独立业务定义确实需要时才把通知、费用处理拆成独立需求。

实施：先决定只是 work item／task 分解，还是需求本身拆分。前者保留一个 REQ，后者保存新条目和原条目的 derived_from／replaces 等既有关系及当前范围。合并同样保留历史来源，不复制多份当前正文。

验收：一个需求可有多个工作项及真实 task；旧 task 内步骤可以 task_id＋step_id 引用；拆分后的交付按范围核对，不向所有新需求机械复制旧 PASS。程序不判断“最佳拆分粒度”。

主要 VPM：04、07、08、12、24、25。位置：plan／update／reconcile references；确定性规则复用 plans.ts、writer.ts。

### S04：多对多和范围化关联

业务例：一个权限改造 task 同时实现接口权限校验，并为客户审计提供操作人字段；它没有完成全部审计查询与导出。

实施：各 owner 下保存 TaskBinding 的 role、coverage、来源及 plan_items；不维护中央重复绑定库，不在 plan 双写 task 状态。允许无 REQ 的维护／探索工作，不为关系完整虚构需求。

验收：同一 task 对两个需求的作用可分别解释；完成 task 不使未覆盖审计需求自动达成；无按任务数完成率、贡献比例或工时分摊。

主要 VPM：07、08、12、24。位置：plans.ts 与 plan／reconcile references，优先复用现有能力。

### S05：未知—探索—调整计划

业务例：先验证设备断电后能否恢复待同步日志，再细化离线同步方案。

实施：允许受限 exploration／verification task，未来 work item 暂无 task 身份、保留 outcome、scope、未知项。探索得出当前方案不可行，也可能完成探索目标；相应更新设计／计划，不把探索完成当成产品需求交付。

验收：可在未知下推进受限探索，后续计划按结果调整；简单明确需求不被强制加探索阶段；没有伪造未来 task_id 或新增研究状态机。

主要 VPM：05、07、08、24、25。位置：plan／reconcile／update references。

### S06：临时工作纳入、优先顺序与真实前提

业务例：客户上线前插入审计导出，推迟报表优化；导出前必须有可靠操作记录，而“客户更着急”只是排序理由。

实施：复用稳定 work_item_id，新增 origin=added 和变化依据；更新 deferred／withdrawn 等安排，不重编号。区分 depends_on.kind=order 与 prerequisite；先后位置不自动形成依赖。

验收：新旧安排、被推迟范围和理由可回查；在执行 task 的实际状态仍来自 assistance；文档不自动 close／adopt／focus，也不从 task close 推断工程前提满足。无自动排期或资源优化。

主要 VPM：06、07、12、24、25。位置：plans.ts 与 plan reference。

### S07：E6 外部失败、插入修复和复验闭环

业务例：E6A 导入、E6B 处理已结束，E6C 未开始，用户无 task 的真实数据验证发现失败，需要 E6R。

实施：接纳原日志／选定文本／明确用户报告，不要求补验证 task。区分用户报告与 Agent 复现；按需求范围、输入及实现版本核对原 PASS 和新失败。用 pending_sources 或新／更新的范围化 assessment 表达当前待核对；原报告保留，不机械混合不同对象结果。

E6R 使用既有真实 task 流程，绑定当前需求、问题来源、plan item 和历史修复范围。脚本由 E6A 实施不证明缺陷由它引入。不重开 A/B，不替换 C，不把修复 close 当复验通过。C 的受影响部分依据真实前提安排，不受影响部分可在既有授权内继续。

验收：取得观察、原文保存、规范保存、task、绑定、复验及摘要分别回读；需求定义摘要不变时新反证仍可见；task 创建后绑定失败的重试不重复 prepare；新输入格式要求与原缺陷能区分。E6A/B/C 如原是步骤，不强制改成独立 task。

主要 VPM：07、08、09、10、12、14、24、25。位置：reconcile／plan／recovery references 与既有 task 接入；不改 task reducer。

### S08：历史归属与当前修复范围

业务例：新版 Excel 导入复用了旧 CSV 金额解析函数，当前修复服务新版格式，旧 CSV 需求已 retired。

实施：分别记录旧实现归属与当前有效目标；保留 retired 侧历史引用，建立当前侧 scope 清楚的修复绑定。若仍有明确兼容维护要求，应依据现有意图澄清或调整当前范围；纯历史且无当前影响、无维护授权的缺陷可以只记录。

验收：当前修复不自动恢复旧目标、不强制重开旧计划/task；retired 标签也不能掩盖当前明确支持义务。无默认“全部历史问题必须修”。

主要 VPM：03、07、08、09、12、25。位置：reconcile／plan／update references。

### S09：选择性讨论收存、多议题与局部采纳

业务例：一次访谈讨论云同步、错误提示、多设备，本期只采纳错误提示。

实施：原文按实际取得内容保存一次，按片段整理多个议题；关联用 declared／inferred 和可定位依据。保存、关联、确认关联、采纳分别处理；未采纳不一律等于否定，否定也不退回普通候选。无可用模型或无匹配时保留原文及未整理范围。

验收：只有选定观点进入正式需求；其他议题保留正确地位；原文无重复复制、未知日期和作者不补造；归档中的指令不执行。讨论维护不是普通开发或简单需求变更的前置条件。

主要 VPM：16～23。位置：discussion／recovery references，复用 capture 和来源结构。无全聊天采集、自动正式需求生成或新知识平台。

### S10：否定持久与合法重新关联

业务例：用户否定“云同步讨论属于当前离线需求”，重新整理相同材料时不得恢复；后来用户明确改变决定，则仍应有合法路径。

实施：完成 F01/F02，并在 discussion 和 recovery 写明重试读取 dismissed、依据检查和当前授权解释。否定按具体片段、对象和关系范围处理，不扩成全项目关键词禁令。

验收：相同材料换序、更换属性顺序等不复活关系；用户明确改变决定及真实新增依据的合法路径可执行并保留历史；不存在额外模型服务或关联审批体系。

主要 VPM：12、14、18、21、22。位置：writer.ts；discussion／recovery references。

### S11：长需求约束不丢失

业务例：为设备需求补充“不得上传设备原始数据，诊断同样遵守”。

实施：完成 F06；正常采用三级及更深业务章节；宿主回读确认约束属于目标条目。手工编辑把明确用户限制写进附录时，Agent 不能因为结构未归属就忽略，应报告并在授权内维护。影响核对按真实含义覆盖同步／诊断／日志，不自行扩大成禁止一切联网。

验收：合法约束可保存并被条目回读；越界 body 被拒绝且原文件不变；无静默截断或全文件重排；代码块等伪标题仍合法。

主要 VPM：01、04、05、09、11、14。位置：writer.ts／parser.ts；update／recovery references。

### S12：多 worktree、冲突及安全重试

业务例：A 调整导入、B 调整报表，且用户在 Agent 读取之后修改文件。

实施：完成 4.8 的范围化恢复路径并验证现有工作副本标识；不按 project_id 或文件时间戳合并未提交内容，不把无文本冲突等同于无业务冲突。

验收：过期写入被已实现的版本检查检测时不覆盖；冲突不清掉已建 task 或已存原文，重试只补剩余动作；清楚记录任意外部编辑器竞态限制。无自动合并、跨文件事务和实时协作扩张。

主要 VPM：12、14、15。位置：catalog.ts／writer.ts；recovery／plan references。

### S13：手工修改、局部修复、缺失诊断及真实结果

业务例：用户加入未知字段后要求删除，又移动了登记文档；另一登记目录是 junction。

实施：完成 F03/F04/F05；合法手工编辑直接接纳，坏条目局部降级，授权修复可执行；移动后可在已授权、已知读取范围定位稳定身份或更新明确路径，不全磁盘追踪。未知位置保持未知。

验收：可读条目不被坏条目拖垮；删字段后实际消失；原证据和未修改条目保留；漏读不冒充完整；不因修格式恢复旧业务意图；v1 读取不强制迁移，写入按显式迁移规则。

主要 VPM：01、10、11、12、14、15。位置：writer.ts／paths.ts／catalog.ts，按需 references.ts；recovery／inventory references。

## 7. 验证设计：正反行为及证据层次

### 7.1 六项缺陷的最小正反配对

| 问题 | 必须拒绝／准确失败 | 必须允许／准确成功 |
|---|---|---|
| F01 | 普通整文件候选挪用 ID/type；无新依据恢复 dismissed；v1 未带 migrate 写为 v2 | 原授权内合法整文件正文更新；显式迁移选中文件；普通合法局部更新 |
| F02 | 来源换序、重复相同来源、对象属性换序作为“新依据”恢复关系 | 记录当前明确用户改变决定或经核对的新依据后合法重新关联 |
| F03 | 删除 id/type；删除其他必需字段后结构不合法 | 无 metadata 的 optional 字段删除；字段不存在时正确 unchanged；assessment_id 消失但原 assessment 保留 |
| F04 | 指定缺失文件／未读相关目录仍声称范围完整 | 已成功枚举的有效 glob 空集合；明确排除范围；范围内正常读取；部分失败后其他独立来源仍可读 |
| F05 | 借修一个条目改写无关坏条目或绕过身份／迁移保护 | 合法完整候选修已选坏条目；其他坏条目原字节不变并继续报告降级 |
| F06 | 局部 body 用真实二级标题使尾部逃逸、吞邻项或改变目标身份 | 三级业务章节、代码／引用中的伪标题、合法文件附录及相邻条目不变 |

不要把这个表硬编码成固定数量测试。合并共用夹具、参数化共享输入差异，保留对本次实际漏洞有保护价值的断言。仅为文案或函数名添加 contains 测试不能代替行为测试。

Windows junction 必须在支持环境中取得相应证据；Linux symlink 通过不等于 Windows junction 已验证。环境无法执行时明确标未验证，不擅自取消路径安全规则，也不把跳过算通过。

### 7.2 业务场景可合并成四条验收流

| 验收流 | 可覆盖场景 | 重点 |
|---|---|---|
| 目标与计划演进 | S01、S02、S03、S05、S06 | 当前意图、共享风险、拆分层次、探索结果、插入及延期 |
| 交付与 E6 修复 | S04、S07、S08 | 多对多范围、外部反证、历史归属、真实 task 与复验 |
| 讨论与用户决定 | S09、S10 | 选择性原文、多议题、局部采纳、否定重试、合法改变决定 |
| 故障恢复与约束维护 | S11、S12、S13 | 正文边界、并发、坏条目、缺失资料、幂等重试 |

上述四流是组织材料的建议，不是四个必须新建的长期测试框架。必须保留 S01～S13 的覆盖映射，不能因为合并就漏掉某个分支。

确定性脚本可准备夹具和断言保存结果；不能由脚本直接填好“业务判断答案”后宣称宿主模型已经理解。至少实际运行涉及判断的宿主整理、更新、讨论和 E6 流程，记录真实工具调用和回读。可以在隔离合成业务项目中完成；不因此声称真实用户项目、其他模型或 TraceLens 页面都已验收。没有可用宿主验证条件时如实记录缺口，不把检查 references 的文字当替代证据。

所有合成来源和 task 示例清晰标为测试资料。需要 task 身份时在隔离环境通过真实 assistance 建立并保留返回值，不能把固定示例 ID 当实际执行结果。重复执行时只清理受控测试夹具，不扩大到用户 records 或业务目录。

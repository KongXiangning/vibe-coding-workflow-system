# 产品文档组织与 TraceLens 配套修订方案

日期：2026-10-16。状态：历史讨论草案，当前不执行；此前文件拆分方向的规范、Skill、模板和测试改动已撤回。

当前取向：保留既有文档布局和业务逻辑，优先讨论 Runtime 紧凑返回与按需读取。此前实测发现按条目读取仍返回大量全局信息，局部写入默认返回整份旧文件的 Base64，因此上下文问题不能仅归因于文档未拆分或 Agent 使用方式。该 Runtime 优化尚未实施。

以下保留原方案供回顾，不作为当前维护要求或后续迁移授权。原方案中报告去重／正文压缩超出纯文件拆分边界；拆分导致新的评估失配，也不能算作保持原结果的完成交付。LawAgent 与 TraceLens 均未按本方案修改。

## 1. 当前问题与已有基础

### 1.1 需要解决的问题

原契约允许一文件多条目和跨文件关联，但目录示例、通用模板及日常维护方法容易引导宿主持续追加到全项目总表。由此形成三个问题：

1. 完整需求和评估混合多个独立业务范围，局部维护需要读取大量无关内容。
2. 总览、实施状态、评估总表和专项报告分别保存详细事实，后续更新需要在多处同步。
3. 文件迁移涉及机器读取、历史证据和页面来源定位，仅把 Markdown 拆成几个文件不足以证明迁移完成。

LawAgent 当前托管目录的观察如下。大小为约数，只用于说明现状，不作为自动拆分阈值。

| 文件 | 当前内容 | 组织判断 |
| --- | --- | --- |
| `REQUIREMENTS.md`，301 KB | 29 项需求、功能点、边界、验收及大量关联元数据 | 优先按业务范围拆分完整定义 |
| `IMPLEMENTATION_STATUS.md`，214 KB | 29 项需求的详细功能点实施评估 | 优先拆分，并核对与专项报告的镜像内容 |
| `ASSESSMENTS.md`，98 KB | 29 项需求的评估与持续追加记录 | 详细报告归入对应业务范围 |
| `SCOPED_ASSESSMENTS.md`，70 KB | 15 条报告，涉及 6 个目标／需求及不同对象、范围 | 按实际评估范围组织；保留历史报告的独立身份 |
| `REQUIREMENT_PROGRESS.md`，49 KB | 19 项需求的产品实施启动状态 | 总览保留简短状态和链接，详细依据归入范围文档 |
| `PROJECT.md`，59 KB | 项目定位、需求导航、交付明细、历史任务映射和维护记录 | 压缩为总览，详细内容引用已有范围文档或原任务证据 |

已观察到案例、司法文书、证据专项报告与实施总表存在整段相同的验证／历史说明。相同段落提示需要核对镜像，不能据此直接认定两条 Assessment 可合并或删除。

`GOALS.md` 的总体／阶段目标、`PLANS.md` 的少量独立计划、`DESIGNS.md` 和 `CHANGES.md` 不因使用通用名称就自动判定违规。已有 `CASE_ASSESSMENTS.md`、`JUDICIAL_ASSESSMENTS.md` 等已经体现业务范围，可复用。

### 1.2 已有实现与本次补充

撤回前曾补充文档契约、maintain-project 入口及 inventory／update／plan／reconcile／recovery 指导、文档组织 reference 和模板提示。对应安装测试曾有 6 项通过；新增合成拆分场景验证了业务文件升级保留、条目身份、正文、历史 SHA 和离线消费。这些改动及新增测试现已撤回，原结果仅描述此前被撤回版本。

TraceLens 当前代码按 Manifest 登记路径发现文档，按项目和条目 ID 建索引，并已有移动文件后身份保持的测试。其完整页面、增量刷新、历史引用和报告处置在本次组织变更下尚未联合验收。

本次主要补充：各文档类型的职责边界、存量整理与报告去重的区别、历史路径保留规则、摘要变化处置、TraceLens 交接示例／整理提示及真实文档副本的联合回归。

## 2. 文档职责和组织规则

### 2.1 按业务语义确定边界

同一业务模块或独立能力的多个需求、功能点可以放在一份范围文件中。跨模块共享能力保留唯一正文，其他模块通过既有 links 和来源引用表达关系。文件目录只是组织方式，不自动创建 module、父需求或新的业务层级。

出现独立业务范围混放，或日常维护某一能力反复需要读取、修改大量无关内容时，应按范围整理。行数、字节数和条目数可以辅助发现候选，不单独触发拆分。保留跨模块的真实整体要求和组合验收，不能为了文件变小丢失这些义务。

### 2.2 各类文档的职责

| 文档角色 | 应保存的内容 | 组织方式 |
| --- | --- | --- |
| 项目入口 `PROJECT.md` | 定位、当前范围概述、盘点缺口、简短状态、导航 | 一个项目入口；不复制详细功能点、验收表、运行证据和任务历史 |
| 全项目需求／进度导航 | 需求身份、短标题、必要状态／缺口、正文和报告链接 | 按阅读需要保留；避免再建立多份相同导航总表 |
| 目标定义 | 总体结果、阶段结果、边界、既有目标关系及范围声明 | 总体／少量阶段目标可集中；独立能力目标随范围维护 |
| 需求定义 | 完整功能点、输入输出、边界、异常、验收、关系和绑定 | 按业务模块或独立能力拆分；不以进展替代完整定义 |
| 交付评估 | 某个目标／需求、范围、对象、时间下的结论与证据 | 按业务范围组织；同范围可容纳多条独立报告，定义与评估分文件 |
| 产品实施启动状态 | 用户已采用的实施安排／启动事实及其适用边界 | 总览简短表达，具体依据随相关范围；不等同于代码存在或交付满足 |
| 设计 | 方案、约束、取舍、实现差异 | 独立模块设计按范围保存；真正的整体架构可有项目级文档 |
| 实施路线图 | 已采用／候选工作安排、稳定工作项、前提和未决事项 | 允许项目级路线图与局部路线图；引用需求，不复制完整功能定义和证据 |
| 变更记录 | 真实变化的依据、前后含义、影响及未同步项 | 小规模项目可集中；跨多个独立业务且持续增长时按业务／阶段分组，保留跨范围变更的完整语义 |
| 讨论资料 | 选定原文、议题、关联与未决问题 | 按议题／业务范围命名；原文与当前正式定义分开 |
| 历史与验证材料 | 原字节、原报告、旧对象和迁移依据 | 通过来源引用读取，不成为第二份当前定义 |

“入口只保留摘要和链接”针对导航入口。总体目标、整体架构和项目路线图可以有其自身的实质内容，只要没有再次承载全项目详细需求／评估副本。

### 2.3 文件命名与目录

默认采用“业务范围＋文档角色”，例如 `FILE_INGEST_REQUIREMENTS.md`、`FILE_INGEST_ASSESSMENTS.md`、`CONTRACT_REVIEW_DESIGN.md`。沿用项目已有语言和命名习惯，中文范围名同样可用。名称表达稳定业务含义，评估日期和适用对象仍由条目元数据承担。

平铺和子目录均合法。项目较大时可使用以下结构，按实际内容创建文件，不预先生成空模块和空报告：

```text
docs/product/
  PROJECT.md
  GOALS.md
  IMPLEMENTATION_ROADMAP.md
  modules/
    file-ingest/
      FILE_INGEST_REQUIREMENTS.md
      FILE_INGEST_ASSESSMENTS.md
    contract-review/
      CONTRACT_REVIEW_REQUIREMENTS.md
      CONTRACT_REVIEW_DESIGN.md
      CONTRACT_REVIEW_ASSESSMENTS.md
  discussions/
  history/
```

模板文件 `REQUIREMENTS.md`、`ASSESSMENT.md` 表示语法格式，不规定目标项目的实际文件名。模板提示应按文档角色编写，避免把目标、变更和讨论模板都机械引向需求文件名。

## 3. Manifest、身份与证据兼容

### 3.1 当前定义和历史读取分别登记

`managed_paths` 只纳入当前规范条目；`source_paths` 允许按引用读取必要历史。`docs/product/*.md` 不递归包含子目录，采用模块目录时必须登记实际路径。

普通迁移可登记已采用的入口及范围目录，例如：

```yaml
managed_paths:
  - docs/product/PROJECT.md
  - docs/product/GOALS.md
  - docs/product/IMPLEMENTATION_ROADMAP.md
  - docs/product/modules/*/*.md
  - docs/product/discussions/*.md
source_paths:
  - docs/product/history/**
  - docs/product/discussions/raw/**
  - docs/evidence/**
```

示例中的具体文件只在实际存在并采用时登记。修改已有 Manifest 时保留其他仍有效的登记、源目录、维护状态和排除约束，不以示例整份覆盖。

**前一版指导需要修正：不能使用 `exclude_paths` 让一个仍需读取的历史文件退出当前定义。** 两端读取器的排除规则也作用于来源读取。若旧原件必须留在原路径，应缩小或细化 `managed_paths`，并将该旧路径登记到 `source_paths`；它不能同时被全局排除。已有排除约束不能为了迁移被静默放宽。

旧总表改为导航后，若仍命中 `managed_paths`，保留原支持版本的合法头部及 `items: []`；如果移出托管，则可作为普通 Markdown 导航。唯一 project 条目继续位于 Manifest 的 entry 文件。

### 3.2 文件拆分保持业务身份

纯组织迁移保留 project_id、item ID／type、Schema 版本、功能点编号、完整业务定义、关系及其否定历史、TaskBinding、需求顺序、目标范围声明、评估选择、计划／工作项身份和既有基线。

不因文件拆分新增或退休需求，不创建 replaces／derived_from，不改变 Task 状态，不把已存在的基础代码解释为产品已启动或完整交付。Schema 升级与业务重判只在另有实际需要时处理。

### 3.3 当前链接和历史依据使用不同迁移方法

| 引用类别 | 迁移方法 | 必须核对 |
| --- | --- | --- |
| 当前 Markdown 导航／无版本当前 SourceRef | 更新文件、锚点和必要定位信息 | 打开的是迁移后的同一条目 |
| SHA 固定的需求／目标依据或验证来源 | 保留原路径原字节，或在允许修改的引用中指向字节相同的历史副本 | SHA、原条目／章节／行号仍可解析；不能换成新文件再更新 SHA 冒充旧依据 |
| 不可变 Runtime 事件／冻结报告中的引用 | 保持原记录及其依赖字节；必要时旧文件留原路径，只退出当前管理 | 新旧读取均不把历史当成当前，也不破坏证据可达性 |
| 目录移动引起的正文相对链接 | 尽量选择少改正文的落点；必要调整时记录准确差异 | 链接目标语义保持，同时检查定义／报告摘要的实际变化 |
| v6 证据处置及路线图基线 | 保留原判断和原依据，验证其适用性 | 不自动刷新 checked_at、改写基线或把失配变成已处理 |

文件路径本身不决定条目身份，但正文参与定义摘要。相对链接文字改变可能导致定义摘要变化；v6 报告处置的摘要也包含部分元数据和正文，重定向引用可能影响复用。迁移应优先减少这类改动；确需修改时按现有对账语义处理受影响部分，并保留真实待核对状态。不得承诺所有组织迁移都能让所有摘要原值不变，也不得以消除提示为由改写旧评估事实。

## 4. 升级后整理既有文件的方法

### 4.1 触发和授权

安装／升级交付新的 Skill、契约和支持资源，业务资料仍由目标项目维护。用户要求“整理旧总表”“按模块拆分功能点”“按新组织规范迁移这些文件”时，maintain-project 使用同一子流程完成已授权范围；不为每个文件或字段重复索取确认。

只请求分析时返回候选分组、路径和影响。一般局部维护继续修改相应范围，不强制先迁完整项目。新增内容优先进入已有合适范围文件，避免继续扩大详细总表。

### 4.2 先拆分，再处理确认的镜像

第一阶段进行身份和内容保持的文件重组。第二阶段只处理已确认属于同一评估范围／对象、重复维护同一结论的镜像正文；当前入口缩减为摘要和链接，历史原文保留。

不同 ID、时间、目标、输入、对象或适用范围的 Assessment 不能只因正文相似就合并。需求实施启动状态与历史局部交付是不同事实；旧报告被新报告选择替代，也不等于旧身份可以删除。缩减报告正文可能改变 v6 处置依据，须在对应范围核对后如实保留结果。

### 4.3 操作顺序和恢复

| 阶段 | 操作 | 输出或完成条件 |
| --- | --- | --- |
| 读取与分组 | 读取选定文件、Manifest、必要引用和冻结约束；按业务范围分配原条目及正文细项 | 可审阅的旧路径／ID／锚点到新位置映射；未读、歧义及冻结范围明确 |
| 保留依据 | 保存实际原字节与摘要，确定需要留在旧路径的文件 | 恢复副本可读取；历史来源的可达方式明确 |
| 准备候选 | 生成完整范围文件、简短入口、当前链接和 Manifest 候选 | 候选解析通过；条目集合、元数据、正文和必要定位差异可比较 |
| 发布重组 | 在核对并发变化后逐文件保存并切换实际管理范围 | 每一步有已保存／未保存事实，未发生静默覆盖 |
| 回读和续作 | 从磁盘重新读取，核对身份唯一、引用、摘要和评估选择 | 失败只补未完成部分，成功部分不重复迁移或执行原业务工作 |
| 镜像整理 | 对已确认镜像保留历史并压缩当前摘要 | 详细事实归属明确，独立历史报告和原选择不丢失 |

迁移映射和进度是本次整理的恢复材料，保存在既有获授权位置；完成后作为历史，不建立新的长期功能数据库或第二套当前登记表。

现有 helper 的 apply 以单文件为保存边界，并拒绝跨当前文件重复 ID；它不是跨文件 move 事务。准备候选后可使用正常获授权宿主工具进行重组，配合原文保留和并发字节检查。多文件切换中可能短暂出现重复或缺失条目，迁移未结束时不能宣称基线完整；不新增全局锁或 Runtime 审批状态机。TraceLens 应显示已观察到的不完整状态，迁移完成刷新后恢复一致结果。

若冻结、引用保护或并发修改使某部分无法安全迁移，保留该部分原状并说明具体原因，独立部分继续；不能通过改名、重新编号或扩大路径权限绕过约束。回退只恢复属于本次迁移且未被后续修改的文件，先核对最新字节，避免覆盖用户的新工作。

## 6. TraceLens 配套范围

### 6.1 已有能力和需验证部分

| 消费环节 | 已有基础 | 本轮要求 |
| --- | --- | --- |
| 文档发现 | 根据 Manifest 登记路径枚举 | 验证平铺／模块子目录、明确文件、空导航和排除规则；不能固定文件名 |
| 条目身份 | 项目／工作副本命名空间加 item ID，已有移动身份测试 | 迁移后保持需求、目标、报告、工作项的原身份和选择入口；重复 ID 仍诊断 |
| 关系与顺序 | 按 links、requirement_order、绑定和工作项关系构建 | 文件数量和目录顺序不改变业务关系、展示顺序或 Task 贡献 |
| 原文与证据 | 读取实际来源路径、SHA 和条目／章节／行号 | 当前来源跳转到新位置；固定历史来源仍打开原字节和原范围 |
| 报告选择与处置 | 根据声明范围、对象和定义依据判定 | 拆分不凭新时间或新路径替换报告；失配和未核对继续可见 |
| 增量刷新 | 文件树指纹包含 Manifest、登记路径和来源 | 文件增删／移动及 Manifest 改动后消除旧条目；正在打开的详情可恢复或提示失效 |
| 文档中心与整理提示 | 读取项目导航，生成面向宿主的整理提示 | 更新导航／Profile 的实际入口；提示采用范围文档和唯一正文，避免重新生成总表 |

依据当前代码，尚无证据表明必须重写 TraceLens 核心模型。先补有针对性的消费测试，遇到实际失败再修正读取器、索引、来源导航或刷新链路。

### 6.2 具体代码和文档接入点

- `src/server/product-reader.ts`、`product-index.ts`、`product-parser.ts`：路径枚举、跨文件解析、唯一身份和关联。
- `src/server/tree-fingerprint.ts`、`snapshot.ts`：新增／移除文档及 Manifest 更新后的刷新结果。
- `src/server/product-markdown.ts`、`src/web/product.tsx` 及来源组件：正文链接、当前来源与历史来源定位。
- `src/shared/evidence-dispositions.ts`、相关评估选择／路线图逻辑：仅在具体摘要或引用变化时验证降级和复用。
- `src/shared/organization-prompt.ts`：同步组织原则，继续由 vNext 执行业务文档维护；不在 TraceLens 建立第二个迁移写入入口。
- 复用 product-reader、product-index、reference-rendering、incremental-refresh 及产品浏览器场景承载必要回归；具体增加哪些测试以缺少的行为覆盖为准。

## 7. LawAgent 迁移建议

LawAgent 用作真实结构的验证对象，先在隔离副本中演练。以下分组为文件组织建议，不是新增业务分类或采用需求关系；实际迁移以正文和现有关系核对为准。

| 建议范围 | 主要归入内容 |
| --- | --- |
| 知识底座 | 稳定身份、来源／版本、共享注册与治理能力 |
| 文件入库 | 转换、批量导入、自动编排、校验及恢复 |
| 采集平台 | 控制面与来源采集；来源能力需要独立维护时再细分 |
| 法律法规／案例／司法文书 | 沿现有独立需求与专项报告分别组织 |
| 证据与历史复现 | 精确证据、可信等级、引用和复现要求 |
| 投影与检索 | 按现有独立能力分别维护投影、安全重建、多路召回及解释 |
| 合同审查 | 合同解析、条款理解、关联、风险、复核、工作台、报告等；按实际独立边界继续分组 |
| 企业知识与学习 | 标准条款、企业历史、内部规范、反馈和学习；保留各项当前／后续／候选状态 |
| 横向约束 | 安全、管理、性能与可靠性等独立义务，其他范围引用 |

优先处理 `REQUIREMENTS.md`、`IMPLEMENTATION_STATUS.md`、`ASSESSMENTS.md`；同时修复直接依赖这些文件的 PROJECT 导航和报告引用。随后按业务／对象整理 `SCOPED_ASSESSMENTS.md` 和 `REQUIREMENT_PROGRESS.md`。已体现范围的专项报告优先复用。

总体目标可留在 `GOALS.md`。计划、设计和变更按其实际独立维护需要整理，不为了统一目录一次性改名全部文件。历史 Task 的执行、关闭、自审／独立审查和发布边界保持原义，原始资料不因迁移被删除。

实际目标项目迁移以对应项目的维护请求执行；本方案和本轮源码改动不构成已经升级或整理 LawAgent 的声明。

## 8. 联合验收

### 8.1 核心场景

| 场景 | 必须观察到的结果 |
| --- | --- |
| 新项目有两个独立业务范围 | 完整定义与评估进入范围文件；总入口简短；没有空模板冒充业务事实 |
| 在已有模块中增加功能点 | 更新对应文件及必要关联；不继续扩大全项目详细总表，也不强制一功能点一文件 |
| 旧总表拆分，原 ID 不变 | helper、离线读取器、TraceLens 对同一条目集合及顺序／关系的读取一致 |
| 采用模块子目录 | 正确登记后可见；未登记或登记失效时显示准确缺口，不宣称全项目完整 |
| 旧位置变为摘要导航 | 托管语法有效，无重复当前 ID；链接能定位范围正文 |
| 历史 SHA／章节／行号引用 | 保留的原件可读取，Hash 和定位均匹配；当前文件不冒充历史依据 |
| 不可变记录必须依赖旧路径 | 旧原件保持，只退出 managed 范围并仍可按 source 读取；不能被 exclude_paths 一并屏蔽 |
| 相对链接或报告元数据变化 | 观察实际摘要与适用性变化；保留真实待核对，不静默刷新旧结论或处置 |
| 存在镜像正文和独立历史报告 | 只缩减已确认镜像；独立报告身份、对象、时间和选择仍可用 |
| 迁移中断、并发修改、冻结文件 | 不覆盖新编辑或冻结内容；报告具体已保存／待处理，能依据磁盘状态续作 |
| TraceLens 在迁移前后刷新 | 迁移完成后无旧条目残留或重复；需求图、详情、Task 关联、报告及来源可正常导航 |
| 只升级软件 | 指导资源更新，目标项目业务原文、Manifest 和 Task 事实不被自动重组 |

上述场景可组合为少量有代表性的用例，不要求逐行建立测试，也不要求为文档重组重跑业务产品全部验收。

### 8.2 分层证据

1. **规范与生成一致性**：人工核对角色和引用语义，运行受影响生成及现有协议／源码契约检查，确认安装资源一致。
2. **生产与离线消费**：验证当前／旧格式混用、ID 和正文保持、真实历史字节、登记范围、部分迁移恢复。
3. **TraceLens 消费与页面**：在同一迁移夹具上核对数据结果，并用浏览器验证刷新、详情、关系、评估选择和来源定位。
4. **宿主实际执行**：在隔离项目中以自然语言请求让宿主按新版 Skill 完成一次新建和一次存量拆分，观察文件组织、引用修复、失败说明与回读；测试脚本直接搬文件不能替代这项证据。
5. **真实结构演练**：用 LawAgent 所选产品资料及必要本地引用的隔离副本比较迁移前后；只读取和整理文档，不运行其业务代码。未纳入副本的外部依据单列，不误报为迁移新损失。

用迁移前后差异判断结果：预先已有的缺失来源、未知结论和无效条目可以保留，但本次造成的新缺口必须解决或明确报告为未完成。不能以修复全部历史问题作为普通迁移的前置门槛。

## 9. 实施顺序与交付边界

| 工作包 | 交付内容 | 完成条件 |
| --- | --- | --- |
| A 规范收敛 | 完善角色表、命名、历史路径和摘要变化规则，纠正前版不适用表述 | 契约、指南和共享 reference 一致，无相互冲突的默认规则 |
| B Skill 与模板交付 | 更新入口／各子流程／模板及 TraceLens 交接说明，生成本地分发 | 新安装与升级包含指导，业务文件保持；分发与源码对应 |
| C 迁移演练 | 用合成项目完成身份保持拆分、历史原件读取及中断续作 | helper 与离线读取一致，实际保存和回读结果可复核 |
| D TraceLens 配套 | 更新整理提示，补消费／刷新／来源／页面测试，修复发现的具体缺口 | 同一夹具从读取到页面通过；无需新增文件格式分支 |
| E 宿主演练与真实结构验证 | 执行有限自然语言场景和 LawAgent 文档副本迁移 | 组织方法实际可执行；原事实保持，新增缺口及限制明确 |
| F 软件与项目交接 | 保存改动、分发来源、验证结果和目标项目整理入口 | 软件验证、真实项目整理、发布／安装状态分别说明 |

A、B 以前轮改动为基础完成增量；C 提供 D、E 共用的迁移样例。最终受支持的软件组合应通过联合验收后，再用于目标项目正式迁移。提交、发布和目标项目安装按实际工作请求执行，不由方案状态推断已完成。

交付完成要求：新建路径不再默认生成全项目详细总表；旧文件能在保留身份和历史依据的前提下整理；总入口简短；TraceLens 能正确发现、刷新、关联、选择报告和打开新旧来源；实际未完成范围可定位；软件升级不会自动改变业务事实。

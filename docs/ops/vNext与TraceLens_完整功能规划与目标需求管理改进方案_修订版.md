# vNext 与 TraceLens：完整功能规划与目标需求管理改进方案

> 修订日期：2026-10-11。修订主题：**完整规划当前交付范围，动态维护长期产品需求，按 Task 渐进实施。**
>
> 本文整合本次对话已确认的职责边界、功能点细化、需求顺序、Task 软关联、范围化成果判断和页面设计，替代上一版改进方案中与本稿冲突的内容。尤其不再把“默认只细化近期功能”作为当前交付范围的总体规划方法。
>
> 实现依据沿用上一轮已核对的固定提交 `fdc71a895663f33dc96c522ff81b5caa742879ff`，源码版本 0.24.6；此前比较范围为 `334580494634cbd88c60b62bcdf50345e1b0abe5..fdc71a895663f33dc96c522ff81b5caa742879ff`。本次是方案重整，没有重新获取远端 HEAD、重新审查 TraceLens 源码或运行代码测试，也没有修改仓库、创建 Task、提交、推送或升级项目。
>
> 方法定位：这是结合用户作为架构师的工作方式确定的产品取舍，不宣称某一种开发流程对所有项目普遍最优。本文的“功能点”指具体业务行为或能力，不是工作量计量意义上的功能点估算法。

## 1. 总体结论与本轮目标

vNext 的目标需求管理，应当具备产品经理和架构师用于整体规划的价值，而不只是伴随 Task 执行逐步积累条目。

对于已经明确当前交付范围的新项目、版本或用户约定阶段，默认先通过 `maintain-project` 协同用户系统分析该范围内的全部已知功能、重要异常、质量要求和必要约束，形成可审阅、可维护的当前需求基线；随后按 Task 分批组织实施。

迭代中新增正式需求时，先分析该次新增范围的完整功能与必要影响，用户采用后纳入当前基线，再由 Task 承接。尚未明确的原始意图可以先记录，不能因没有分析完就丢失，也不能冒充已经确认的详细功能。

探索性项目或确实需要实验才能回答的部分，允许先明确问题、候选和已有边界，通过探索补充事实，再完善要求。探索只改变相关不确定范围的处理，不成为推迟梳理其他已知功能的理由。

**完整功能规划是默认协作方法，不是 Runtime 准入机制。** 用户明确要求先实施、排障、探索或暂缓维护时，Task 仍可独立推进；已知管理缺口如实保留。

本轮交付应使用户能够：在实施前看清当前交付的整体功能范围；在实施中知道各项功能由哪些工作承接；在交付后理解哪些要求已满足、哪些有具体缺口、哪些尚无充分结论。

## 4. 职责与不可越过的边界

### 4.1 各主体职责

| 主体 | 职责 |
| --- | --- |
| 用户 | 确定业务意图、当前交付范围、采纳内容和例外安排；不需要逐项填写内部字段或重复确认已有决定 |
| vNext 的宿主大模型 | 分析与提出需求细化，依据真实决定维护文档，准备 Task，核对交付与当前要求的关系 |
| 文档与任务工具 | 保存真实身份、结构、来源与记录，处理既有校验、冲突和状态；不代替用户或模型作业务判断 |
| TraceLens | 读取和展示已记录目标、要求、关系、顺序、结论及 Task／Step；提供搜索、筛选、来源和历史下钻 |

TraceLens 不新增或修改需求，不采用建议，不调整任务生命周期，不运行模型重新判断业务，不提供拖动写回排序或“关闭 Task”按钮。视觉布局可改变，文档业务关系不因布局改变。

### 4.2 软关联

一个需求或功能点可以关联多个 Task；一个 Task 可以关联多个要求、只关联上层需求，或者完全不关联。

没有 PRODUCT、维护暂停、功能未细化、未关联需求、达成结论缺失、文档保存冲突或展示不可用，都不能单独成为 prepare、confirm、execute、close 或停止的条件。

Task 已确认而关联未保存，是合法的局部成功：保留 Task，只补失败的关联，不重复 prepare，不撤销 adopt，不把维护失败改写成任务失败。

真实必要的业务选择、接口或数据缺失，仍按实际影响说明。非阻塞不意味着假定真实前提满足；“图上连了一条依赖线”也不意味着 Runtime 应阻止执行。

### 4.3 完整规划与用户例外并存

产品行为应同时做到：

- 用户要求完整规划时，认真完成所选交付范围的分析，不能拿“Task 非阻塞”作不做需求分析的理由。
- 用户明确先做排障、实验、局部实现或暂缓规划时，尊重该安排，不能以功能清单尚未完成为由拒绝独立工作。

这两点是“默认方法”与“执行权限”的区分，不是相互抵消。

## 5. “完整功能规划”的范围和深度

### 5.1 完整的是当前约定交付，不是未来整个产品生命周期

当前范围可以是一个有明确边界的项目、版本、用户已约定阶段，或一项新增需求。只有项目确实存在分期时才使用阶段；不为界面自行制造第一期、第二期。

对这个范围，应系统考虑当前已知的全部功能，包含不是马上实施、但已经承诺在本次交付中的部分。长期设想或尚未采用方向保留未来／候选属性，不要求与本次功能达到相同精度。

总体目标本身仍是结果与边界说明，不是把所有功能点塞进一段目标正文。完整范围通过它与需求、子需求及约束的结构化关联共同表达。

### 5.2 “完整”不等于只有功能名称

针对适用业务，应把主要使用场景、输入输出、关键规则、正常行为、重要异常、数据与来源约束、接口组合及质量要求说明到足以进行业务审阅和后续 Task 规划的程度。

这些是分析视角，不是每个项目必须填满的模板清单。无关内容不制造要求；同一规则已经有权威文档时用引用，不复制一份。

### 5.3 功能定义与实现细节分开

编码前通常需要明确“本次交付应提供什么行为、在什么条件下怎样算符合要求”。具体函数组织、库内实现、性能参数调优及每个 Task 的 Step，不必在此阶段全部确定。

例如，可以先明确检索应保留约定来源定位、支持特定查询与评价条件；某个排序模型或参数的具体选择，可以通过有明确目标的技术验证完成。不能把未知参数伪装成既定方案，也不能因此不定义已知的检索功能。

重要架构约束和跨功能接口需要在规划中分析、引用和核对；本轮不新增架构审批状态机。

### 5.4 已知完整与真正未知分别说明

完整分析的结果应说明：读取和覆盖了什么；采用哪些功能与约束；明确排除哪些内容；还有哪些重要问题尚未决定、影响哪部分工作。

“已覆盖所有已读来源”不证明所有业务事实都已取得。请求范围内存在未读材料或尚未明确的必要功能时，准确指出缺口，不能宣称所有功能都已确定。

必要问题尚未解决时，其他已知部分仍可形成可用基线和实际工作安排。是否实施受影响部分由用户基于具体问题决定，不设置全项目完整性开关。

## 6. 业务结构与数据表达

### 6.1 主体模型

```text
项目总目标及当前交付边界
    ├─ 业务需求
    │    ├─ 具体功能要求
    │    ├─ 具体质量或异常处理要求
    │    └─ 按实际需要进一步细化
    └─ 必要的真实子目标或阶段范围
         └─ 相关需求与具体要求

任意合适层级的要求
    └─ 可选关联一个或多个 Task
         └─ Step 与原有执行、验证、审查、生命周期记录
```

这不是单父节点的强制数据树。一个要求可以服务多个目标，多父或多目标关系仍使用同一身份。结构上的支撑关系，不自动证明它穷尽上层全部要求。

### 6.2 功能点采用细粒度 requirement

复用 `type: requirement` 和现有正文：需求内容、范围边界、验收要求。子项通过 declared、active 的 `part_of` 指向父 requirement。

已经足够具体的需求不再强行增加同名子项。只有在独立说明、变化、关联或对账上有实际价值的内容，才建立独立条目；只是实施步骤或正文里的简短验收条件，不要求全部对象化。

不强制固定深度、数量、工时或“一点一 Task”。功能和质量要求均可成为末级节点，不凭“没有子项”自动认定节点类别。

### 6.3 父项与子项的内容边界

父项保留总体业务要求、范围、共性约束及组合使用条件；子项维护具体行为和条件。父项不复制每个子项的完整正文、Task 清单和达成状态。

细化当前要求时父项默认继续存在。只有用户实际决定替代、合并或退出，才调整旧范围，并保留身份和历史；`replaces`、`derived_from` 不代替当前 `part_of`。

### 6.4 定义、评估范围和结果分开

| 内容 | 现有表达及用途 |
| --- | --- |
| 目标与总体范围 | goal／project 的现有正文、来源和明确选择 |
| 具体功能及质量要求 | requirement 正文，必要时使用子 requirement |
| 当前组成和支撑 | part_of、supports；依赖另用 depends_on |
| 需求登记顺序 | project.requirement_order |
| 某项要求的当前评估范围 | 相应 goal.assessment_scopes；不等同全项目功能清单 |
| 已确认成果与满足结论 | 独立 v3 assessment，按 target／goal／scope／subject 定位 |
| Task 关联 | 既有 TaskBinding，保留覆盖范围、角色与来源 |
| 采纳、变化及未决内容 | 既有 change、sources、适用正文及必要 discussion；不要求保存整段聊天 |

结构关系不自动生成评估范围，评估范围声明也不自动新增结构关系。需要某项精确范围结论时维护相应声明，不要求为了建立功能清单立即给每个功能点创建 assessment。[S06][S07]

## 7. 默认协作流程

### 7.1 新项目或当前交付范围的完整规划

| 环节 | vNext 应完成的工作 | 实际输出 |
| --- | --- | --- |
| 确定范围 | 复用用户已给出的目标、场景和边界；只澄清真正影响业务的未知 | 当前目标与交付边界 |
| 整体分析 | 读取该范围的相关资料，系统梳理全部已知需求、功能、异常、质量与必要约束 | 可审阅的整体结构，而非下一批 Task 清单 |
| 交叉核对 | 检查遗漏、重复、冲突、接口与组合行为；区分确定内容和候选 | 明确的未决项、排除范围和影响说明 |
| 用户采用 | 展示足以审阅的业务结果，使用当前或已有效的明确决定 | 当前需求基线及采用来源 |
| 保存与回读 | 保存现有规范条目、关系及一份需求顺序；必要评估范围按需登记 | 实际已保存／未保存范围 |
| 分批实施 | 根据已确认功能、实际依赖和用户优先项准备接下来的 Task | 当前执行计划；远期 Task 无需预创建 |

正常协作以“先形成当前交付范围的功能基线，再进入批量实施”为默认方向。用户已经采用了充分明确的内容，不再要求对每个功能点逐条重复确认；讨论中的备选不能因用户采用另一部分内容而自动转正。

这里确认的是业务要求，不是新建 Runtime 审批。也不要求用户选择内部策略名、关系枚举或文件字段。

### 7.2 迭代中新增正式需求

先识别用户此次增加的业务结果和范围，再完整分析本次增量包含的具体功能、异常、质量要求及与既有能力的必要关系。复用现有要求，避免把重复实现批次当成新需求。

实际采用后，保存新要求或更新原要求，并核对真正受影响的设计与结论；新 ID 作为本批次追加，旧任务历史不改。然后按范围准备 Task。

不因为“是敏捷迭代”就把明确新增需求默认直接交给 AI 编码、以后再补功能分析。也不因新增局部需求重新规划全部无关模块。

若用户只是提出问题、想法或待比较方案，先保留原意和候选；未采纳前不伪称它已进入当前交付承诺。

### 7.3 用户明确要求局部任务或先实施

已经明确 Task 意图、无需全局分析即可开展时，直接准备和推进。读取相关已有要求，可提出有用的局部关联或缺口提示，但不强制先调用 maintain-project 完成全项目功能规划。

这条路径是正常可用能力。管理资料暂未完整时，不能以“本稿默认先规划”为由制造新的拦截。

### 7.4 探索性范围

当功能定义或技术可行性必须通过实验才能确定时，明确需要回答的问题、当前已知边界和结果如何影响正式要求。允许先做探索 Task，也允许探索 Task 没有需求绑定。

探索结果返回后，在授权内补充或调整相关功能定义。不能将被排除方案的探索成功等同于产品功能交付；也不能因局部未知让当前其他已知功能长期缺席整体规划。

### 7.5 进行中项目的接入与补齐

接入已有项目时，保留原要求、已交付能力、真实 Task 及来源。从用户请求的当前范围补齐整体结构，而不是只整理尚未关闭的任务。

缺历史材料就保留可定位来源与未知，不创造过去的创建顺序、采用时间或验收结论。后补的功能条目不会使历史实现消失，也不会要求重建或重开旧 Task。

## 8. 功能基线及其动态维护

### 8.1 基线的含义

本方案的“需求基线”是当前采用的功能定义、约束、范围和重要决定在规范文档中的一致集合。它可以演进，不等于永久冻结，不是新的配置对象或审批状态。

不要求新增 `BASELINE.yaml`、中央功能数据库或第二份权威清单。项目与需求现有文档可以承载定义，change 和 sources 承载采用及变化依据。

### 8.2 更新规则

新增本次交付功能，应先分析完整增量并更新必要要求；撤回某项义务，应明确其退出哪个范围并保留历史。只是细化原义、改名或文字澄清，不冒充新业务方向。

父项变化只处理实际受影响部分。一个共享需求退出某个目标，不等于从所有目标中删除。已明确未来范围不自动被计入当前缺口。

实现方案可以随着验证调整，但不能在没有授权的情况下缩减已约定功能；明确采用的需求变化也不能因为旧 Task 计划而被永久禁止。

### 8.3 不用审批计数代替业务理解

完整规划不等于每个条目都获得一个单独“已确认”字段。是否采用看真实用户决定与来源，工具的结构合法性不认证业务完整性。

用户采用一份整体方案，可以覆盖其明确包含的要求；不据此采用附带的备选或未决建议。重试只处理未完成保存，不重复要求用户确认已明确内容。

## 9. 需求展示顺序：继续稳定追加

使用一份项目级 `requirement_order`。首次按采用的分解顺序登记；后续新增批次仅追加新 ID，保留已有相对位置。

```text
原序列：            A — B — C
后续新增：          D — E — F
最终序列：          A — B — C — D — E — F
```

D 即使是 C 的前置条件，也不自动插到 C 前面。依赖、Task 状态、需求达成情况、文件时间和工作项顺序均不自动改变这一序列。

完整功能规划可以在第一次维护时登记本次已经采用的全部已知需求和细项。后续新增一项需求时，登记其新身份及新细项；不为增加细节重编号旧 ID。

例如已有 `R1、R2、R3、R4`，后来 R3 增加 `R3-A、R3-B`，项目序列为 `R1、R2、R3、R4、R3-A、R3-B`。展开 R3 时局部显示两个子项，是关系视图，不是另一份项目排序。

用户另有明确重排决定时，由 vNext 使用既有路径更新序列及变化依据；TraceLens 只读。目标筛选只取原序列的子序列。未登记的可读条目保留“未指定顺序”入口，不自行猜排。

**需求登记顺序不是执行排程。** 功能基线先明确以后，用户和 vNext 仍可根据真实前提安排 Task，且不必同步重排概览中的需求序列。

## 10. Task 关联与执行方式

### 10.1 prepare：消费既有要求并提出可选关联

用户指定了需求或功能点时，以其实际范围为依据，可以附带少量有依据的其他关联建议；未指定时推荐相关要求。无法确定或用户不采用，保持为空。

不要求每个 Task 关联末级功能点，不为填关联字段临时创造需求，不在 prepare 期间重做全项目规划。正常语义判断由宿主处理，不新增专项关联审查或逐条规则问卷。

### 10.2 confirm：先保留实际任务确认，再保存采用的关联

使用真实 Task ID 和实际采用范围，在已有维护授权内保存 TaskBinding。用户已明确的关联或不关联决定不重复确认；未被采用的额外建议不能静默加入正式关系。

Task adoption 与产品绑定分别报告。绑定失败只补绑定，不重复 prepare、不撤销 adoption、不改变焦点，也不自动调整 Task 范围或生命周期。[S12][S14]

### 10.3 一个功能点可以有多个 Task

多个 Task 可以分批实现同一功能点，一个 Task 也可覆盖多个功能或质量要求。功能点不是固定工时工作包，Task 完成数量不能换算为功能完成度。

父项可以汇集自身与子项的 Task，注明“直接关联”或“来自某子项”，按真实身份去重并保留覆盖说明。这是展示派生，不额外向每个祖先写同一份 TaskBinding。

仅关联父项的 Task 不自动下传到全部子项。历史资料确实能证明细项映射时才局部补充，不能从标题相似自动分摊成果。

### 10.4 close 与 pause

真实 `paused` 显示“已暂停”，`closed` 显示“已关闭”。用户已选择关闭，即使仍有未完成部分，界面也不重新要求其满足关闭资格。

关闭不表示全部 Step finished 或验证 PASS。剩余内容保留在 Task 详情；不新增“放弃型关闭”“完成型关闭”等另一套生命周期。

Task 已关闭与需求尚未满足可以同时成立，需求评估不能重开 Task，也不能未经用户决定创建修复 Task。

## 11. 功能点及上层目标的达成对账

### 11.1 三个问题分别回答

| 维度 | 问题 | 不能混同为 |
| --- | --- | --- |
| 定义与范围 | 当前要求是否已经分析清楚，是否还存在已知未决范围？ | 功能未实现或测试失败 |
| 业务达成 | 当前范围和对象下，实际成果满足了什么？ | Task 关闭数量 |
| 执行生命周期 | 某个 Task 是草案、进行中、暂停还是关闭？ | 需求满足结论 |

这三个维度不要求新增三套状态机。范围和定义问题优先复用现有正文、inventory 和未决项；业务达成使用 assessment；Task 使用实际生命周期。

### 11.2 沿用四值结论

| 结论 | 含义 |
| --- | --- |
| satisfied／已满足 | 有适用于当前约定范围的明确满足依据 |
| partially-satisfied／部分满足 | 有明确已满足范围，同时有明确未满足范围 |
| not-satisfied／未满足 | 有依据表明当前要求尚未达到 |
| undetermined／尚未判定 | 证据或适用性不足，或仍有需要核对的内容 |

已有成果加未知剩余，使用尚未判定并保留成果；不能因为没有报告就写未满足，也不能将“计划已采用”直接变成“已满足”。[S06][S08][S13]

### 11.3 功能点明确以后，上层完成判断如何成立

功能点细化为父项对账提供更具体的依据。宿主核对本次必要范围是否已覆盖，适用成果是否支持这些功能及约束，以及组合使用是否符合父项要求。

已有材料充分时，应形成明确的父需求当前范围已满足结论，不能无理由永久保留未知。总体目标是业务结果时，另核对实际结果范围；不把功能清单机械等同于业务成效。

**不采用 `all(children.satisfied)` 自动认证上层。也不要求每个子项先有独立报告，才能写父项结论。** 已有直接覆盖父项或组合行为的材料可以复用；一份证据可支持多个实际覆盖的细项，不强制新增测试或 Task。

功能全部满足可以支持需求满足，但前提是它们覆盖了当前必要要求，并有适用的组合与质量依据。这种判断由 vNext 宿主记录，不由 TraceLens 自行重判。

### 11.4 范围化报告和来源

继续按 `(target, goal_id, scope_id, subject)` 选择结论。某个细项的报告不自动成为另一个目标、版本或父项的报告。当前范围来自目标声明，不能从旧报告反推今日范围。

定义在原有规范文件中，结果在独立 assessment 文件中。保存实际评估时间 checked_at、来源、适用对象及既有算法／摘要信息，使用现有 helper 能力，不要求用户或模型手工猜摘要。

一个报告文件可以包含多条报告，无变化读取不追加。合法 supersedes 只处理同定位的旧报告；跨目标、范围或对象保留各自结果。并发冲突、待核对新材料和元数据不完整按现有契约处理，不另造覆盖规则。[S06][S08]

### 11.5 日常触发与变化处理

沿用 close-task 成功并回读之后的局部评估；有实际交付、外部反馈、用户请求或要求变化时，也可以通过 maintain-project 局部 reconcile，不必等到 close。

先对账实际受影响细项，再按影响核对父需求；确有目标层影响才继续向上。没有关联、资料缺失、维护暂停或用户暂缓时，保留已有结果和具体待维护范围，不影响任务状态。

新增当前义务、细化既有要求、未来增强、撤回要求及反证需要分别解释。历史成果不因新增细项自动消失；有实际反证又不能被旧 PASS 掩盖。

当前摘要并不递归包含全部子项，新增功能点后不能假设父项会自动得出正确的新结论。必要上层核对由局部业务维护完成，不新增递归失效传播器。[S09]

目标整体摘要可能因其他范围声明变化而产生保守待核对提示，这是当前已记录取舍。本轮不将其改判为必修缺陷；保留旧成果与提示，不要求全项目重评。一个维护批次可以先保存采用的定义和必要声明，再取实际摘要形成报告，减少重复改动。[S06]

## 12. TraceLens 页面方案

### 12.1 项目概览：完整范围可见，不等于把全部细项铺满首页

顶部展示明确总目标、当前范围及必要的来源／演变入口；主体保留唯一需求全景，不重复建设“需求顺序线”和“需求拆分概览”。

按项目登记顺序展示适合总览的较高层需求，其子项默认折叠。没有 Task 的需求、尚未实现的已确定功能，均属于整体范围的一部分，不能被过滤成不存在。

卡片重点仍是需求名称、范围和 Task 概况，不给整项需求永久完成颜色，不计算完成率。不常驻展示大段“界面原则”。

存在已记录的定义缺口时，可以用一行摘要提示并进入详情，例如“当前范围有 2 项规则待明确”。只有具体来源支持时才显示数量；没有明确数据，不由前端自由文本猜计数或推出“全量功能已确认”。

### 12.2 需求视图：目标—需求—具体要求关系图

主图展示当前目标及其组成、支撑关系，按需展开具体功能与质量要求。依赖单独按需显示，历史在二级入口；不画成操作工作流，也不把目录＋详情再次作为唯一主视图。

节点展示适用的满足结论，以及简短的已确认成果、缺口和未知。信息来自已有报告和明确正文，不让前端 AI 总结成新的业务判定。

用户应能够直接回答：为了实现当前目标，需要哪些已知要求；哪一项已满足；哪一项尚缺具体能力；哪一部分要求本身尚不清楚。

### 12.3 搜索、筛选与统计

缺口筛选保留必要祖先；“业务未满足”和“尚未判定”可分别筛选。定义待明确的内容按已有正文定位展示；若要机器筛选，先核对已有结构是否足够，不从自然语言猜字段，也不借本轮默认建立一套定义审批状态。

统计仅表示所选范围内已列出的独立条目分布，不将父子节点或 DAG 共享节点重复计数，不将已列数量等同项目全部功能，也不显示需求完成百分比。

项目顺序是原序列，树形展开是关系布局。子项只有在可展示父项之下才折叠，没有可展示父项或未指定顺序的条目保留可见入口。

### 12.4 需求、Task 和历史下钻

从概览点击需求，进入需求图并定位，打开同一需求详情；查看正文、范围、已有成果、未决项、关联 Task 和来源。Task 采用紧凑列表，再进入原 Task／Step 详情。

返回保留目标／范围／对象选择、选中需求、筛选和必要滚动位置。历史通过二级入口查看，不为目标每次增加功能都自动产生一个新版本对象。

### 12.5 现有页面先复用，再补缺口

固定提交的交付记录已经包含相关 TL 工作包。本次不把整个前端重新列为未实现；实施时以实际 TraceLens 源码核对完整结构可达性、层级折叠、父层 Task 汇集与缺口筛选。满足的部分只验证，不制造无意义修改。[S04]

## 13. 数据消费、降级和文件规模

目标与需求仍通过规范项目文件消费。Task／Step 沿用最新已采用的本地 Runtime 只读查询与可信固定入口，查询不可用时使用已有明确快照降级，不让 TraceLens 重放日志实现第二套 reducer。[S04][S05]

不存在“调用查询就授权执行”的关系。不能由 TraceLens 自动调用 prepare、adopt、close、rebuild 来修复数据；来源 read 也只读取明确授权范围。

项目和工作副本隔离、分页版本一致性、异步读取、来源信任和快照标识继续使用已有消费契约，不因本轮功能细化重做整套查询系统。

产品文档可读而任务查询失败时，完整业务结构继续可见；任务部分说明不可用或最近快照。反过来，没有 PRODUCT 不应影响独立任务浏览。未知不能填零，快照读取时间不冒充执行时间或已核验实时状态。

一个定义文件可保存多个功能点；报告独立于定义文件，但可多条共存。引用已有证据，避免一功能点一文件、一查看一快照和重复复制原始日志。不以功能点增加为由默认新增数据库、索引、全文历史扫描或归档子系统。

## 15. 分项实施工作包

以下 FP 编号继续作为方案工作包引用，不是真实 Task ID，不要求一包对应一个 Task，也不默认预创建全部任务。

### FP-01：完整当前范围的语义、用例与差距核对

使用现有 v3 建立一套完整合成资料：明确当前交付目标、多项父需求、其中部分暂不立即实施的已知功能、质量与异常要求、明确未来范围及一项真正待决定问题。

先核对已有 Schema、关系、顺序和报告能否表达，区分“已有可用”“Skill 行为需要补充”“有确定性消费缺口”。不是只提供单个父需求的两项细分，就宣称已经验证总体完整规划。

产出：更新必要使用说明及共用样例；明确采用范围、待决、关系、顺序和 Task 计划的区别。

完成标准：当前范围所有来自材料的必要内容都有准确去向或明确未决说明；不会仅因实施在后期就缺席。用户已采用的全部定义得到实际保存和回读；未采用内容不冒充正式要求。

### FP-02：现有 Skill 的完整规划与维护衔接

在 inventory／update／plan／reconcile 的现有 references 中统一默认行为。主 Skill 仅放必要导向，沿用 confirm 后保存关联、先关闭后局部评估、空关联和用户暂缓路径。

产出：适度的指导增量，以及有限宿主真实工具操作。包含完整规划、新增需求、局部任务和不确定性探索的不同请求，不把“所有请求都先完整规划”写成固定动作。

完成标准：完整规划请求确实产出全范围分析；新增需求产出完整本次增量；局部任务不被强制转全项目分析；原 Task、决定和已成功写入在失败后保留。

### FP-03：细分后的完整范围消费与页面适配

以同一套资料核对 TraceLens 现有代码。先复用已有根目标、顺序、关系图、范围报告、Task 查询和导航；仅修改实际不满足的视图或模型。

产出：能读到全部已知当前要求，概览高层折叠而非消失，关系图可展开细项，定义缺口与实现缺口可解释，父层 Task 汇集去重并注明来源。

完成标准：通过实际页面能够从整体看到缺口、进入细项／Task／Step 并返回；未实施、未绑定以及未来／未决内容按真实范围显示，不改变排序和任务状态。

### FP-04：有限验收、生成与配套交付

按实际修改复用相关测试，生成相应资产，并在隔离安装中核对 Skill、references、helper、Schema 与源码匹配。涉及前端的改动用同一组合完成必要交互验证。

产出：实际命令及结果、使用与兼容说明、已知限制、真实生成物来源。不能以源模板更改代替目标项目已安装内容，不手改生成目录。

完成标准：改进的协作行为有证据，确定性结构和非阻塞路径有相应回归，源码／生成／安装／页面分别报告。软件交付标准不构成用户业务 Task 的执行门槛。

推荐先完成 FP-01，再推进 FP-02 与 FP-03 的相应内容，最后 FP-04。任务创建、工作副本和跨仓库写入在实际实施时依当时授权确定，本方案本身不授权自动进入其他仓库或发布软件。

## 16. 验收场景与证据选择

| 编号 | 场景 | 应观察到的行为 |
| --- | --- | --- |
| A01 | 用户给出明确目标，要求当前交付完整规划 | 全部已知当前功能、必要异常与质量要求进入分析，不只列近期工作 |
| A02 | 当前范围中有实施较晚的明确功能 | 功能仍在当前基线，未预创建 Task 不影响其可见性 |
| A03 | 输入本来已有完整功能清单 | 原内容被完整消费和关联，不重复造同义要求或只抽取部分 |
| A04 | 一项新增正式需求 | 分析本次增量及必要影响，再按实际采用保存，不改无关要求 |
| A05 | 当前范围有真实不确定项 | 不编造决定，不虚报功能全部明确；已知部分继续可用 |
| A06 | 用户要求探索某一未知点 | 明确问题和结果用途，允许探索 Task，不假装已经交付产品能力 |
| A07 | 用户只要求直接修复或明确先实施 | 不强制全项目规划；关联可为空；记录真实管理缺口 |
| A08 | 用户已采用整体方案 | 在授权内保存其明确内容，不重复逐条审批，不采纳附带候选 |
| A09 | 父需求细化出多个功能点 | 父项保留，子项稳定身份、关系和范围不丢失 |
| A10 | 需求本身已足够具体 | 不新增同名子项，不以深度不齐阻止 Task |
| A11 | 一功能点多 Task／一个 Task 多要求 | 实际关联和覆盖保留，不计算完成率 |
| A12 | confirm 成功但绑定冲突 | Task 已采用结果保留，仅处理失败关联 |
| A13 | 关闭时仍有未满足功能或报告失败 | Task 保持 closed，缺口另行记录，不重开不补造 PASS |
| A14 | 暂停和关闭分别发生 | 分别显示 paused 与 closed，不创建额外关闭类型 |
| A15 | 子项已有成果但其他部分未知 | 保留成果，业务结论为适当的尚未判定，而不是盲目部分满足 |
| A16 | 现有组合证据充分支持父项 | 可形成父项结论，不要求每个子项先有报告或增加测试 |
| A17 | 子项看似全满足但父项有遗漏或组合缺口 | 不自动上卷为达成，具体差距可见 |
| A18 | 新增当前要求／后续增强／原义细化 | 分别处理局部结论，保留旧成果及实际适用性，不全图清零 |
| A19 | A-B-C 后新增 D-E-F，D 是 C 的前提 | 序列仍 A-B-C-D-E-F，关系单独显示 |
| A20 | 展开父项或切换目标 | 只改变可见范围，不重写项目顺序、不丢失孤立／未登记条目 |
| A21 | 多目标共享细项及父层 Task 汇集 | 一份定义，结论不跨 scope／subject 套用；Task 去重但不复制绑定 |
| A22 | 产品资料存在但 Task 查询不可用 | 保留完整要求，任务局部降级，不误报零或运行写操作 |
| A23 | 请求全范围但有选定资料未读 | 明确缺口，不用结构合法或已读局部冒称总体完整 |
| A24 | 重复维护或刷新 | 不重复创建 Task、需求、绑定、报告或证据副本 |

这些是行为场景，不是每行必须新增自动化测试。确定性字段、保存和读取优先复用既有 v3 与产品维护测试；业务分析采用有限真实宿主交互，页面采用实际交互核对。

对“完整分析”只能验证给定材料和场景下的覆盖与判断，不能据此宣称任何模型能发现用户从未提供、也无法推断的全部未来要求。预先生成最终答案的脚本，不应被当成 Agent 完成需求分析的证据。

不为标题、常识或指令逐字匹配建立专项测试。审查区分确定性机器规则、AI 行为指导、产品取舍与假设风险；不是文字还可以更严密，就自动增加字段、状态和控制。

## 17. 旧项目、兼容与交付说明

不默认全量迁移旧资料。确需 v3 的子需求或范围表达时，在授权内处理相关文件并保留原内容；旧格式仍按现有能力读取，报告适用性按其实际定义算法处理。

过去没有功能点清单，不说明功能过去没有实现。历史代码、报告与真实用户材料能够支撑时局部补齐；不能确认就保留未知，不伪造旧验收或旧 Task 身份。

完整规划允许分批读取和保存，但请求范围尚有未处理内容时，持续报告剩余范围，不能把一次小批次完成直接叫全项目完成。已有成功批次在冲突或中断后复用，不从头重复生成。

源文档、主 Skill、安装 references、生产 Schema 和消费者应配套验证。新增说明应写回既有长期文档，旧冲突表述在受影响文件中同步修正，避免同时保留“全范围规划”和“默认只细化近期”两套相互冲突的默认规则。

本轮不顺势实施未授权的全项目资料重整、正式发布、真实项目升级、记录清理或数据库改造。版本号由实际交付规则决定，不在方案中先宣称新版本已经可用。

## 18. 合成业务结构示意

以下仅说明“总体先看全、执行可分批”，不是 LawAgent 实际采用的完整需求清单，也不是技术或法律数据源选型结论。

| 较大需求 | 本次规划中应逐项分析的已知细项示意 | 实施安排 |
| --- | --- | --- |
| 法律内容采集 | 内容获取、更新识别、来源保留、失败处理 | 由用户和 vNext 后续分批安排，不要求同时创建 Task |
| 底层存储 | 结构化数据及来源关系、向量索引、必要查询支持 | 架构约束先核对，具体实施 Task 逐步准备 |
| 自动导入 | 清洗切分、全量入库、重复处理、异常记录、失败恢复 | 每点可有多个 Task，范围先明确 |
| 检索能力 | 查询召回、结果排序、来源定位、约定条件下的效果与性能 | 本次承诺即进入基线，未知参数通过必要验证确定 |

完整规划的输出不仅是上表标题，还包括每项实际采用的条件、结果、边界和核对依据。不能把示意点全部复制成真实需求，也不能看到“检索最后实施”就只写一个检索标题、把已有可明确功能全部留待以后。

需求视图按需展开这些细项。尚未创建 Task 的功能仍存在；已关闭的 Task 不自动使功能满足；后续增强不自动使本期已满足要求变为未满足。

## 20. 最终交付口径

本轮要交付的不是“多一层功能点”，而是一种完整可用的协作方式：

**先由用户与 vNext 把当前交付范围的功能和重要约束分析清楚，形成可维护基线；再以 Task 分批实施；发生变化时完整分析本次增量；以适用证据对账具体功能及上层要求；由 TraceLens 如实、简约地展示全貌与差距。**

其中，当前范围的分析应系统完整，长期需求可以动态演进，Task／Step 可以逐步准备。任何管理资料、绑定或评估的缺口，都不能自动剥夺用户继续独立开发的路径。

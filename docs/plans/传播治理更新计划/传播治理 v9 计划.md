# 传播治理 v9 计划（关联影响完整性与大变更迁移修正版）

## Summary

在 v8 基础上继续修复“关联影响完整性保证”与“大变更迁移控制”的剩余缺口，并以 `v9` 作为新的正式计划版本：

- 增加正式的 `修改资格判定协议`，回答“影响链上的中间节点 A 到底能不能改”
- 增加 `实体变更传播 checklist` 与不可兼容冲突上报，降低实体变更遗漏风险
- 把 `CSS / 布局级联副作用` 提升为正式契约对象，而不只锁 DOM 关系
- 增加 `隐式共享符号自动升级` 与 `consumer registry 鲜度校验`
- 增加 `链式回归检测`、`行为契约`、`分阶段迁移计划`

同时保留 v8 的核心结论：

- `V1-V8` 的规范默认持续有效，除非未来显式 `superseded`
- `V4-V8` 的公开结构、生命周期规则、blocker-mapped compatibility reporting 在 `V9` 中继续生效，不得隐式弱化

## Mutation Eligibility Protocol

### 1. 修改资格判定协议

为影响链中的中间节点定义正式的 `MutationEligibilityAssessment`，回答“节点 A 是否允许直接修改”。

判定顺序：

1. 识别节点 `A` 的对象类型
   - symbol / API / DTO field / entity field / UI anchor / layout container
2. 检查是否命中显式锁定项
   - `🔒` 命中则默认不可直改
   - `🟡` 命中则只允许兼容式扩展
3. 若未显式登记，则执行共享性判定
   - evidence 发现 direct consumers 数量
   - 是否跨边界
   - 是否命中行为契约 / 布局契约 / consumer registry
4. 生成资格结论
   - `directly-mutable`
   - `compatible-extension-only`
   - `adapter-required`
   - `not-eligible`
5. 若结论为 `not-eligible` 或 `adapter-required`，不得继续原地修改

默认规则：

- 未登记但 direct consumers `>= 3` 的符号，默认视为共享对象，至少自动升级为 `🟡 candidate`
- 未登记但 direct consumers `>= 5` 且跨边界或命中关键路径的对象，默认视为 `🔒 candidate`
- 任何命中 `locked-hit unresolved gap` 的节点，资格结论不能为 `directly-mutable`

推荐结构：

```yaml
mutation_eligibility_assessment:
  object_path: <string>
  object_kind: <symbol|api|dto-field|entity-field|ui-anchor|layout-container>
  explicit_contract_state: <locked|extend-only|unregistered>
  discovered_direct_consumers: <number>
  cross_boundary: <true|false>
  critical_path_hit: <true|false>
  registry_freshness: <fresh|stale|unknown>
  eligibility: <directly-mutable|compatible-extension-only|adapter-required|not-eligible>
  rationale: <string>
```

## Entity Mutation Completeness

### 1. 实体变更传播 Checklist

增加固定的 `EntityMutationChecklist`，实体 `P` 变更时必须逐类覆盖：

- 定义处
- 构造点 / factory
- 写入点 / repository / ORM
- 读取点 / query / selector
- 映射层 / mapper / adapter
- 序列化 / 反序列化 / validator
- API / DTO / event
- 测试 / fixture / mock / snapshot
- 前端消费
  - hook / store / page / widget / form / table / detail view
- 文档 / 示例

推荐结构：

```yaml
entity_mutation_checklist:
  entity_name: <string>
  categories:
    definition: <covered|gap>
    construction: <covered|gap>
    writes: <covered|gap>
    reads: <covered|gap>
    mapping: <covered|gap>
    serialization: <covered|gap>
    api_dto_event: <covered|gap>
    tests: <covered|gap>
    frontend_consumers: <covered|gap>
    docs_examples: <covered|gap>
  unresolved_categories:
    - <string>
```

### 2. 不可兼容冲突显式上报

新增错误码：

- `INCOMPATIBLE_MUTATION_CONFLICT`

触发条件：

- 实体 / DTO / event / API field 变更命中了某个 `🔒` consumer
- 且没有兼容层、双字段、v2、mapper、adapter 等可行过渡路径

默认 gate：

- `blocks-merge`
- 若该冲突直接影响 release/ship compatibility baseline，则在 ship gate 升级为 `blocks-ship`

## Layout Contract

### 1. CSS / 布局契约

把关键容器布局模型与级联副作用纳入正式契约面，而不仅是元素关系。

必须可锁定的对象：

- 关键容器布局模型
  - `display`
  - `position`
  - `flex-direction`
  - `justify-content`
  - `align-items`
  - `grid-template-*`
  - `gap`
  - `overflow`
  - `width/height` constraints
- 关键 class / utility class
- 全局样式入口
- 主题 token 对关键布局的影响

推荐结构：

```yaml
layout_contract:
  container_path: <ui object path>
  machine_anchor: <data-testid|selector|component-path>
  layout_model: <flex|grid|block|sticky|absolute>
  locked_properties:
    - property: <string>
      value_rule: <exact|range|semantic-lock>
  cascade_sources:
    - <global-style|utility-class|theme-token|local-style>
  side_effect_scope: <children-only|page-region|global>
```

规则：

- 父容器布局属性变更若会改变锁定子元素关系，必须视为 layout contract 破坏
- utility class 或全局样式若影响锁定容器，也必须进入 impact set

## Registry Freshness And Auto Promotion

### 1. 隐式共享符号自动升级

增加“发现时自动升级”规则：

- direct consumers `>= 3`：自动建议升级为 `🟡 candidate`
- direct consumers `>= 5` 或命中跨边界 / critical path：自动建议升级为 `🔒 candidate`
- 若项目忽略升级建议并继续修改，触发：
  - `IMPLICIT_SHARED_OBJECT_UNPROTECTED`

### 2. consumer registry 鲜度校验

每次命中传播条件时，必须对 registry 做 freshness re-scan，而不能只信已登记内容。

推荐结构：

```yaml
registry_freshness_report:
  object_path: <string>
  registry_consumers: <number>
  discovered_consumers: <number>
  freshness: <fresh|stale|unknown>
  divergence_summary: <string>
```

默认规则：

- registry 与 evidence 发现结果不一致时，默认按 discovered union 扩展
- 若 registry stale 且命中 `🔒` 对象，默认 `blocks-merge`

## Regression And Behavior Contracts

### 1. 链式回归检测

新增 `LinkedRegressionRecord`，用于识别“修 A 导致 B，修 B 导致 C”的关联回归。

推荐结构：

```yaml
linked_regression_record:
  current_issue: <string>
  prior_fix_refs:
    - <task|commit|summary>
  shared_objects:
    - <object_path>
  relation: <same-file|same-consumer-chain|same-layout-container|same-entity>
  escalation: <none|warning|blocks-merge>
```

默认规则：

- 若当前 bug 与前一轮修复共享锁定对象、共享容器、共享 entity 或 consumer chain，默认升级为 `关联回归`
- 关联回归连续出现 `>= 2` 次时，不再等同普通新 bug，默认提前停机

### 2. 行为契约

增加 `BehaviorContract`，覆盖签名不变但行为变化的风险。

可声明的行为断言：

- 返回排序
- 默认分支
- 参数默认值
- 条件语义
- 空状态 / loading / error 行为
- API fallback 行为

推荐结构：

```yaml
behavior_contract:
  object_path: <string>
  assertions:
    - type: <sort-order|default-branch|default-parameter|conditional-semantics|fallback>
      rule: <string>
      verification: <test|snapshot|smoke-check>
```

## Staged Migration Protocol

### 1. 分阶段迁移计划

把 `recommend_task_split` 正式扩展为 `StagedMigrationPlan`。

推荐结构：

```yaml
staged_migration_plan:
  migration_id: <string>
  phases:
    - phase_id: <string>
      objective: <string>
      preconditions:
        - <string>
      allowed_mutations:
        - <string>
      runtime_state: <string>
      verification:
        - <string>
      exit_criteria:
        - <string>
  dependencies:
    - from: <phase_id>
      to: <phase_id>
```

规则：

- 被标记为 `recommend_task_split` 的大变更，若继续推进，必须产出 `StagedMigrationPlan`
- 每个阶段必须能回答：
  - 这一阶段做什么
  - 系统在半迁移状态下如何运行
  - 下一阶段的前置条件是什么

## Test Plan

必须覆盖以下场景：

- 未登记但被多方依赖的符号命中自动升级建议
- 修改资格判定对 `A` 给出 `adapter-required` 或 `not-eligible`
- 实体变更 checklist 任一类别缺失时判为不完整
- 实体变更命中 `🔒` consumer 且无兼容路径时产出 `INCOMPATIBLE_MUTATION_CONFLICT`
- 父容器布局属性变更导致锁定子元素关系漂移时，命中 layout contract break
- registry stale 且命中锁定对象时 blocker
- 链式回归连续出现时提前停机
- 签名不变但排序 / 默认分支变化时命中 behavior contract break
- `recommend_task_split` 场景若无 `StagedMigrationPlan`，判为不完整

验证入口至少包括：

- `bun run test:workflow-docs`
- 相关 protocol / validation tests
- generated docs freshness checks

## Assumptions

- `V9` 是对 `V8` 的 additive clarification + completeness repair，不替代 `V4-V8` 结构，也不废止 `V1-V3` 规则
- 所有公开结构继续有效，除非未来显式写出 superseded 关系
- 本轮仍优先补协议、schema、模板、结果 contract，不要求立即实现完整自动推理器
- 这轮继续属于协议与文档 contract 扩展，建议协议版本从 `0.9.0` 提升到 `0.10.0`

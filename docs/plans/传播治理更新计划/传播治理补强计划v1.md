# 传播治理补强方案（前后端统一、复用现有文档结构）

## Summary

先把体系补成一套统一的“变更传播规则”，再映射回现有文档。核心不是新增很多文档，而是在现有 `CONTRACTS.md`、`CURRENT_TASK.md`、`BASELINES.md`、`WORKFLOW_PROTOCOL.md` 里正式定义：

- 变更起点
- 影响集合
- 必改集合
- 冲突集合
- 兼容策略
- 回归矩阵

这套规则同时适用于：

- 后端共享函数 / 共享接口
- 实体 / DTO / schema / event / table 变更
- 前端调用后端接口的多消费方场景
- 已锁定 UI / 组件 / 交互结构的扩展场景

默认策略采用“条件触发 + 优先兼容层”，不把每个任务都变重，但一旦碰共享接口、锁定符号、实体结构、DTO/API 字段、关键 UI，就必须进入传播分析。

## Rule Package

### 1. 统一术语与判断顺序

新增并统一使用以下术语：

- `变更起点`：本轮真正要满足的需求入口，可能是 `Z` 接口、实体 `P`、某个 API、某个 UI 区域
- `影响集合`：所有直接或间接受影响的调用方、被调方、消费方、测试、映射层、渲染层
- `必改集合`：不改就会产生错误、语义漂移或编译失败的对象
- `冲突集合`：理论上应改，但因 `🔒` 契约、稳定 UI、兼容性基线等原因不能直接改的对象
- `兼容策略`：adapter / decorator / wrapper / AA / 映射层 / v2 API / 双字段过渡
- `回归矩阵`：所有既有调用方和关键消费链路的验证清单

统一判断顺序固定为：

1. 识别变更起点  
2. 计算影响集合  
3. 区分必改集合与冲突集合  
4. 先选兼容策略，再决定是否允许原地修改  
5. 列出回归矩阵后才进入实现

### 2. 共享符号与共享接口规则

对共享函数、导出符号、服务接口、前端 API client 方法统一采用以下规则：

- 若一个稳定符号被多个调用方复用，默认禁止为单一新需求直接改旧语义
- 只有在该符号明确标记为 `🟡 可扩展不可破坏`，且能证明所有旧调用方语义不变时，才允许原地扩展
- 如果改动只服务新链路，默认新增兼容层，如 `AA`、wrapper、adapter、v2 方法
- 若冲突集合中存在任何 `🔒` 调用方、`🔒` 返回字段、`🔒` UI 锚点、`🔒` 事件语义，AI 必须停下并报告，不允许静默传播修改

### 3. 实体 / DTO / Schema / Event 传播规则

当实体 `P`、DTO、表结构、事件 payload 或 API 字段变更时，传播分析必须覆盖：

- 定义处
- 构造与写入点
- 读取与消费点
- 映射 / 序列化 / 反序列化 / 校验层
- 测试、fixture、mock、snapshot
- 前端 selector / hook / component / form / table / detail view

固定决策规则：

- 字段重命名、语义变化、类型变化默认视为高风险传播
- 若对外 API / DTO 已锁定，默认不直接改旧字段，优先保留旧字段并映射到新内部语义，或提供 v2
- 在冲突集合未被显式解决前，不进入代码实现

### 4. 前端调用后端接口的统一跨边界契约

把 API 明确定义为“跨边界共享契约”，不是只属于后端。每个稳定 API 至少记录：

- 提供方
- 消费方列表
- 稳定入参
- 稳定返回字段
- 不可破坏语义
- 默认兼容策略

规则统一为：

- 后端改接口时，必须同时分析前端消费方传播
- 前端新增需求若逼迫改接口，也必须先分析其他前端调用方是否受影响
- 一个接口被多个前端方法、页面、hook、store 复用时，默认不直接破坏旧字段/旧行为
- 默认先保留旧接口行为，通过可选参数、兼容字段、client adapter 或 v2 endpoint 过渡

## Test Plan

### 规则与文档测试

- `CONTRACTS.md` 生成结果保留原有 heading，同时包含传播治理示例骨架
- `CURRENT_TASK.md` 生成结果在不触发传播时保持轻量，在触发传播时能容纳影响集合 / 冲突集合 / 兼容策略
- `BASELINES.md` 兼容性基线存在 API 兼容窗口和迁移要求示例
- `WORKFLOW_PROTOCOL.md` 与 `FILE_SCHEMAS.md` 对 `contract-compatibility` 的语义表述一致

### 场景测试

至少新增或更新以下 doc-contract / generator 用例：

- 共享函数 `A` 被 `B/C` 复用，新需求 `Z` 只允许新增 `AA`，不允许破坏 `A`
- 实体 `P` 字段变更时，任务包要求列出所有消费层并给出兼容策略
- 后端接口被多个前端页面 / hook / store 复用时，不允许直接删旧字段
- 未写影响集合但触发传播条件的任务包，应被视为 contract 不完整
- 只改普通单点逻辑、未触发传播条件的任务包，不应被错误地提升为重流程

### 验证命令

实现后应至少通过：

- `bun run test:workflow-docs`
- 必要的 protocol/runtime 相关测试
- 重新生成 docs 后的 freshness 校验

## Assumptions

- 根路径 [FILE_SCHEMAS.md](/e:/coding/github/gstack/FILE_SCHEMAS.md:1) 是规范源；`dist/**` 只作为打包产物后续同步
- 本轮采用“复用现有章节”策略，不新增新的治理文档，也不新增新的一级 heading
- 传播分析采用“条件触发”，不是每个任务都强制展开
- 前后端共享接口统一建模为“跨边界契约”，不是仅后端所有
- 发生冲突时默认优先兼容层，不默认允许破坏旧符号 / 旧字段 / 旧 UI 锚点
- 因为会收紧 doc contract 与验证语义，协议版本默认按 `0.x` 下的非兼容扩展处理，建议落地时将 `Protocol-Version` 从 `0.2.0` 提升到 `0.3.0`

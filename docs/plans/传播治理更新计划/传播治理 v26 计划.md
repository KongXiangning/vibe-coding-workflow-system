# 传播治理 v26 计划（主线整合完整版 + schema / 执行协议 / CSS cascade 治理补完 + eligibility / contract schema 收口）

## Summary

`v26` 是新的主线整合版本，以 `v25` 为唯一基线完整复制后做增量修复，目标是在不丢失 `v25` 信息的前提下，清除 `MutationEligibilityAssessment` 状态机里残留的旧语义文案，并让 Test Plan 与条件分支 schema 完全一致，使实现者不必回看早期版本即可获得一致可执行的主线定义。

本版目标：

- 保留 `v4-v25` 已确立的公开结构、生命周期规则、blocker-mapped compatibility reporting
- 统一 `Public Interfaces / Contracts`
- 统一 complexity / evidence governance、candidate 收敛、链式回归、layout / behavior contract、migration blocker、entity / registry 规则
- 补完 `EvidenceRecord`、`UIAnchorReplacement`、`MutationEligibilityAssessment`、`LinkedRegressionRecord`、`LayoutContract`、`BehaviorContract`、`StagedMigrationPlan` 的正式 schema
- 补完执行顺序协议、发现机制协议、多 blocker 并发优先级、CSS cascade / sibling reflow / breakpoint 治理
- 让实现者只看 `v26` 就能获得完整 contract 面、错误码、默认 gate、schema 结构和测试要求

## Public Interfaces / Contracts

`v26` retains all public structures and governance rules from `v4-v25` unless explicitly superseded。

统一公开结构如下：

- 来自 `v4 / v5 / v6`
  - `EvidenceRecord`
  - `UIAnchorReplacement`
  - `ContractCompatibilityResult`
  - `EvidenceAggregation`
  - `ComplexityAssessment`
  - `over_limit_policy`
  - `evidence_diff_threshold`
- 来自主线传播治理
  - `MutationEligibilityAssessment`
  - `EntityMutationChecklist`
  - `LayoutContract`
  - `RegistryFreshnessReport`
  - `LinkedRegressionRecord`
  - `BehaviorContract`
  - `StagedMigrationPlan`
- 来自 focused patch 并入主线
  - `migration_plan_requirement`
  - `implicit_shared_object_detection`

同时继续保留并主线化以下规则：

- graded forced strategies
- complexity / evidence 联动升级
- blocker-mapped compatibility reporting

规则：

- 新增结构一旦被 schema / protocol / tests 引用，必须同步进入 `Public Interfaces / Contracts`
- 后续版本默认只能 `additive extend`
- 若要移除、替换、降级任一结构或治理规则，必须显式标注 `superseded`

`ContractCompatibilityResult` 继续保留并升级为正式结构，强制包含：

- `error_code`
- `object_path`
- `severity`
- `default_blocker_level`
- `evidence`
- `strategy_origin`
- `branch_gate_mapping`
- `suggested_resolution`

`ContractCompatibilityResult` 正式结构：

```yaml
contract_compatibility_result:
  error_code: <string>
  object_path: <string>
  severity: <warning|error|critical>
  default_blocker_level: <warning-only|blocks-merge|blocks-ship>
  evidence:
    - <EvidenceRecord ref or summary>
  strategy_origin:
    over_limit_policy_branch: <recommend_task_split|enforce_compat_layer|enforce_adapter_boundary|hard_stop|none>
    divergence_state: <no_divergence|significant_divergence|locked_hit_gap>
  branch_gate_mapping:
    merge_gate: <warning-only|blocks-merge>
    ship_gate: <warning-only|blocks-merge|blocks-ship>
    rationale: <string>
  suggested_resolution: <string>
```

规则：

- `none` 只允许出现在 `ContractCompatibilityResult.strategy_origin.over_limit_policy_branch`
- `none` 表示当前结果未命中任何 over-limit policy branch
- `no_divergence` 只允许出现在 `ContractCompatibilityResult.strategy_origin.divergence_state`
- `no_divergence` 表示当前结果未命中 evidence divergence 或 locked-hit gap
- `none` 不得出现在 `ComplexityAssessment.forced_strategy`
- `none` 不得再作为 `divergence_state` 的无分歧占位值使用
- `severity` 必须服从以下映射：
  - `warning`
    - 只允许用于 `warning-only`
    - 只允许命中未锁定对象或非 breaking 观察结果
  - `error`
    - 默认用于 `blocks-merge`
  - `critical`
    - 默认用于 `blocks-ship`
    - 或命中 `hard_stop`、`locked_hit_gap`、release-critical behavior/layout break、ship compatibility baseline break
- `severity` 不能降低 `default_blocker_level`
- 所有 blocker / warning 输出都必须收敛为正式 `ContractCompatibilityResult`，不允许只输出口头推荐结果

`EvidenceRecord` 正式结构：

```yaml
evidence_record:
  mechanism: <symbol-reference-search|import-graph|api-client-grep|dto-type-usage|event-usage-search|ui-usage-scan|selector-search|snapshot-scan|style-source-scan>
  query_or_entrypoint: <string>
  scope: <string>
  result_summary: <string>
  confidence: <low|medium|high>
  gaps:
    - <string>
```

规则：

- `query_or_entrypoint` 必须可复现，不允许使用“全局搜了一下”之类不可审计描述
- `scope` 必须明确到目录、模块、服务边界、页面区域或样式入口
- 命中 `🔒` / `🟡` / API / entity / UI frozen target 时，默认至少需要 2 种不同 discovery mechanism
- `style-source-scan` 用于发现 utility class、theme token、global style、component-local style 对 layout 的隐式影响

`UIAnchorReplacement` 正式结构：

```yaml
ui_anchor_replacement:
  old_anchor: <ui object path + machine anchor>
  successor_anchor: <ui object path + machine anchor>
  transition_window: <version|window|task-cycle>
  alias_policy: <dual-anchor|alias-selector|no-alias-with-reason>
  alias_details: <string>
  relation_migration:
    - from_relation: <old relation>
      to_relation: <new relation>
  removal_precondition: <string>
  verification: <string>
```

规则：

- 旧 anchor 被替换时必须声明 `successor_anchor`
- 默认保留 `dual-anchor` 或 `alias-selector` 直到 `removal_precondition` 满足
- 被锁定的 relation 迁移必须同步迁移 relation 两端，而不是只替换单个 selector

`MutationEligibilityAssessment` 正式结构：

```yaml
mutation_eligibility_assessment:
  common:
    object_path: <string>
    object_kind: <symbol|api|dto-field|entity-field|ui-anchor|layout-container>
    explicit_contract_state: <locked|extend-only|unregistered>
    discovered_direct_consumers: <number>
    cross_boundary: <true|false>
    critical_path_hit: <true|false>
    locked_hit_chain: <true|false>
    registry_freshness: <fresh|stale|unknown>
    rationale: <string>
  when_pending_prerequisites:
    assessment_status: pending-prerequisites
    blocking_gaps:
      - <locked_hit_gap_unresolved|registry_freshness_stale_locked_hit>
    eligibility: forbidden
  when_completed:
    assessment_status: completed
    blocking_gaps: forbidden
    eligibility: <directly-mutable|compatible-extension-only|adapter-required|not-eligible>
```

规则：

- 它是“当前对象能否直接改旧语义”的正式裁决对象
- 同文件不等于可直接修改；所有判断以 `object_path` 粒度进行，不以 file 粒度粗暴放行
- `assessment_status`
  - `pending-prerequisites` 表示仍存在未消解前置 gap，当前不得输出最终 eligibility 结论
  - `completed` 表示 eligibility 已完成正式裁决，`eligibility` 字段必须可直接驱动后续 gate / blocker
- `locked_hit_chain=true`
  - 表示当前对象位于一条传播链上，且该链已命中 `🔒 / 🟡 / frozen UI / locked API / locked entity / locked behavior/layout contract` 中至少一个受保护对象
  - 命中后，该对象不得再按普通未登记对象处理
- `compatible-extension-only`
  - 只能通过 wrapper / decorator / facade / `A -> AA` 兼容层扩展
  - 不允许直接修改被 `B/C/...` 复用的旧入口语义
- `adapter-required`
  - 用于 cross-boundary 或 direct consumer 过高、且需要边界隔离的场景
- `not-eligible`
  - 用于“正式裁决结果已收敛为当前对象不允许直接变更”的场景
  - 它只允许出现在 `assessment_status=completed`
  - 其上游原因只允许来自已完成裁决后仍成立的 completed 态原因，例如不存在可行兼容路径或不存在可接受写回路径
- direct consumers `>= 3` 时，至少自动升级为 `extend-only-candidate`
- direct consumers `>= 3` 且命中 `cross-boundary / critical path / locked-hit chain` 时，至少自动升级为 `locked-candidate`
- 未消解前置 gap 与正式 eligibility 结果必须显式区分：
  - 前者属于“为什么当前还不能完成 eligibility 收敛”的根因
  - 后者属于“eligibility 已完成裁决，结果为 `not-eligible`”的正式输出状态
- `assessment_status=pending-prerequisites` 时：
  - `eligibility` 必须禁止出现
  - `blocking_gaps` 必须非空
  - `blocking_gaps` 中每一项都必须能映射到一个 `P0` 错误码
- `assessment_status=completed` 时：
  - `eligibility` 必须存在
  - `blocking_gaps` 必须禁止出现
- `blocking_gaps`
  - 只能使用以下受控枚举：
    - `locked_hit_gap_unresolved`
    - `registry_freshness_stale_locked_hit`
  - 决定“为什么 eligibility 还没完成正式裁决”
  - 它们只允许作为 `pending-prerequisites / P0` 根因出现，不得作为 completed 态 `not-eligible` 的上游原因复用
  - 不允许出现不能映射到 `P0` 的 `blocking_gaps`
  - 不允许出现 `P0` 之外的前置 gap 仍滞留在 `pending-prerequisites`
- `blocking_gaps` 到 `P0` 错误码的固定映射：
  - `locked_hit_gap_unresolved` -> `IMPACT_LOCKED_HIT_GAP_UNRESOLVED`
  - `registry_freshness_stale_locked_hit` -> `REGISTRY_FRESHNESS_STALE_LOCKED_HIT`

标准错误：

- `MUTATION_NOT_ELIGIBLE`
  - 触发条件：
    - `MutationEligibilityAssessment.assessment_status=completed`
    - `MutationEligibilityAssessment.eligibility=not-eligible`
    - 且不存在可立即消解的兼容路径或写回路径
  - 默认 gate：
    - merge 阶段 `blocks-merge`
    - 若命中 release / ship critical path，则升级为 `blocks-ship`
  - 语义定位：
    - 它是 eligibility 已完成收敛后的正式错误结果
    - 它不等价于“仍有未消解前置 gap”

## Key Changes

### 1. Complexity / Evidence Governance 主线补回

把 `v8 / V6` 的复杂度与证据分歧治理补回主线。

`evidence_diff_threshold` 正式结构：

```yaml
evidence_diff_threshold:
  absolute_diff: 3
  relative_diff_ratio: 0.5
```

`EvidenceAggregation` 正式结构：

```yaml
evidence_aggregation:
  aggregation_strategy: union
  sources:
    - <EvidenceRecord ref>
  candidate_impact_set:
    - <object_path>
  significant_divergence: <true|false>
  divergence_reason:
    - <string>
  unresolved_gaps:
    - <string>
  aggregated_confidence: <low|medium|high>
```

默认证据聚合规则：

- 默认 `union + conflict escalation`
- `union` 是唯一允许的主线 evidence aggregation 策略
- 所有 evidence 命中的对象取并集形成 `candidate impact set`
- 若数量差异满足以下任一条件，视为 `significant_divergence`
  - `absolute_diff > 3`
  - `relative_diff_ratio > 0.5`
- 若一个 evidence 结果为 0，另一个非 0，且命中 locked/shared 对象，直接进入 unresolved gap
- `intersection` / `priority` 不属于当前主线协议对象，后续若要支持，必须显式扩展 schema、默认规则、适用条件与测试
- `divergence_state` 判定优先级固定为：
  - `locked_hit_gap` > `significant_divergence` > `no_divergence`
- 若 `unresolved_gaps` 命中 `🔒` / `🟡` / API / entity / UI frozen target，则 `divergence_state=locked_hit_gap`
- 若未命中 locked-hit gap，但 `significant_divergence=true`，则 `divergence_state=significant_divergence`
- 若 `significant_divergence=false` 且 `unresolved_gaps` 为空，则 `divergence_state=no_divergence`

`over_limit_policy` 正式结构：

```yaml
over_limit_policy:
  rules:
    - when:
        depth_exceeded: true
      then:
        - recommend_task_split
    - when:
        direct_consumers_exceeded: true
      then:
        - enforce_compat_layer
    - when:
        total_consumers_exceeded: true
      then:
        - enforce_compat_layer
    - when:
        cross_boundary_exceeded: true
      then:
        - enforce_adapter_boundary
    - when:
        multiple_metrics_exceeded: true
      then:
        - hard_stop
```

默认复杂度阈值：

- `max_propagation_depth: 3`
- `max_direct_consumers: 8`
- `max_total_candidate_consumers: 20`
- `max_cross_boundary_hops: 2`

语义细化：

- `depth_exceeded`
  - 优先表示任务已经跨出单次安全改动边界，应拆任务
- `direct_consumers_exceeded`
  - 优先表示旧入口直接扇出过高，不允许直接改旧语义
  - 默认需要 wrapper / facade / compat layer 保护旧入口
- `total_consumers_exceeded`
  - 优先表示全传播面过大
  - 默认需要 compat layer，并结合迁移计划或 phased rollout 判断
- `multiple_metrics_exceeded`
  - 表示问题不是单点治理，而是整体扩边失控，进入 `hard_stop`

`ComplexityAssessment` 正式结构：

```yaml
complexity_assessment:
  propagation_depth: <number>
  direct_consumers: <number>
  total_candidate_consumers: <number>
  cross_boundary_hops: <number>
  exceeded_metrics:
    - <depth|direct_consumers|total_consumers|cross_boundary_hops>
  threshold_status: <within-limit|over-limit>
  forced_strategy: <direct-change|recommend_task_split|enforce_compat_layer|enforce_adapter_boundary|hard_stop>
```

联动升级规则：

- `hard_stop` 不是 advisory，必须转化为 blocker 结果
- `significant_divergence + locked/shared/API/UI frozen target` 必须 blocker
- `within-limit` 不等于可继续实现，只要仍有 unresolved locked-hit gap，仍阻断 merge
- `ComplexityAssessment.forced_strategy` 与 `ContractCompatibilityResult.strategy_origin.over_limit_policy_branch` 共享同一组 blocker branch 命名
- `direct-change` 只允许出现在 `ComplexityAssessment.forced_strategy`
- `direct-change` 仅表示未触发 blocker 的直接推进状态，不对应独立错误码
- `direct-change` 不得出现在 `ContractCompatibilityResult.strategy_origin.over_limit_policy_branch`
- `none` 只属于 `over_limit_policy_branch`；`no_divergence` / `significant_divergence` / `locked_hit_gap` 只属于 `divergence_state`
- `direct-change` 只属于 assessment state
- 两者共享的 branch 只有：
  - `recommend_task_split`
  - `enforce_compat_layer`
  - `enforce_adapter_boundary`
  - `hard_stop`
- `none`、`no_divergence` 与 `direct-change` 不是可互换值，也不是共享 branch 命名的一部分
- 映射关系固定为：
  - `recommend_task_split` -> `IMPACT_TASK_SPLIT_IGNORED`（被忽略且继续扩边时）
  - `enforce_compat_layer` -> `COMPAT_LAYER_REQUIRED_BUT_MISSING`
  - `enforce_adapter_boundary` -> `COMPAT_ADAPTER_BOUNDARY_MISSING`
  - `hard_stop` -> `IMPACT_HARD_STOP_REQUIRED`

### 2. Candidate 收敛与隐式共享对象治理

默认检测阈值：

- direct consumers `>= 3` -> `extend-only-candidate`
- direct consumers `>= 3` 且命中 `cross-boundary / critical path / locked-hit chain` -> `locked-candidate`

`implicit_shared_object_detection` 正式结构：

```yaml
implicit_shared_object_detection:
  object_path: <string>
  object_kind: <symbol|api|dto-field|entity-field|ui-anchor|layout-container>
  direct_consumers: <number>
  cross_boundary: <true|false>
  critical_path_hit: <true|false>
  locked_hit_chain: <true|false>
  proposed_contract_state: <extend-only-candidate|locked-candidate>
  writeback_required: <true|false>
```

收敛规则：

- `extend-only-candidate`
  - 在当前任务内按真实 `🟡` 处理
  - 若继续推进实现，必须回写到 `CONTRACTS.md`
- `locked-candidate`
  - 在当前任务内按真实 `🔒` 处理
  - 未回写前不得直接修改旧语义
- `locked_hit_chain=true`
  - 表示当前对象位于一条传播链上，且该链已命中 `🔒 / 🟡 / frozen UI / locked API / locked entity / locked behavior/layout contract` 中至少一个受保护对象
  - 命中后，该对象不得再按普通未登记对象处理
- 显式 `🔒` / `🟡` 永远高于 candidate
- candidate 与旧 registry 冲突时，按更严格的一侧执行
- candidate 不是 advisory tag，而是当前任务内立即生效的临时保护级别

强制闭环：

- 检测到共享对象后，必须二选一：
  - 回写到 `CONTRACTS.md`
  - 输出 blocker 结果并停止继续修改
- 不允许存在“检测到了共享对象，但既不回写、也不阻断”的中间状态

标准错误：

- `IMPLICIT_SHARED_OBJECT_UNPROTECTED`
  - 默认 `blocks-merge`
  - 命中 release / ship critical path 且仍未回写或未停机时升级为 `blocks-ship`

### 3. 链式回归协议

`LinkedRegressionRecord` 从原则升级为可校验协议。

正式结构：

```yaml
linked_regression_record:
  regression_chain_id: <string>
  current_issue: <string>
  prior_fix_refs:
    - <task|commit|summary>
  window_scope: <current-task-plus-1-direct-prior-fix|extended-by-explicit-chain>
  window_size: <number>
  count_basis: <fix-chain|task>
  linked_components:
    - <object_path>
  shared_objects:
    - <object_path>
  relation: <same-file|same-consumer-chain|same-layout-container|same-entity|same-behavior-contract|same-migration-chain>
  escalation: <none|warning|blocks-merge|blocks-ship>
```

默认统计规则：

- `window_scope`: 当前任务 + 最近 1 个直接前序修复任务
- `window_size`: 2 个连续修复单元
- `count_basis`: 以 `fix chain / task` 为单位，不按单条 commit 计
- 默认不跨独立会话追溯；仅当同一 `regression_chain_id` 被显式延续时才跨会话累计

默认触发条件：

- 同一 `regression_chain_id` 下连续出现 `>= 2` 次关联回归
- 且触发对象与上一轮修复对象存在共享依赖、共享 consumer、共享 layout region、共享 behavior contract、或同一迁移链路

标准错误：

- `LINKED_REGRESSION_EARLY_STOP`
  - 默认 `blocks-merge`
  - 命中 release / ship critical path 时可升级为 `blocks-ship`

### 4. Layout / Behavior Contract 正式 gate 化

`LayoutContract` 裁决对象：

- 父容器布局模型
- 关键 CSS 属性值
- 关键 region / anchor 的位置、对齐、伸缩、层级、可见性关系
- sibling 的顺序、占位、flex-grow / shrink、grid span 与插入影响
- utility class / theme token / global style / local style 的 cascade 来源
- breakpoint 下的关系断言
- stacking context、overflow clip、z-index 关系

`BehaviorContract` 裁决对象：

- 排序语义
- 默认分支
- 参数默认值语义
- 条件行为断言
- API / function 的关键运行时行为

`LayoutContract` 正式结构：

```yaml
layout_contract:
  container_path: <ui object path>
  machine_anchor: <data-testid|selector|component-path>
  layout_model: <flex|grid|block|sticky|absolute>
  locked_properties:
    - property: <string>
      value_rule: <exact|range|semantic-lock>
  locked_relations:
    - relation: <left-of|right-of|above|below|aligned-with|occupies|same-row|same-column>
      target: <ui object path>
      rule: <exact|semantic-lock>
  cascade_sources:
    - <global-style|utility-class|theme-token|local-style>
  sibling_reflow_sensitive: <true|false>
  insertion_guard:
    mode: <allow-in-extension-zone|allow-with-precheck|forbidden-in-frozen-zone>
    protected_siblings:
      - <ui object path>
  breakpoint_contracts:
    - range: <string>
      assertions:
        - <string>
  stacking_context:
    z_index_rule: <exact|range|semantic-lock>
    overflow_clip_rule: <exact|range|semantic-lock>
  side_effect_scope: <children-only|page-region|global>
```

`BehaviorContract` 正式结构：

```yaml
behavior_contract:
  object_path: <string>
  assertions:
    - type: <sort-order|default-branch|default-parameter|conditional-semantics|fallback>
      rule: <string>
      verification: <test|snapshot|smoke-check>
```

标准错误：

- `LAYOUT_CONTRACT_BREAK` -> `blocks-merge`
- `BEHAVIOR_CONTRACT_BREAK` -> `blocks-merge`

ship 升级规则：

- 命中 frozen UI region、locked anchor relation、critical interaction path、或 release-critical behavior contract
- 且未通过兼容层或替代迁移
- 可升级为 `blocks-ship`

统一要求：

- 只要 tests / validation 命中了 layout break 或 behavior break，就必须产出正式 `ContractCompatibilityResult`
- 新增元素进入 locked region 或 expand-only-no-reflow region 前，必须执行 layout impact precheck
- layout impact precheck 至少检查：
  - sibling 顺序是否变化
  - 左右 / 上下 / 对齐关系是否变化
  - flex / grid 占位与 grow / shrink 是否变化
  - breakpoint 下断言是否被破坏
  - cascade source 是否新增覆盖
  - stacking context 是否变化
- 命中以下任一情况时，视为 `LAYOUT_CONTRACT_BREAK`：
  - 原本左对齐元素被新元素推到右侧
  - 原本固定顺序的按钮组被重排
  - 原本冻结区中的 sibling 宽度 / 对齐 / 层级被被动改变
  - breakpoint 下出现溢出、换列、重叠、不可见
- `LayoutContract` 默认支持三类 zone：
  - allowed extension zone
  - expand-only-no-reflow zone
  - fully frozen zone

### 5. Migration 计划强制阻断化

`migration_plan_requirement` 正式结构：

```yaml
migration_plan_requirement:
  required: <true|false>
  trigger_reason:
    - <recommend_task_split|multi_phase_compat|dual_field_transition|v2_cutover|ui_anchor_transition|cross_boundary_migration>
```

触发规则：

- `required=true` 且任务继续实现时，没有 `StagedMigrationPlan` 就直接失败
- `required=true` 但选择“仅输出分析不实现”时，可不提供完整迁移计划，但必须明确停机

`StagedMigrationPlan` 正式结构：

```yaml
staged_migration_plan:
  migration_id: <string>
  phases:
    - phase_id: <string>
      objective: <string>
      preconditions:
        - <string>
      allowed_mutations:
        - <string>
      runtime_state: <string>
      verification:
        - <string>
      exit_criteria:
        - <string>
  dependencies:
    - from: <phase_id>
      to: <phase_id>
```

`StagedMigrationPlan` 最小完整性要求：

- `migration_id`
- 至少 2 个 phase
- 每个 phase 必须包含：
  - `objective`
  - `preconditions`
  - `allowed_mutations`
  - `runtime_state`
  - `verification`
  - `exit_criteria`
- 明确 phase dependencies
- 明确哪一阶段开始引入兼容层，哪一阶段允许移除旧行为

完整性校验：

- 没有 `runtime_state` -> `MIGRATION_RUNTIME_STATE_UNDECLARED`
- phase 顺序依赖无法形成有效 DAG -> `MIGRATION_PHASE_ORDER_INVALID`
- phase 数量不足、字段缺失、没有 verification / exit criteria -> `MIGRATION_PLAN_INCOMPLETE`

标准错误：

- `MIGRATION_PLAN_REQUIRED_BUT_MISSING` -> `blocks-merge`
- `MIGRATION_PLAN_INCOMPLETE` -> `blocks-merge`
- `MIGRATION_PHASE_ORDER_INVALID` -> `blocks-merge`
- `MIGRATION_RUNTIME_STATE_UNDECLARED` -> `blocks-merge`

ship 升级规则：

- 迁移窗口相关场景可升级为 `blocks-ship`

### 6. 实体变更与 registry 鲜度治理

`EntityMutationChecklist` 正式结构：

```yaml
entity_mutation_checklist:
  entity_name: <string>
  categories:
    definition: <covered|gap>
    construction: <covered|gap>
    writes: <covered|gap>
    reads: <covered|gap>
    mapping: <covered|gap>
    serialization: <covered|gap>
    api_dto_event: <covered|gap>
    tests: <covered|gap>
    frontend_consumers: <covered|gap>
    docs_examples: <covered|gap>
  unresolved_categories:
    - <string>
```

`EntityMutationChecklist` 必须逐类覆盖：

- 定义处
- 构造点 / factory
- 写入点 / repository / ORM
- 读取点 / query / selector
- 映射层 / mapper / adapter
- 序列化 / 反序列化 / validator
- API / DTO / event
- 测试 / fixture / mock / snapshot
- 前端消费
  - hook / store / page / widget / form / table / detail view
- 文档 / 示例

规则：

- `EntityMutationChecklist` 是正式检查模板，不是结构名占位
- 若存在 `gap`，必须进入 `unresolved_categories` 或 blocker 判断

`RegistryFreshnessReport` 正式结构：

```yaml
registry_freshness_report:
  object_path: <string>
  registry_consumers: <number>
  discovered_consumers: <number>
  freshness: <fresh|stale|unknown>
  divergence_summary: <string>
```

默认规则：

- registry 与 evidence 发现结果不一致时，默认按 discovered union 扩展
- 若 registry stale 且命中 `🔒` 对象，必须产出正式 blocker 结果

标准错误：

- `REGISTRY_FRESHNESS_STALE_LOCKED_HIT`
  - 默认 `blocks-merge`
  - 命中 release / ship critical path 时可升级为 `blocks-ship`

实体不可兼容冲突：

- `INCOMPATIBLE_MUTATION_CONFLICT`
  - 触发条件：
    - 实体 / DTO / event / API field 变更命中了某个 `🔒` consumer
    - 且没有兼容层、双字段、v2、mapper、adapter 等可行过渡路径
  - 默认 gate：
    - merge 阶段 `blocks-merge`
    - 若直接影响 release / ship compatibility baseline，则 ship gate 升级为 `blocks-ship`

### 7. 执行顺序与发现机制协议

标准执行顺序：

1. 识别 `change_start_set`
   - 把用户需求映射为 object-path 粒度的变更起点，而不是 file 粒度
2. 读取显式 contract
   - 查找 `🔒` / `🟡` / candidate / frozen zone / behavior contract / layout contract
3. 执行 discovery
   - 为每个起点生成最少证据集，产出 `EvidenceRecord`
4. 聚合传播面
   - 生成 `EvidenceAggregation`、`candidate impact set`
   - 同步做 `RegistryFreshnessReport`
5. 对命中对象做专属评估
   - symbol / api / dto / entity / ui-anchor / layout-container 必须进入 `MutationEligibilityAssessment`
   - entity 变更必须进入 `EntityMutationChecklist`
   - UI 变更必须进入 `LayoutContract`
   - 关键运行时语义变更必须进入 `BehaviorContract`
6. 做 complexity / divergence 判定
   - 产出 `ComplexityAssessment`
   - 生成 `strategy_origin`
7. 做 compat / migration 判定
   - 命中 compat layer、adapter、task split、migration window 时，必须补齐对应方案
8. 汇总 blocker
   - 生成所有 `ContractCompatibilityResult`
   - 应用 blocker priority
9. 只有在不存在 `blocks-merge` / `blocks-ship` 结果时，才允许进入实现

禁止事项：

- 不允许在 discovery 未完成前直接修改旧语义
- 不允许把“同文件”当作“可直接改动”的豁免条件
- 不允许先实现后补 blocker 解释

标准 discovery 最低证据要求：

- `symbol / function`
  - 至少 `symbol-reference-search` + `import-graph`
- `api`
  - 至少 `api-client-grep` + 前端 usage scan + 服务端 route/handler 对位
- `entity / dto-field / event-field`
  - 至少 `dto-type-usage` + `event-usage-search`
  - 若涉及持久化，追加 repository / query / serializer / validator 搜索
- `ui-anchor / layout-container`
  - 至少 `ui-usage-scan` + `selector-search|snapshot-scan` + `style-source-scan`

跨栈强制要求：

- 后端 API / DTO / event 变更必须扩展到前端 `hook / store / page / widget / form / table / detail view`
- 前端页面新增重元素时，必须回溯对应 API、selector、store、layout container 和 style source

### 8. 多 blocker 并发优先级

默认优先级：

1. `P0`：eligibility 未收敛的前置 gap 类（封闭集合）
   - `IMPACT_LOCKED_HIT_GAP_UNRESOLVED`
   - `REGISTRY_FRESHNESS_STALE_LOCKED_HIT`
2. `P1`：eligibility 已收敛且直接变更不允许类
   - `IMPACT_HARD_STOP_REQUIRED`
   - `INCOMPATIBLE_MUTATION_CONFLICT`
   - `MUTATION_NOT_ELIGIBLE`
   - `COMPAT_ADAPTER_BOUNDARY_MISSING`
   - `COMPAT_LAYER_REQUIRED_BUT_MISSING`
3. `P2`：迁移缺失类
   - `MIGRATION_PLAN_REQUIRED_BUT_MISSING`
   - `MIGRATION_PLAN_INCOMPLETE`
   - `MIGRATION_PHASE_ORDER_INVALID`
   - `MIGRATION_RUNTIME_STATE_UNDECLARED`
4. `P3`：contract 破坏类
   - `LAYOUT_CONTRACT_BREAK`
   - `BEHAVIOR_CONTRACT_BREAK`
5. `P4`：链式风险升级类
   - `LINKED_REGRESSION_EARLY_STOP`

收敛规则：

- 多 blocker 同时命中时，必须全部输出，不能只报一个
- 若对象仍存在 `P0` 封闭集合中的未消解前置 gap，优先输出对应 `P0` 根因 blocker，不得提前把同一语义收敛成 `MUTATION_NOT_ELIGIBLE`
- 只有在 `MutationEligibilityAssessment.assessment_status=completed` 且结果为 `not-eligible` 时，才输出 `P1/MUTATION_NOT_ELIGIBLE`
- 解决顺序按优先级从高到低
- `P0` / `P1` 未关闭前，不允许推进 `P2-P4` 修复性实现
- 如果低优先级 blocker 是由高优先级 blocker 派生，则根因修复后必须重新跑完整 discovery，而不是沿用旧影响集合

# 传播治理 v3 计划（补齐发现机制、UI 机器锚点、兼容性错误分类）

## Summary

在 v2 方案基础上再补 3 个执行闭环缺口：

- 影响集合不只要求“列出来”，还要求“基于可复现发现机制”
- UI contract 不只停留在语义锚点，还要求绑定至少一种 machine-checkable anchor
- `contract-compatibility` 不只扩语义，还要定义标准错误类型，避免后续检查结果失控

仍然复用现有文档结构，不新增新的治理文档，也不新增新的强制 validation slot。  
这次的重点是把“传播分析、UI 锚点、兼容性检查”变成**可证据化、可报错、可停机**。

## Key Changes

### 1. 影响集合的发现机制

把“影响集合必须列出”升级为“影响集合必须附带发现依据”。

新增规则：

- 任何传播分析都必须记录至少一种可复现搜索路径，否则视为不完整
- 高风险传播建议要求至少两类搜索依据交叉确认
- 如果无法提供发现依据，默认进入停机条件，不允许继续做破坏旧语义的实现

允许的最小发现机制类型：

- `symbol reference search`
- `import graph`
- `API client grep`
- `DTO / type usage search`
- `event usage search`
- `UI usage scan`
- `selector / test-id usage search`
- `snapshot / mock / fixture scan`

规则落点：

- `CURRENT_TASK.md` 在命中传播条件时必须新增记录：
  - `发现依据`
  - `搜索入口`
  - `未确认传播点`
- `CONTRACTS.md -> ## 三、变更规则` 明确：
  - 影响集合必须基于可复现发现机制
  - 无发现依据的影响集合视为不完整
- `WORKFLOW_PROTOCOL.md` 明确：
  - 传播分析是“evidence-backed enumeration”，不是自由发挥
- `BASELINES.md -> 兼容性基线` 可补充：
  - 高风险 API / DTO / entity 变更的最小发现证据要求

推荐的对象到发现机制映射：

- 符号 / 方法 / 导出：`symbol reference search` + `import graph`
- 参数 / 返回字段：`type usage search` + `consumer grep`
- DTO / event / entity：`DTO type usage` + `mapper / validator / fixture scan`
- API：`API client grep` + `consumer registry`
- UI anchor：`component usage scan` + `selector / test-id search`

### 2. UI contract 的 machine-checkable 最小锚点

把 UI contract 从纯语义约束升级为“语义 + 可绑定对象”。

新增规则：

- 所有 `🔒` UI 锚点必须至少绑定一种稳定标识
- 所有 `🔒` UI 关系必须能落到两个已绑定锚点之间
- 没有 machine-checkable anchor 的 UI 锁定项，不算合格锁定项

允许的 machine-checkable anchor 形式：

- `data-testid`
- 稳定 selector anchor
- 稳定组件路径
- 稳定组件 key / slot id
- 约定的 DOM role + label 组合
- 固定渲染容器 id / region id

建议优先级：

1. `data-testid`
2. 稳定 selector / region id
3. 组件路径 + 稳定 slot 名称

UI contract 新表达要求：

- `ui::OrdersPage/HeaderActions.SearchBar`
  - machine anchor: `data-testid=orders-search-bar`
- `ui::OrdersPage/PrimaryCTA`
  - machine anchor: `data-testid=orders-primary-cta`
- `ui::OrdersPage/HeaderActions.SearchBar -> PrimaryCTA [left-of, aligned-top]`
  - 两端都必须有 machine-checkable anchor
- `ui::OrdersPage/StickyFilters`
  - region anchor: `data-testid=orders-sticky-filters`

新增 UI 规则：

- 锁定的不只是元素，还要锁关系
- 锁定的不只是视觉语义，还要锁最小 DOM / selector 锚点
- 新增元素进入允许扩展区时，必须保留旧 anchor 不变
- 旧 test id / anchor id 默认不可移除，除非完成替代迁移并更新契约

文档落点：

- `CONTRACTS.md` 增加 UI 锚点条目模板
- `CURRENT_TASK.md` 在命中 UI 传播时记录：
  - 受影响 UI anchors
  - 受影响 UI relations
  - 关键 smoke check / visual check
- `WORKFLOW_PROTOCOL.md` 的 frontend/fullstack 特化中补：
  - machine-checkable UI anchors
  - UI anchor regression
- `BASELINES.md` 的兼容性基线补：
  - 锁定 UI anchors 的替换 / 淘汰前提

### 3. contract-compatibility 的错误类型体系

把 `contract-compatibility` 从“大杂烩检查名”补成有标准错误分类的验证语义。

本轮不新增新的 validation slot，但定义统一错误类型前缀和分类。

建议错误命名空间：

- `CONTRACT_`：通用兼容性错误
- `IMPACT_`：传播发现与影响集合错误
- `UI_`：UI contract 错误
- `COMPAT_`：兼容层 / 迁移窗口错误

最小错误类型集：

- `IMPACT_DISCOVERY_MISSING`
  - 没有发现依据
- `IMPACT_SET_INCOMPLETE`
  - 影响集合不完整
- `IMPACT_CONSUMER_UNCONFIRMED`
  - 存在未确认 consumer
- `CONTRACT_SYMBOL_BREAK`
  - 锁定符号被破坏
- `CONTRACT_PARAM_BREAK`
  - 参数语义 / 默认行为被破坏
- `CONTRACT_RETURN_FIELD_BREAK`
  - 返回字段删除、重命名或语义变化
- `CONTRACT_DTO_BREAK`
  - DTO / event / entity 字段兼容性破坏
- `CONTRACT_API_CONSUMER_BREAK`
  - API 对现有 consumer 产生破坏
- `UI_ANCHOR_BREAK`
  - 锁定 UI anchor 缺失、替换或失效
- `UI_RELATION_BREAK`
  - 锁定 UI 关系被破坏
- `UI_REGION_REFLOW_BREAK`
  - 禁止扰动区 / 冻结区被重排
- `COMPAT_STRATEGY_MISSING`
  - 命中锁定对象但未定义兼容策略
- `COMPAT_WINDOW_VIOLATION`
  - 在迁移完成前提前移除旧行为
- `COMPAT_REMOVAL_PRECONDITION_UNMET`
  - removal precondition 未满足

规则：

- `contract-compatibility` 的输出至少要包含：
  - `error_code`
  - `object_path`
  - `severity`
  - `evidence`
  - `suggested_resolution`
- 同一个结果不得只写“契约不兼容”，必须能归到上面某一类
- 协议只先定义错误类型，不强制现在把每类拆成独立 runner

## Test Plan

必须覆盖以下测试与样例：

- 命中传播条件但未写发现依据时，任务包被判为不完整
- 仅列了部分 consumer、无搜索入口时，触发 `IMPACT_SET_INCOMPLETE`
- UI 锁定项无 `data-testid` / selector anchor / 稳定绑定时，触发 UI contract 不合格
- UI 锁定关系的任一端无 machine anchor 时，不能作为有效锁定关系
- API 多 consumer 场景下删除旧字段，返回 `CONTRACT_API_CONSUMER_BREAK`
- 改默认参数行为但未改函数名，返回 `CONTRACT_PARAM_BREAK`
- 提前移除 dual field / v1 API，返回 `COMPAT_WINDOW_VIOLATION`
- 普通小改动未命中传播条件时，仍可保持轻流程

验证入口至少包括：

- `bun run test:workflow-docs`
- 相关 protocol / validation tests
- generated docs freshness checks

## Assumptions

- 本轮先把“发现机制”定义为证据要求，不强制实现全自动引用图分析
- 本轮先定义 `contract-compatibility` 的标准错误分类，不强制拆分多个独立 validation entrypoint
- UI machine-checkable anchor 不强制统一为 `data-testid`，但所有锁定 UI 项必须至少有一种稳定绑定
- `consumer registry` 仍归属 `CONTRACTS.md`
- `compatibility lifecycle` 仍归属 `BASELINES.md`
- 这轮仍属于协议语义与文档 contract 扩展，建议协议版本从 `0.3.0` 再提升到 `0.4.0`

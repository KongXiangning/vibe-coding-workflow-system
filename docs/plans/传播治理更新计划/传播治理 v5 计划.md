# 传播治理 v5 计划（证据聚合、复杂度上限、兼容层强制切换）

## Summary

在 v4 基础上继续补两个执行层硬规则：

- 多来源 `evidence` 的聚合与冲突处理规则
- 传播分析的复杂度上限与超限后的默认降级策略

这轮的目标不是再扩理念，而是让传播治理在复杂项目里仍然可执行、可停机、可降级。  
默认策略确定为：

- `evidence aggregation`: `union + conflict escalation`
- `over-limit policy`: `禁止直改，走兼容层`
- `threshold style`: `中等阈值`

## Key Changes

### 1. Evidence Aggregation Strategy

为多来源发现机制正式定义聚合规则，避免 `symbol search`、`grep`、`API scan`、`selector scan` 给出不同结果时无从判断。

新增 `EvidenceAggregation` 规则：

- 默认聚合策略：`union`
- 所有 evidence 命中的对象取并集，形成 `candidate impact set`
- 若不同 evidence 对同一对象的“是否为 consumer / 是否为 locked hit / 是否为 relation endpoint”结论冲突，则进入 `conflict escalation`
- 冲突对象必须进入：
  - `unresolved gaps`
  - `待确认问题`
  - 或直接触发停机条件

新增 confidence 合并原则：

- 每条 `EvidenceRecord` 自带 `confidence`
- 聚合后对象的 `aggregated_confidence` 取以下规则：
  - 多个高置信一致命中：`high`
  - 高置信与低置信冲突：降为 `medium`，并标记 gap
  - 多来源均不完整或互相矛盾：`low`
- 任一 `low` 且命中 `🔒` 契约对象，默认触发停机或人工确认

新增 gap 升级条件：

以下任一成立，`unresolved gap` 升级为 blocker：

- 命中锁定符号 / 锁定 API / 锁定 UI anchor
- 涉及返回字段、DTO、event、entity 语义变化
- 涉及冻结区 / 禁止扰动区 UI
- evidence 结果数量差异超过阈值
- 存在“可能 consumer”但无法确认是否已迁移

新增最小聚合结构：

```yaml
aggregation_strategy: union
sources:
  - <EvidenceRecord ref>
candidate_impact_set:
  - <object_path>
conflicts:
  - object_path: <string>
    conflict_reason: <string>
    participating_evidence:
      - <EvidenceRecord ref>
aggregated_confidence: <low|medium|high>
unresolved_gaps:
  - <string>
```

默认权威原则：

- 不采用单一 priority source 作为绝对 authoritative
- 仅在具体对象类型上定义推荐优先级，用于解释冲突，不用于覆盖并集
- 推荐优先级：
  - symbol / type refs 高于纯 grep
  - consumer registry 高于临时任务 grep
  - locked UI anchor registry 高于视觉主观判断

### 2. 传播复杂度上限控制

为传播分析定义默认复杂度边界，防止在大项目里无限向下展开。

新增默认复杂度指标：

- `max_propagation_depth`
- `max_direct_consumers`
- `max_total_candidate_consumers`
- `max_cross-boundary_hops`

推荐默认值采用中等阈值：

- `max_propagation_depth: 3`
  - 例：定义处 → 直接 consumer → 二级 consumer → 三级验证对象
- `max_direct_consumers: 8`
- `max_total_candidate_consumers: 20`
- `max_cross-boundary_hops: 2`
  - 例：DTO → API → UI，或 symbol → service → page

复杂度超限时的默认规则：

- 禁止继续直接修改旧符号 / 旧 API / 旧 UI 锚点 / 旧字段语义
- 必须切换到兼容层策略：
  - adapter
  - wrapper
  - mapper
  - decorator / `AA`
  - dual field
  - v2 API
  - 新 slot / 新 region 扩展
- 必要时强制拆分任务，但默认第一动作不是“继续枚举”，而是“停止直改”

新增超限判定结构：

```yaml
complexity_assessment:
  propagation_depth: <number>
  direct_consumers: <number>
  total_candidate_consumers: <number>
  cross_boundary_hops: <number>
  threshold_status: <within-limit|over-limit>
  forced_strategy: <direct-change|compatibility-layer|split-task>
```

默认 forced strategy：

- `within-limit`:
  - 可继续传播分析并考虑直接修改
- `over-limit`:
  - 默认 `compatibility-layer`
- 若 `over-limit` 且同时存在 unresolved gaps:
  - 直接停机，不进入实现

### 3. 复杂度与停机规则联动

把复杂度阈值与现有停机条件正式联动。

新增硬规则：

- 超过复杂度阈值但仍尝试原地修改旧语义，视为协议违规
- 超限且 evidence 冲突未消解，必须停机
- 超限且 consumer registry 不完整，必须停机
- 超限且 UI anchor replacement 无 successor / transition window，必须停机

这意味着：

- “复杂”不再是继续搜索的理由
- “复杂且共享”默认转向兼容层，而不是继续硬改

### 4. Public Interfaces / Contracts To Add

本轮在已有三个结构外，再补两个公开结构：

- `EvidenceAggregation`
- `ComplexityAssessment`

完整公开结构集为：

- `EvidenceRecord`
- `EvidenceAggregation`
- `UIAnchorReplacement`
- `ContractCompatibilityResult`
- `ComplexityAssessment`

## Test Plan

必须覆盖以下场景：

- 两种 evidence 命中 consumer 数量不同，聚合结果取并集并生成 unresolved gap
- 高置信 symbol ref 与低置信 grep 冲突时，aggregated confidence 降级且触发 gap
- 命中锁定对象但 evidence 冲突未消解，触发 `IMPACT_CONSUMER_UNCONFIRMED` 或 `IMPACT_SET_INCOMPLETE`
- 传播深度 / consumer 数量超限时，`forced_strategy` 自动为 `compatibility-layer`
- 超限场景仍尝试直接修改旧 API / 旧字段 / 旧 UI anchor，返回 blocker 级结果
- UI 大页面新增重元素导致冻结区重排，同时复杂度超限，必须停止直改
- 普通小变更未超限时，仍允许直接传播分析与轻流程

验证入口至少包括：

- `bun run test:workflow-docs`
- 相关 protocol / validation tests
- generated docs freshness checks

## Assumptions

- `union + conflict escalation` 作为默认 evidence aggregation strategy
- 中等阈值作为全局默认：
  - `depth=3`
  - `direct consumers=8`
  - `total candidate consumers=20`
  - `cross-boundary hops=2`
- 超限后默认切到兼容层，而不是继续无限枚举
- 若 target project 有更严格需求，可在项目层基线中收紧阈值，但不应放宽到允许超限直改 `🔒` 对象
- 本轮依然先定义协议、schema、模板与校验语义，不要求实现自动依赖图推理器
- 这轮继续属于协议与文档 contract 扩展，建议协议版本从 `0.5.0` 提升到 `0.6.0`

# 传播治理 v6 计划（超限分级策略 + Evidence 差异阈值）

## Summary

在 v5 基础上再补两个裁决层规则：

- `complexity over-limit` 从单一后果升级为按超限维度分级响应
- `evidence conflict escalation` 从定性描述升级为显式数值阈值

这轮的目标是让系统在复杂项目里不仅能“停下”，还能根据超限类型选择更合适的降级路径。

默认新增两套规则：

- `over_limit_policy`：按 depth / consumers / cross-boundary / multiple-metrics 分级
- `evidence_diff_threshold`：默认 `absolute_diff=3`、`relative_diff_ratio=0.5`

## Key Changes

### 1. Complexity Over-Limit Policy 分级化

把原来的：

- `over-limit -> 禁止直改 -> compatibility-layer`

细化为按触发维度分级响应。

新增标准结构：

```yaml
over_limit_policy:
  if:
    depth_exceeded: true
  then:
    - recommend_task_split

  if:
    total_consumers_exceeded: true
  then:
    - enforce_compat_layer

  if:
    cross_boundary_exceeded: true
  then:
    - enforce_adapter_boundary

  if:
    multiple_metrics_exceeded: true
  then:
    - hard_stop
```

默认解释规则：

- `depth_exceeded`
  - 问题本质是传播链太长，默认优先建议拆任务
  - 不一定立刻停机，但禁止继续无边界下钻
- `total_consumers_exceeded`
  - 问题本质是共享面过大，默认强制兼容层
  - 不允许继续直接改旧语义
- `cross_boundary_exceeded`
  - 问题本质是跨层 / 跨边界影响过宽，默认强制 adapter boundary
  - 如 DTO mapper、API facade、client adapter、slot wrapper
- `multiple_metrics_exceeded`
  - 说明同时存在复杂链路、共享面、跨边界爆炸
  - 默认 `hard_stop`

新增动作语义：

- `recommend_task_split`
  - 当前任务必须拆分为更小迁移单元后再继续
- `enforce_compat_layer`
  - 默认引入 wrapper / mapper / dual field / v2
- `enforce_adapter_boundary`
  - 必须在边界层解决，不允许把改动直接传播进旧 consumer
- `hard_stop`
  - 停止实现，只允许输出分析结果、冲突点、建议迁移路径

补充决策顺序：

1. 先做 `ComplexityAssessment`
2. 再套用 `over_limit_policy`
3. 得到 `forced_strategy`
4. 若结果是 `hard_stop`，不得进入实现
5. 若结果是 `recommend_task_split`，不得继续扩大当前任务边界

### 2. Evidence 数量差异阈值显式化

把“evidence 结果数量差异超过阈值”写成明确规则。

新增默认阈值：

```yaml
evidence_diff_threshold:
  absolute_diff: 3
  relative_diff_ratio: 0.5
```

判断方式：

- `absolute_diff = abs(count_a - count_b)`
- `relative_diff_ratio = absolute_diff / min(nonzero(count_a, count_b))`

默认升级条件：

- 若 `absolute_diff > 3`，进入差异升级判断
- 若 `relative_diff_ratio > 0.5`，进入差异升级判断
- 两者任一成立，则该 evidence pair 视为 `significant divergence`
- 若 `significant divergence` 命中锁定对象、共享 API、锁定 UI、DTO/event/entity 变更，默认升级为 unresolved gap

示例：

- `5 vs 8`
  - `absolute_diff = 3`
  - `relative_diff_ratio = 0.6`
  - 命中相对差异阈值，按高风险对象升级
- `5 vs 20`
  - `absolute_diff = 15`
  - `relative_diff_ratio = 3.0`
  - 必升级
- `20 vs 22`
  - `absolute_diff = 2`
  - `relative_diff_ratio = 0.1`
  - 默认不升级

补充边界规则：

- 当一个 evidence 的结果为 0，另一个非 0：
  - 若对象为锁定项或共享项，默认直接进入 unresolved gap
- 数量接近不代表语义一致
  - 若对象集合重叠很低，即使数量接近，也仍可升级
- 所以数量阈值只是“初步升级条件”，不是唯一冲突判断依据

### 3. Evidence Aggregation 与 Complexity 联动

把新的数量阈值与复杂度评估联动。

新增联动规则：

- 若 evidence 差异显著且 `cross_boundary_exceeded=true`
  - 默认 `hard_stop`
- 若 evidence 差异显著且 `total_consumers_exceeded=true`
  - 默认 `enforce_compat_layer`
- 若 evidence 差异显著但仅 `depth_exceeded=true`
  - 默认先 `recommend_task_split`
- 若 evidence 差异显著并命中 UI relation / frozen region
  - 直接升级为 blocker

也就是说：

- “复杂但一致”可以降级处理
- “复杂且证据分裂”必须更强停机

### 4. Public Interfaces / Contracts To Add

在 v5 的 5 个公开结构上补两个字段族：

- `ComplexityAssessment.over_limit_policy_result`
- `EvidenceAggregation.significant_divergence`

推荐结构：

```yaml
complexity_assessment:
  propagation_depth: <number>
  direct_consumers: <number>
  total_candidate_consumers: <number>
  cross_boundary_hops: <number>
  exceeded_metrics:
    - <depth|direct_consumers|total_consumers|cross_boundary_hops>
  threshold_status: <within-limit|over-limit>
  forced_strategy: <direct-change|compatibility-layer|adapter-boundary|split-task|hard-stop>
```

```yaml
evidence_aggregation:
  aggregation_strategy: union
  candidate_impact_set:
    - <object_path>
  significant_divergence: <true|false>
  divergence_reason:
    - <string>
  unresolved_gaps:
    - <string>
```

## Test Plan

必须覆盖以下场景：

- `depth_exceeded=true` 且其他指标正常，结果为 `recommend_task_split`
- `total_consumers_exceeded=true`，结果为 `enforce_compat_layer`
- `cross_boundary_exceeded=true`，结果为 `enforce_adapter_boundary`
- `multiple_metrics_exceeded=true`，结果为 `hard_stop`
- `5 vs 8` 在高风险对象上触发 `significant_divergence`
- `20 vs 22` 不触发数量级升级
- 一个 evidence 为 0、另一个非 0 且命中锁定对象，直接升级 unresolved gap
- evidence divergence 与 cross-boundary 同时出现时，升级为更强 blocker
- over-limit 但 evidence 一致时，可降级为 compat/adapter/split-task，而不是一律 hard-stop
- over-limit 且 evidence divergence 严重时，不允许继续实现

验证入口至少包括：

- `bun run test:workflow-docs`
- 相关 protocol / validation tests
- generated docs freshness checks

## Assumptions

- 默认 `over_limit_policy` 分级生效
- 默认 `evidence_diff_threshold`：
  - `absolute_diff=3`
  - `relative_diff_ratio=0.5`
- 数量阈值只用于初步升级，不替代对象级语义比对
- 项目可以在基线中收紧阈值，但不应允许对 `🔒` 对象在超限时继续直接修改
- 本轮仍优先定义协议、schema、模板与校验语义，不要求实现自动 evidence comparator
- 这轮继续属于协议与文档 contract 扩展，建议协议版本从 `0.6.0` 提升到 `0.7.0`

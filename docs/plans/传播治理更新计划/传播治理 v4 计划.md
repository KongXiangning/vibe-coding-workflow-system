# 传播治理 v4 计划（证据标准化、UI Anchor 迁移、错误码 Gate 映射）

## Summary

在 v3 方案上继续补 3 个硬落地点：

- 为传播分析定义统一的 `evidence schema`
- 为 UI machine anchor 定义正式的 `replacement lifecycle`
- 为 `contract-compatibility` 错误码定义 `blocker mapping`

本轮仍复用现有文档结构，不新增新的治理文档，也不新增新的强制 validation slot。  
重点是把传播治理从“可表达”推进到“可记录、可迁移、可阻断”。

## Key Changes

### 1. 发现依据标准化为 Evidence Schema

把“发现依据”从自由文本升级为统一结构。所有命中传播条件的任务，必须记录至少一个 `EvidenceRecord`；高风险变更默认要求两个不同机制的 `EvidenceRecord`，否则必须写明原因。

最小 `EvidenceRecord` 结构：

```yaml
mechanism: <symbol-reference-search|import-graph|api-client-grep|dto-type-usage|event-usage-search|ui-usage-scan|selector-search|snapshot-scan>
query_or_entrypoint: <string>
scope: <string>
result_summary: <string>
confidence: <low|medium|high>
gaps:
  - <string>
```

规则：

- `mechanism` 必须是协议允许的枚举值
- `query_or_entrypoint` 必须能复现搜索入口，不允许只写“全局搜了一下”
- `scope` 必须说明搜索边界，如目录、模块、服务层、前端消费层
- `result_summary` 必须说明命中的对象，不允许只写“有一些引用”
- `confidence` 必须是显式等级
- `gaps` 必须列出未确认传播点；没有 gaps 时写空数组或“无”

补充要求：

- 高风险对象包括：
  - 锁定符号
  - 锁定 API
  - 实体 / DTO / event / schema 变更
  - 锁定 UI anchor / relation
- 高风险对象默认要求至少两种不同 `mechanism`
- 如果只能提供一种机制，必须在 `待确认问题` 中说明原因并触发人工确认或停机判断

文档落点：

- `CURRENT_TASK.md`
  - 在传播触发时新增 `发现依据` 记录块
- `CONTRACTS.md -> ## 三、变更规则`
  - 明确“无可复现 evidence schema 的影响集合视为不完整”
- `WORKFLOW_PROTOCOL.md`
  - 正式定义 `EvidenceRecord` 为传播分析的最小证据结构
- `FILE_SCHEMAS.md`
  - 约束传播类任务包必须支持该结构

### 2. UI Machine Anchor Replacement Lifecycle

把 UI anchor 的替换过程正式建模，类似 API deprecation，而不是“允许替换即可”。

新增 `UIAnchorReplacement` 结构：

```yaml
old_anchor: <ui object path + machine anchor>
successor_anchor: <ui object path + machine anchor>
transition_window: <version/window/task-cycle>
alias_policy: <dual-anchor|alias-selector|no-alias-with-reason>
alias_details: <string>
relation_migration:
  - from_relation: <old relation>
    to_relation: <new relation>
removal_precondition: <string>
verification: <string>
```

规则：

- 旧 anchor 被替换时，必须声明 `successor_anchor`
- 必须有 `transition_window`
- 默认要求一个周期内保留双锚点或 alias
- 如果不保留 alias，必须明确写明原因
- UI relation 迁移时，关系两端 anchor 的 successor 都必须记录
- 未满足 `removal_precondition` 前，不允许移除旧 anchor
- 锁定 UI anchor 的替换必须更新契约与任务包，不能只改代码

默认迁移策略：

- 优先 `dual-anchor`
- 次选 `alias-selector`
- 只有在明确说明无法双锚点且不会破坏验证入口时，才允许 `no-alias-with-reason`

文档落点：

- `CONTRACTS.md`
  - UI 锁定项支持旧 anchor / successor / relation migration 记录
- `BASELINES.md -> 兼容性基线`
  - 记录 UI anchor 替换窗口与淘汰前提
- `CURRENT_TASK.md`
  - 命中 UI 迁移时必须记录：
    - 受影响 anchors
    - successor anchors
    - relation migration
    - verification entry
- `WORKFLOW_PROTOCOL.md`
  - 将 UI anchor replacement 视为 compatibility lifecycle 的一部分

### 3. 错误码的 Blocker Mapping

保留单一 `contract-compatibility` 槽位，但增加标准错误分类到 gate 的映射原则。

定义统一结果结构：

```yaml
error_code: <string>
object_path: <string>
severity: <warning|error|critical>
default_blocker_level: <warning-only|blocks-merge|blocks-ship>
evidence:
  - <EvidenceRecord ref or summary>
suggested_resolution: <string>
```

错误码与默认 gate 映射：

- `IMPACT_DISCOVERY_MISSING`
  - 默认：`blocks-merge`
- `IMPACT_SET_INCOMPLETE`
  - 默认：`blocks-merge`
- `IMPACT_CONSUMER_UNCONFIRMED`
  - 默认：`blocks-merge`
- `CONTRACT_SYMBOL_BREAK`
  - 默认：`blocks-merge`
- `CONTRACT_PARAM_BREAK`
  - 默认：`blocks-merge`
- `CONTRACT_RETURN_FIELD_BREAK`
  - 默认：`blocks-merge`
- `CONTRACT_DTO_BREAK`
  - 默认：`blocks-merge`
- `CONTRACT_API_CONSUMER_BREAK`
  - 默认：`blocks-merge`
- `UI_ANCHOR_BREAK`
  - 对锁定 UI 默认：`blocks-merge`
- `UI_RELATION_BREAK`
  - 对锁定 UI 默认：`blocks-merge`
- `UI_REGION_REFLOW_BREAK`
  - 对冻结区 / 禁止扰动区默认：`blocks-merge`
- `COMPAT_STRATEGY_MISSING`
  - 默认：`blocks-merge`
- `COMPAT_WINDOW_VIOLATION`
  - 默认：`blocks-merge`
  - 在 ship/deploy gate 若仍存在，升级为：`blocks-ship`
- `COMPAT_REMOVAL_PRECONDITION_UNMET`
  - 默认：`blocks-merge`
  - 在 ship/deploy gate 若仍存在，升级为：`blocks-ship`

统一原则：

- merge 前发现的兼容性破坏默认至少阻断 merge
- 与迁移窗口、淘汰前提相关的错误，在 ship/deploy gate 可进一步升级为 `blocks-ship`
- `warning-only` 仅适用于未锁定对象、非破坏性观察项，不适用于任何 `🔒` 契约命中项
- 无法分类的错误不得降级为泛化 warning，必须作为协议不合格处理

### 4. Public Interfaces / Contracts To Add

本轮新增的规范接口：

- `EvidenceRecord`
- `UIAnchorReplacement`
- `ContractCompatibilityResult`

它们是协议与文档的公开结构约束，后续模板、生成器、校验器、运行时摘要都按这三类结构对齐。

## Test Plan

必须覆盖以下场景：

- 命中传播条件但 `发现依据` 不是结构化 evidence schema，判为不完整
- 只写“全局搜索”但没有 `query_or_entrypoint` / `scope` / `gaps`，触发 `IMPACT_DISCOVERY_MISSING`
- 高风险变更只提供一个 evidence record 且无理由，触发 `IMPACT_SET_INCOMPLETE`
- 锁定 UI anchor 被替换但未声明 `successor_anchor`，触发 `UI_ANCHOR_BREAK`
- UI relation 迁移只替换一端 anchor，触发 `UI_RELATION_BREAK`
- 旧 anchor 直接删除、无过渡窗口或 alias 策略，触发 `COMPAT_STRATEGY_MISSING`
- 迁移窗口未结束却移除旧 anchor / 旧字段 / 旧 API，触发 `COMPAT_WINDOW_VIOLATION`
- removal precondition 未满足却淘汰兼容层，触发 `COMPAT_REMOVAL_PRECONDITION_UNMET`
- 错误结果缺少 `default_blocker_level` 或 `object_path`，视为 validation result 不合格
- 普通未锁定 UI 或普通小改动仍可保持轻流程，不被错误升级

验证入口至少包括：

- `bun run test:workflow-docs`
- 相关 protocol / validation tests
- generated docs freshness checks

## Assumptions

- 本轮先标准化 evidence schema，不强制实现自动 import graph / symbol graph 构建器
- 本轮先标准化 UI anchor replacement lifecycle，不强制实现自动 alias 检测器
- blocker mapping 先定义为默认规则，允许后续在具体项目里做更严格升级，但不允许对 `🔒` 契约命中项降级为 `warning-only`
- `consumer registry` 继续归属 `CONTRACTS.md`
- `compatibility lifecycle` 继续归属 `BASELINES.md`
- 这轮继续属于协议与文档 contract 扩展，建议协议版本从 `0.4.0` 提升到 `0.5.0`

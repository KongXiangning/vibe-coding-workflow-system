# 使用 maintain-project 维护目标、完整需求与实施安排

项目级实施安排对外称 **Implementation Roadmap（项目实施路线图）**，内部仍是 `plan`。
已有需求但没有路线图时可直接要求“按现有需求整理首版实施路线图”；保留已有需求与
历史 Task，未来 Task 按需创建。新建建议 `docs/product/IMPLEMENTATION_ROADMAP.md`，旧
`PLAN.md` 不需改名。它与 Agent Plan Mode、单个 Task Plan 分开。

支持完整或局部规划。例如 24 项需求只安排近期 6 项，其余 18 项继续可见；跨阶段
REQ-20 保留一个身份，W20-A 与 W20-B 各自安排，基础任务结束不等于完整需求满足。
v4/v5 路线图可保存实际已核对成员、定义及安排的基线。再次用于选择工作时，读取结果区分
当前已核对、变化待核对、已核对但明确暂缓、无法确认；需求手工修改或新增即使没有
Change 仍可发现。只有真实完成影响核对才能更新基线；只读不会制造记录。

多份路线图分别选定适用范围，不按修改时间合并。需求保存成功而路线图失败时保留
已保存内容，只补失败部分。缺少路线图、旧格式或差异均不阻断直接 Task 流程；任务
续接优先，不在每次步骤、关闭或 Git 操作扫描全库。详情见[契约第 11 节](../product/project-maintenance/document-contract.md#11-v4implementation-roadmap-与规划核对基线)、[核对示例](../product/project-maintenance/examples/roadmap-reconciliation.md)和[本轮验证范围](../ops/vnext-roadmap-validation.md)。

在目标项目调用 `$maintain-project`，直接说明要整理的资料、当前决定或待核对结果。它把目标、完整需求、设计、安排和交付依据保存在项目自己的文档中；Task 继续由原有 vNext 管理，TraceLens 负责只读展示。

本指南按当前源码版本 **`0.24.15`** 说明用法，包含“项目实施路线图与一致性方案”和“需求实施关联与进度聚焦方案”。软件版本与文档格式分别核对：路线图基线可使用 v4/v5，贡献分类使用 v5；已有文件可以混用，不要求全项目迁移。软件来源与格式选择见第 8 节。

历史验收记录各自保留原范围：`0.24.6` 的完整需求、范围报告与展示见[实施与验收交接](../ops/full-scope-planning-evidence/实施与验收交接.md)；`0.24.8` 的结构持续维护见[采用结构示例](../product/project-maintenance/examples/adopted-structure.md)；路线图基线见[路线图验证记录](../ops/vnext-roadmap-validation.md)；`0.24.10` 的贡献分类、隔离安装升级和有限宿主案例见[v5 验证记录](../ops/binding-progress-v5-validation.md)。源码能力、本地包、目标项目已安装字节及消费者展示分别核对，不能用 npm latest 或版本号替代实际验收。

## 1. 先把当前要做的产品说清楚

### 总目标、子目标、父子需求和共享功能

总目标描述项目要达到什么结果；子目标可以描述某个阶段或独立结果。父需求保留完整能力和验收边界，子需求描述它的组成义务。例如，资料可追溯是总目标，固定样本可用是一个子目标，原文存储、导入、查询是需求；来源定位可以是存储、导入和查询共同使用的一个功能点。

沿用已有 v3 的 `part_of` 表达子目标→父目标、子需求→父需求；支撑目标用 `supports`，工程前提用 `depends_on`，它们各自说明不同关系。共享功能保留一个稳定身份和一份当前正文，允许多个父项或目标引用，不复制成几个同名需求。总目标须明确指定，不能从第一个文件或无入边节点猜出。

补子需求默认保留父项身份和范围；改名、移动文件或分批实施也保留身份。真正替代、拆分或合并业务义务时，保留旧身份、退出范围及去向；一条替代关系本身不会让旧项自动退休。只是把实施分成几批时，用工作项或 Task 表达即可。

### 完整当前功能分析与正式增量

新项目或已明确当前交付范围，默认先读原始业务材料形成可审阅的完整功能分析，再安排实施。沿实际用户场景核对输入输出、重要异常与恢复、质量约束、接口组合，形成有依据的能力、边界、验收建议及必要未知。例如，已采纳采集、原文存储、导入和查询四块能力时，不能只写四个标题，也不能因为查询晚实施就把它放到候选。

正式新增需求时，完整分析本次增量及其对父项、共享功能的实际影响。例如新增 BOM 兼容，需要核对输入识别、原文保留、导入异常和下游使用的相关路径；无需重新分析不受影响的全项目。区分新增当前义务、原义细化和未来可选增强，并保留既有验收与排除项。

分析建议不等于采用。依据用户实际采用保存当前定义；已明确采用且授权维护的决定直接落实，不重复询问同一决定。代码现状、推断关联和旧讨论也不自动变成当前义务。

### 已采用的层级要保存为实际结构

例如“按服务端、Web、App 整理已有要求，权限属于服务端；不新增业务”已经明确采用层级时，宿主可复用或建立必要的父需求身份，在当前授权内保存有依据的组成／支撑关系。你无需填写内部编号或逐边确认。父项表示有业务范围、需要核对达成的能力，具体独立功能或质量义务用子需求；纯分类才可用可选 module，平台标签、例子和简单验收细节可留正文。

正式图需要稳定条目和核心 links。分类目录、扩展字段或“已分类”数量可帮助解释，却不能替代实际关系。只要求盘点／比较时提出的新归属、来源冲突或不足的关系仍保留候选／未决；不会批量把所有推断转正，也不会仅因关系由 Agent 整理而永久保持推断。整理身份不增加新的业务指标、设备覆盖或其他承诺。

新增、细化、修改或采用归类时，同一维护过程处理受影响的完整定义、来源、关系和新身份顺序，然后回读形成的正式路径、候选、未归属／未保存部分及只留正文的细项。例如在已有父项下新增一项明确要求，定义与关系应在本次可读取，不需要再发一次“整理需求图”。旧顺序保留，新身份追加；图中展开父子不重排项目数组。

“同次”允许多次 helper 和逐文件保存。发生冲突保留已保存结果，读最新内容后只补失败部分，不重复 Task 或业务操作。没有可靠父项可以保留独立要求；暂停维护、用户要求先实施或入口缺失照常保留开发路径。以上是相关 Skill 实际运行时的维护方法，不是后台监听任意手工修改。参考[有限宿主交互材料](../product/project-maintenance/examples/adopted-structure.md)区分原始输入、确定性回读与宿主判断证据。

局部修复、明确先实施后整理、真正未知的受限探索都可独立使用。完整分析不是每个 Task 的前置门槛；资料、格式或维护失败不能据此阻止正常开发。

## 2. 自然语言请求

不必先选择内部模式，几类意图可以组合。

| 你要做什么 | 可以这样说 | 形成什么结果 |
| --- | --- | --- |
| 整理现状 | 按这两份原始资料整理目标和完整需求，其他业务标明未核对。 | 保留完整正文、来源、已有成果及未知，不只列未完成任务。 |
| 更新决定 | 本期改为单设备，保留离线和错误提示；这项决定已经采用。 | 局部更新当前正文、必要变化依据和安排，保留未变要求与历史。 |
| 规划近期工作 | 四块都属于当前交付，先做导入；以后逐次选下一项。 | 保留完整当前定义，按真实前提安排近期工作；不强制总体计划或提前建所有 Task。 |
| 保存讨论 | 保存这段讨论，分清多个议题和关联，暂不采纳。 | 保存所选原文、观点和关联依据；确认关联与采用观点分别处理。 |
| 对账结果 | 原任务已关闭，但这份新报告显示导入失败；核对实际影响。 | 分清用户报告与实际复现，保留新旧依据，局部维护报告、待核对范围及修复安排。 |
| 核对路线图 | 核对已选的导入路线图与当前需求是否一致，先只分析，不改安排。 | 展示成员、定义及安排差异，保留已有交付、未核对范围和原延期决定。 |
| 重判实施关联 | 核对现有需求关联的任务，区分直接贡献和间接支撑；纠正有充分依据的旧关联。 | 按具体义务核对任务采用范围和结果，同 ID 更正，资料不足的旧值保持待核对。 |

纯讨论可以只给建议。需要保存时复用已有正文和适用计划；不为一个结论另建第二份权威清单。来源只有链接而未取得正文时，只保留链接，不宣称原文已归档。

## 3. 当前范围、需求顺序与实施顺序

`current` 表示目前采用的业务范围，包含已交付、正在实施和准备以后实施的能力。有无 Task、先后实施和是否交付是另外几件事。`planned` 是后续范围，`candidate` 是未采用候选，`retired` 是已退出范围；退出或延期均不表示完成。

v3 引入的项目需求展示顺序 `project.requirement_order` 在 v4/v5 中继续保留。首次按采用的拆分顺序登记；存在唯一可用的 v3/v4/v5 项目条目时，helper 自动把成功保存的新 v2/v3/v4/v5 需求身份按本批次文件及条目顺序追加。用户明确提供或移除顺序时以该选择为准，包括有意留空；不会为登记顺序迁移需求文件。顺序更新失败仍保留已保存需求，只补失败的顺序维护，最后回读实际文件。

只有明确采用重排才改变已有位置。改名、加依赖、插入修复 Task、写报告不会重排。未登记但可读的需求仍有独立入口，不附到已登记顺序中冒充业务排序。

计划中的 `work_items` 顺序只表示该计划的工作安排，Task 内步骤顺序继续服务于该 Task。需求展示顺序、工作安排和工程依赖互不替代；数组先后不证明必须串行，没有依赖声明也不证明可安全并行。

三种规划策略可按阶段或业务范围切换，沿用既有决定，不要求每轮重新选择：

| 策略 | 适用方式 |
| --- | --- |
| 预先规划 | 安排本次全部已知实施范围，说明各部分去向、顺序、前提和延期项；未来 Task 不必先建立。 |
| 持续选取 | 无总体计划也可核对相关需求、已有交付及真实前提，直接选择近期工作并在授权内准备 Task。 |
| 混合规划 | 保留总体方向、阶段或里程碑，细化近期工作；粗略远期实施安排不能省略已采用当前能力的定义与验收。 |

### 项目实施路线图与一致性方案

已有完整需求但没有路线图时，可以要求“基于现有需求、已有交付和真实前提，整理首版项目实施路线图”。保留需求、历史 Task 和工作项身份，安排剩余工作，不预先创建所有未来 Task。只安排近期六项也可以，其余已采用需求继续保持当前范围；同一需求跨阶段实施时保留一个需求身份，用多个工作项说明各阶段覆盖。

明确这次核对的是全部当前需求、某个目标下的需求，还是指定的需求列表。多份路线图分别选定，不按文件时间合并；局部路线图不因其他范围新增需求而自动扩项。支撑和组成关系用于定位所选范围，工程依赖不自动变成业务归属。所选身份有冲突或读取不完整时保留无法确认，不把材料缺失解释成没有需求。

路线图保存一次实际核对过的成员、需求定义、相关目标上下文及实施安排。再次消费时与当前材料比较，手工修改需求或新增未引用需求也能发现差异，无需先补一份 Change。结果分别说明：

| 核对结果 | 对用户意味着什么 |
| --- | --- |
| 当前已核对（current） | 所选范围的成员、定义和安排与核对基线一致；不表示工作已经交付或前置已满足。 |
| 变化待核对（changes-pending） | 存在成员、定义、上下文或安排差异，需要读取实际内容判断影响。 |
| 已核对但明确暂缓（reviewed-deferred） | 当前精确版本已有暂缓决定，风险和未实施工作保留；同版本不重复索要相同决定。 |
| 无法确认（unknown） | 无基线、部分未核对、身份冲突、不可比较或来源不可读；已知差异和历史成果仍可查看。 |

例如，CSV 导入新增“批次历史”义务，要核对哪些工作项需要新增或调整；只是澄清既有错误提示且不影响安排，可以记录该精确版本无需调整的理由。材料未读完时保留旧核对版本及未决项，不能为了消除提示就把基线改成当前版本；后续相关义务再次变化时，原延期决定也要重新核对。

先保存并回读需求与实际安排，再保存真正完成的核对及其来源。只分析不会采用安排或更新基线。需求保存成功而路线图失败时不回滚需求，读取最新材料后只补失败部分。仅纠正贡献分类不会改变需求义务摘要或强迫重排；但原基线若精确引用了整个文件，该文件字节变化仍须单独说明。

选择下一工作时消费已明确选定的适用路线图，核对相应覆盖和真实前提，再按实际授权准备 Task。已有活跃任务或父 Task 续接优先；下一业务事项建议不自动建立、切换或执行任务。没有路线图、旧格式或核对差异都不成为开发门槛。字段、示例和验证范围见[契约第 11 节](../product/project-maintenance/document-contract.md#11-v4implementation-roadmap-与规划核对基线)、[路线图示例](../product/project-maintenance/examples/roadmap-reconciliation.md)和[验证记录](../ops/vnext-roadmap-validation.md)。

已有适用计划就局部维护它。无计划且不需要机器展示顺序时，把选取依据和未决项保存在项目正文；需要按 A、B、C 展示时，可以维护一个小范围计划。切换策略不自动删除计划、换 Task 或重编号。建议下一项不自动授权关闭当前 Task 或启动新工作；已有连续实施授权仍按原范围适用。

## 4. 怎样判断一个目标或需求已有成果

一次评估针对一个目标或需求，在明确目标上下文、约定范围和实际对象版本下判断。目标结果使用自身报告；需求可以在不同目标、范围或对象下有不同报告。固定小样本可用、持续更新可用、某个工作副本、某个提交或发布版，不能合成一个无条件的全局状态。

先采用当前目标的范围声明，再读取报告；旧报告不能反推今天的范围。保存依据、实际检查对象、覆盖与排除、已知成果及待核对项。格式通过、摘要一致、有来源或 Task 关闭都不认证业务判断正确。

| 范围结论 | 应如何理解 |
| --- | --- |
| 已满足 | 明确证据支持该对象在所选范围内满足约定。 |
| 部分满足 | 明确知道哪些部分满足、哪些部分未满足。 |
| 未满足 | 明确证据说明该范围未满足。 |
| 尚未判定 | 缺证据、范围／对象不清，或已知部分有成果而剩余部分未知；已知成果仍保留。 |

例如，固定三份资料的直接存储／重建／定位组合证据可以支持该固定范围的父项结论，不要求每个子项先有报告。若只验证关键词查询，类型筛选、无结果提示及规模适用性尚未知，查询组合应为尚未判定，不能写成部分满足或总体目标已达成。

新增子项本身不递归作废旧的明确范围报告。新增义务确实影响当前父范围时，局部核对覆盖；延期或保存失败要说明新未核对／未保存范围。目标共同定义或本次范围声明改变时，读取器提示当前适用性待核对。只有其他范围声明增删改时，如果可唯一读取并验证原目标完整定义，且目标正文、类型、scope、关系及本范围均一致，需求本范围的报告可继续采用；目标整体评估不享受此豁免。缺少可验证的原目标定义或有待对账材料仍保留对应核对项，也不要求全图复评。

定义依据按条目核验：来源可读取、条目可唯一定位且定义算法／摘要仍与报告一致时，任务关联、展示顺序、换行或同文件其他条目的变化不会让该报告降为尚未判定。整文件摘要不同仍保留为来源历史诊断，不能单独转成需求待核对项；不批量刷新旧报告的依据摘要、核对时间或结论来消除提示。原目标定义核验也遵守这一规则。真实义务、范围、对象变化和新反证仍局部处理；固定执行／日志证据及变化处置来源仍须核验原记录字节。

旧 PASS、已关闭 Task 或恢复旧需求文字都不能直接成为新范围的已满足。新反证即使需求文字未变也要对账或列为待核对。报告的原结论与当前适用性分别显示；正式修正报告保留旧报告，并只在同一精确定位下明确替代。

普通步骤实施和成功的局部测试只记录实际 Task／Step 结果与证据，不自动给相关需求报告添加待核对项，也不要求每一步另写影响结论。任务的正常正向进展累积到已授权的阶段或交付评估；共同 Task、修改同一文件、增加来源或依赖关系本身，都不是跨需求重评的理由。

只有需求义务、验收、职责或采用范围发生实质变化，新失败／反例影响既有覆盖，或到了已授权的阶段／交付评估，才局部对账。例如空 MD 使文书目录导入整体中断，还涉及批量导入的逐项终态与失败隔离。helper 的共享 Task／具体来源候选只帮助定位，实际影响仍由读取业务正文判定；只处理受影响的具体义务，保留其他成果。对尚未处理的实质影响，局部修正报告或保存该原证据为 pending_sources。只读、延期、范围不明或保存失败则报告精确待处理位置，主报告保存不代表已处理其他已知影响。

同一职责决定或反例可以影响多份报告，但只需维护一次有来源的影响判断，明确哪些义务保留、移交或仍未核对，并让适用报告引用该结果。同一变更、相同义务版本和报告范围已有适用处置时，后续普通步骤复用它，不重复添加待核对项、刷新核对时间或索要同一决定。延期仍保留待处理；新的失败、对象／输入适用性变化或义务新版本只核对新增影响，不能用旧处置屏蔽。

待核对原因要区分职责／定义迁移、新反例和历史精确来源适用性变化。源文件字节变化不自动表示业务失败；旧记录缺少原因时保留未知。界面按同一变更归并需要处理的事项，同时保留受影响报告位置，不能把“涉及两份报告”变成两次相同核对。以上不增加审批、每步必填记录或开发门槛。

需要机器复用时，可在所选 v6 范围报告中通过现有读写保存可选的 `evidence_dispositions`。它以固定变化来源、具体义务版本、范围／对象和报告依据约束复用；只有这些依据仍匹配的已处理结果才可复用，延期、真实新反例、来源不可用或依据变化继续可见。旧 v1–v5 报告仍可读取，普通步骤不要求迁移或填写这个字段。详见[文档契约](../product/project-maintenance/document-contract.md)和[局部对账规则](../../runtime/vnext/support/product-maintenance/references/reconcile.md)。

完整功能点评估只维护在一份范围报告中；项目入口和旧进展／实施表保留短摘要及链接。helper 会提示匹配的完整正文，供维护判断是否为镜像；不同对象和运行的独立事实继续保留。使用者仍可直接说“重新评估第 08 项需求并保存”，无需另写关联检查或去重提示词。

## 5. Task 关联与关闭后的局部对账

TaskBinding 是软关联：一个 Task 可服务多个目标／需求，一项需求可由多个 Task 实施、修复、验证或探索。每条关联保留实际身份、角色、具体覆盖及来源；项目计划身份与 Runtime 的计划引用分别使用。一个 Task 内步骤仍引用原 Task 和步骤，不虚构新 Task。

### 需求实施关联与进度聚焦方案

v5 在每条目标／需求关联上区分贡献性质。角色说明任务做了什么，贡献说明这项活动与该需求的具体义务是什么关系。同一 Task 对不同需求可以有不同贡献，不能给整个 Task 统一贴一种标签。

| 贡献性质 | 使用条件与例子 |
| --- | --- |
| 直接贡献（direct） | 已采用工作或已查明活动直接针对具体义务。CSV 解析任务直接实现“必填字段校验和错误定位”，即使只覆盖其中一部分也可保留准确的直接覆盖。 |
| 间接支撑（supporting） | 有明确支撑机制，但没有直接履行该需求义务。同一解析任务为“批量导入”提供有效输入，却没有完成批次上传、预览、确认和历史管理。 |
| 旧记录未分类／待核对 | 历史关联缺材料时保留原记录与缺口，不默认直接贡献，也不自动否定。它不是新增正式贡献类别；新关系缺依据时不建立正式绑定。 |

直接验证仍是验证活动，直接探索仍是探索活动；只有该需求本来要求这些成果，才按相应义务评估满足。需求间已有前置依赖可以展示支撑路径，不会沿每条依赖自动新增间接支撑关联。普通参考与直接贡献的组合需要澄清具体活动，旧不清晰值保留诊断。

重判时先读完整需求、验收和排除项，再读 Task 当时的采用范围及必要结果，说明“具体义务 → 工作或结果 → 直接／支撑理由 → 未覆盖与未知”。标题相似、可能受益、目录位置或 Task 已关闭都不足以证明贡献。早期任务确实履行了当前需求的真实子义务时，也不因年代早而一律降为支撑。

可以要求“只分析所有现有需求的任务关联，不改文件”，或“在不改需求验收和 Task 状态的前提下，纠正有依据的关联并保存”。全范围请求分批完成并报告已读、已判定、未读与未保存范围；只分析时不写文件。资料充分的旧关系在原关联 ID 下补分类或纠正 direct/supporting，保留旧依据与必要历史；充分反证可否定关系，资料不足或冲突则保留原值。同一需求、Task、角色及等价覆盖有冲突分类时保留冲突，不优先选 direct 或最新记录，也不另造编号双挂。曾被否定的关系没有新依据时不能靠换编号、改分类或改理由恢复。

新建、重新分类或实质更改角色、覆盖、Task 身份的 v5 活动关系需要具体覆盖、理由和实际来源。只改显示名称、重排数组或迁移格式不要求重新判定未变的旧关系；重复旧编号仍保留诊断，每条旧记录只对应一条保留记录，额外新增的行单独检查。只迁移需要贡献字段的文件，原 v4 路线图可以保留。修正关系不授权缩减验收、改变 Task 生命周期、发布交付报告或重排路线图。详细方法见[共同判定指引](../../runtime/vnext/support/product-maintenance/references/binding-contribution.md)和[业务示例](../product/project-maintenance/examples/binding-contribution.md)。

进度查看应分开回答“安排了什么”“实际进行了什么活动”和“哪个范围已经有成果”：

| 读到的事实 | 可以说明的进度 |
| --- | --- |
| 已准备／采用 Task，有直接关联 | 已安排直接工作；没有实际执行事实时不能说需求已开始。 |
| 对应覆盖有实际执行或 Step 事实 | 说明该范围内的实施、修复、验证或探索活动；宽任务无法定位到某项义务时，仅说明有关联的活动 Task。 |
| 支撑 Task 执行或关闭 | 说明支撑活动，不能推定下游需求已实施或已满足。 |
| 当前目标、范围、对象下适用的 Assessment | 按该报告解释已满足、部分满足、未满足或尚未判定；历史成果和当前适用性分别保留。 |

统计有效关联条数与唯一已确认 Task 身份数时，直接、支撑、未分类分别展示；同一 Task 可出现在多个组，组内 Task 数不能相加充当唯一总数。已否定关系不计入有效关联，未知身份不凑成已确认 Task。父需求汇集子项时保留原 owner、覆盖与来源，共享后代去重；子项直接贡献不自动变成父项自身直接贡献或父项满足。关联状态为 active 仅表示关系有效，Task 的关闭、跳过、暂停、失败仍分别解释。

没有可恢复历史 Task 的真实代码与验收仍可以独立评估，不要求补造 Task 或先补直接关联。纯贡献纠正不改变业务定义摘要；文件字节、关系适用性、成果和规划安排分别核对。当前 Roadmap 一致也不能代替成果报告，核对时间更不能当成功能完成时间。生产、安装及有限合成消费的实际范围见[v5 验证记录](../ops/binding-progress-v5-validation.md)。

### 关闭后的局部对账

先复用真实操作返回的 Task 身份和事件引用。只有历史来源且身份无法确认时，保留未知身份和原位置，不用显示编号猜身份。Task 已建立而绑定保存失败时，读取最新业务文档，只重试关联；不再次准备 Task。关联本身不采用、切换、关闭或重开任务。

启用维护且授权覆盖、没有适用延期时，`$close-task` 在真实关闭并回读后，同次完成实际关联需求／功能点的范围化交付对账。读取当前正文及验收，把任务实际交付切片、验证对象／输入、已知未交付和未知部分对应起来；新增功能点不能因旧表未列出而遗漏。完整依据只保留在一份独立范围报告中，旧进展／实施页保留简短摘要和链接，旧时间与结论保持历史适用范围。

对账结果须有适用的独立 Assessment 并回读范围选择，或明确留下待处理项。缺目标范围声明、适用评价、证据，或维护暂停／延期、写入／回读失败时，在收口报告或既有获授权维护位置记录真实 Task／关闭引用、需求／功能点、已知目标及声明／报告位置、对象与证据、缺项原因和下一维护动作，再回读；无法保存则返回具体未保存位置和原因。不猜造 scope_id、不为收口擅自修改目标，也不把追加摘要或 pending_sources 当成评价完成。此时应报告“任务已关闭；该范围交付对账待处理”，不能宣称管理闭环完成。

关闭先作为事实保存，不能被评价缺失或产品报告的写入失败撤销；纯 Runtime close 不自动调用模型。复用适用旧评价和明确延期，不要求清空无关历史 pending、不强制重开任务或重跑业务测试；重试只补失败的报告或关联。

当前源码修复和有限验证见[收口范围对账验证记录](../ops/close-task-delivery-reconciliation-validation.md)。源码规则更新不表示业务项目已安装升级。

已经存在父 Task 续做位置时，产品评估和下一业务事项建议不能抢走焦点或阻塞已授权的原步骤。修复 Task 关闭也不证明原前提已满足；按实际续接和证据继续工作，不自动完成父步骤。

## 6. 在 TraceLens 中查看和核对

以下是已有历史验收记录覆盖的 v3 TraceLens 展示行为；需要使用包含相应改动的 TraceLens 副本，不能仅凭 vNext 安装版本推断页面已有这些能力。

- v3 当前需求按有效组成 DAG 折叠展示。共享子项保持单一身份，任一父路径展开即可到达；无可展示父项的子项保留入口。搜索和缺口筛选保留命中项与祖先，页面返回时保留展开状态。
- 父需求汇集自身及有效当前组成后代的状态为 active 的 TaskBinding（关联）；不沿支撑、依赖或历史关系传播。按真实 Task 身份去重，未知身份各条保留，每条角色、覆盖与来源仍可查看。
- 关联待核对与真实生命周期分别显示。同一 Task 有一条可信匹配和另一条冲突关联时，可信 Runtime 状态及导航保留，冲突另列警示，不能把已关闭或暂停的 Task 改成未知。
- 目标节点按自身范围读报告；需求按所选目标、范围与对象读取。原报告结论和当前适用性分别说明；关键章节是带位置的原文片段，可以返回完整来源。
- 项目／计划材料有原文入口，材料缺少或未决不被编造为完整度状态。读取失败保留具体诊断，旧快照说明时间和局限，不展示成零需求或全项目完成。

消费 v5 时应保留每条关系的直接／支撑／未分类、角色、覆盖、原 owner 与来源，并分别解释活动和成果，不能把支撑任务关闭显示为需求交付。最新生产与合成消费证据见[v5 验证记录](../ops/binding-progress-v5-validation.md)；该记录明确保留浏览器 UI 未验收的范围，不把格式支持推导成所有页面已经完成升级。

TraceLens 只读，不运行模型、不写被观察项目、不重放 Task journal，不计算百分比。查看到缺口后，把相关项目位置、材料和问题交给目标项目的 vNext 维护，再刷新 TraceLens。[模板与解析交接](tracelens-product-documents.md)保留 v2 兼容资料；v3–v5 字段、报告选择及贡献消费见[文档契约](../product/project-maintenance/document-contract.md)。

## 7. 整理已有项目与处理局部失败

先核对实际工作副本、AGENTS／冻结约束、已安装软件及已有 PRODUCT，沿用真实身份。根据用户所选资料分批读取正文：整理目标和完整需求，记录有来源的已有成果；复用仍适用的旧安排，补可靠历史 Task 关联和重要变化依据。未知旧意、日期或身份保持未知，不强制全史迁移，不重新创建或重开旧任务。

先找已有信息、再核对矛盾、最后区分当前必要缺口与未来可选建议。已有设计写明的规则无需另造文档；缺一次新的全量测试也不抹去已记录成果。资料读完、格式可解析、业务盘点和具体交付结论是分别报告的结果。

PRODUCT 区分当前规范文档、按引用读取的来源和获授权保存原文／历史的位置。原文与历史不同时成为当前定义；没有入口、维护暂停或局部资料损坏时，普通开发仍可继续。既有 v1–v5 文件按原版本可读；新增字段只显式迁移相关文件，不要求全项目升级格式，新范围报告仍可引用未迁移的旧需求。例如 v3 Goal、v5 Requirement 和 v4 Roadmap 可以共存，历史定义与 Task 结果各自保留。

原文保存成功而摘要／关联失败，保留已存原文；多文件部分成功，仅补未保存项。发生并发冲突时保留用户字节，读最新内容后局部重试。维护结果应说清已读、未读、已存、冲突、待核对和延期范围，不把失败包装为成功或开发门槛。

## 8. 软件来源与技术细节

熟悉 vNext 的目标项目用户无需在项目中运行源码仓库的 Bun 构建。需要安装时，先明确软件来源和目标目录，按[分发使用说明](../../packages/vibe-governance/README.md)操作；使用这轮本地候选必须取得对应构建产物，`npx vibe-governance@latest` 不能证明取得了本轮功能。

未安装项目使用 install；旧版 vNext 使用明确 upgrade；legacy 迁移另按其流程。软件安装／升级不创建或覆盖目标项目的 PRODUCT、需求、讨论原文和 Task 历史。同版本正常安装通常校验后 no-op；upgrade 可执行受限行政修复，但不能任意覆盖同版本不同内容的受管资产。遇到 `MANAGED_TARGET_DRIFT` 先核对来源、已安装记录和实际文件，不用删安装状态或强制覆盖来刷新候选。

早期完整需求交接中，同版本 upgrade 被拒后采用全新隔离目录的事实仍保留；它不是升级证明。`0.24.10` 的[v5 验证记录](../ops/binding-progress-v5-validation.md)另行记录了实际构建 `0.24.9` 后正常升级及隔离宿主数据保全，仍限于该记录的合成范围，不认证任意真实项目已安装或所有平台通过。

软件版本 `0.24.10` 与文档格式版本不是同一编号。选择格式时按实际字段需求：

| 内容 | 使用的文档格式 |
| --- | --- |
| 总目标、组成关系、登记顺序和范围报告 | v3；v4/v5 继承相同规则和业务定义摘要算法。 |
| 项目实施路线图的核对基线 | v4 或 v5；已有 v4 路线图无需因其他文件增加贡献分类而迁移。 |
| 目标／需求关联的直接、间接支撑贡献 | v5；旧 v1–v4 Schema 不接受 contribution 字段。 |
| PRODUCT 的来源、托管与原文保存范围 | Manifest v2；旧 Manifest v1 可读，受管写入前显式迁移。 |

旧产品文档 v1 可读，写入前需明确迁移；v2–v5 保留各自写入规则，所有格式升级只作用于所选文件并禁止降级。不要把新字段塞进旧格式或扩展字段来冒充支持。未知未来格式保留原文入口与不支持诊断，不当作零需求。保存分类不改变需求义务摘要，精确整文件来源仍独立核对字节变化。

按需查阅技术资料，无需把字段或 helper 请求手写进日常对话：

- [文档契约](../product/project-maintenance/document-contract.md)：唯一字段语义；第 10 节说明 v3 定义与范围报告，第 11 节说明 v4/v5 路线图基线，第 12 节说明 v5 贡献及进度解释。Manifest 继续 v2。
- [helper API](../../runtime/vnext/support/product-maintenance/API.md)与[Schema](../../runtime/vnext/support/product-maintenance/schemas/)：读取、保存、迁移、定位、字节保护和诊断。

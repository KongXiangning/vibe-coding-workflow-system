# Test Admission Policy

## 1. 适用范围与目标

本规则适用于目标项目中 prepare-task 的测试规划，以及 review-draft
对测试计划和验证方案的审查。

目标是保留真正具有缺陷检出力和回归保护价值的测试，减少低价值测试
造成的生成 token、审查 token、执行时间和维护成本。

本规则属于 Skill 层的工程判断要求，不引入新的 Runtime 准入机制、
状态、字段或逐测试审批流程。

测试精简不等于测试最小化；测试数量和覆盖率都不是独立目标。

## 2. 测试必要性的判断

拟新增或显著扩展持久自动化测试时，应判断：

- 保护对象：它保护什么具体业务行为、验收要求、稳定契约、
  已知回归、关键不变量或具有实际影响的风险？
- 检出能力：什么合理且具体的错误会使它失败？断言是否验证了
  需求或契约要求，而不是复制当前实现、让 mock 自证正确？
- 增量价值：已有测试或检查是否已经充分保护该行为？
  新增测试补足了什么实质缺口？

这些问题用于工程判断，不要求为每个测试填写理由、绑定新的 ID、
创建准入表或生成独立报告。可以按业务行为或契约对测试分组判断。

风险不必已经造成过线上事故，但应有具体的需求、输入边界、
契约或故障机制依据，不能只用“可能出错”“多测更安全”作为理由。

## 3. 保留有价值的单元测试

“业务相关”不等于“只允许业务入口测试或 E2E”。

对于具有稳定契约，并且逻辑关键、被多处依赖或故障影响较大的
公共函数、共享组件、核心算法、解析与序列化、权限判定、
状态转换和关键计算，应保留或规划必要的聚焦单元测试。

公共函数、导出函数或 helper 的身份本身，不自动构成测试理由。
应保护其有价值的行为、边界和不变量，而不是机械地逐函数、
逐分支生成测试。

测试层级由需要证明的行为决定，不默认偏向 E2E，也不默认偏向单测。

## 4. 识别低价值测试

以下理由本身不足以支持新增持久测试：

- 新增或修改了代码、函数、分支、helper，或者存在覆盖率缺口。
- 能想象出更多 edge case，但没有具体契约或风险依据。
- 为实现细节、内部调用顺序或 mock 配置重复编写断言，
  却没有验证被依赖的行为或交互契约。
- 与已有测试重复，不能提供独立的错误检出或回归保护价值。
- 只校验标题、注释、文档措辞或其他不影响行为的文本。

以上不是对 mock、边界测试或文本断言的一概禁止。
当交互次数、顺序、协议字段或用户可见文本本身属于明确契约时，
应按其实际保护价值判断。

对低价值的拟新增测试，应优先取消、合并或缩小范围，
而不是为它补造需求、claim 或风险说明。

## 5. 选择 minimum-sufficient verification

优先检查并复用相关的已有测试和夹具；确有覆盖缺口时，
再扩展现有测试或新增聚焦测试。

需要验证一个 claim，不等于必须新增持久自动化测试。
可以根据具体问题采用已有回归、集成检查、静态分析、
人工验收、真实设备验证等适当证据。

但一次性的静态检查或人工验证，不自动替代有必要长期保留的
自动化回归保护。

区分以下两项决定：

1. 某个测试是否值得长期保留。
2. 某个已有测试是否需要成为本次任务的 acceptance evidence。

已有测试有价值，不代表必须绑定为本次任务的验收证据；
已有充分证据时，不应机械地将整套测试纳入本次验收。

反过来，低价值测试也不会因为改称 ordinary regression 就变得有价值。
“转为 regression”不能成为保留无效新增测试的理由。

## 6. 审查与权限边界

审查必须同时识别：

- Over-testing：无实质保护价值、重复、过细或过度耦合实现的测试。
- Under-testing：真实业务行为、关键公共契约或重要风险缺少必要保护。

即使 draft 没有提出新增测试，也应检查是否遗漏了关键验证。

审查范围以本次任务及其影响面为限，不默认开展全仓库历史测试清理。
不得为了减少测试而降低已确认的验收要求、忽略相关失败，
或删除仍具有独立保护价值的测试。

本规则不扩大 skill 的修改权限。测试删除、计划调整和证据变更，
仍按现有 skill 职责与 workflow 授权路径处理。
